# 文档脱敏规则

> 面向**对外可发布**的内容（`docs/blog/`、公开 README、对外分享的设计文档等）。
> 目标：文档不泄露可识别的真实项目 / 个人 / 环境标识。
> 这是**通用方法论**，不是某一次替换的映射表——具体替换名每次可不同（见末尾示例）。

## 规则 1：先识别、先询问，再动手

写或改一篇**可能对外**的文档时，先扫一遍有没有下列敏感类别（规则 2）。
**只要命中，先问用户「这篇要不要脱敏、脱敏到什么程度」，得到确认再替换**——
不要默认脱敏（内部文档可能故意保留真名），也不要默认不脱敏（对外的必须处理）。

判断「是否对外」拿不准时，就问。

## 规则 2：敏感内容的通用类别

按类别识别，不记具体名字：

| 类别 | 说明 | 典型例子 |
|---|---|---|
| 真实项目/仓库/产品名 | 可定位到具体团队或产品的名字 | 其他仓库名、代号、内部产品名 |
| 个人身份 | 用户名、真实姓名、邮箱、账号 | 绝对路径里的 `/Users/<name>/`、git 作者、真实邮箱 |
| 业务域实体 | 暴露公司业务方向的领域名词 | 行业专有实体（金融/安防/医疗等特征词） |
| 环境/基础设施标识 | 真实环境的可定位信息 | 真实库名、内网 host/IP、bucket 名、容器/服务名 |
| 凭证类 | 任何密钥、token、口令 | 一律不得出现真实值，用占位 |

`Casbin`、`GORM`、`Redis` 这类**公开开源库/技术名不是敏感信息**，不脱敏。

## 规则 3：通用替换手法

1. **占位要"匿名但保留角色区分度"**：多个同类实体要能区分（如两个老项目分别记
   「老项目 A / 老项目 B」），否则对比性论述会塌。占位本身不得反向定位到真实对象。
2. **散文用中文标签、代码用英文占位**：
   - 散文里 → 可读的中文标签（如「老项目 A」），**不加反引号**（反引号像代码标识符，
     且「老项目 \`老项目 A\`」这种双重包裹是典型返工错误）。
   - import 路径 / 目录树 / 文件名里 → **无空格英文占位**（中文带空格会破坏
     `import "x/<占位>/..."` 这类路径）。同一真实名在两种语境下映射到两个占位，正常。
3. **子串陷阱**：替换短词前先确认它不是更大单词的子串
   （经典：`face` 是 `interface` 的子串，裸替会毁掉 `interface`）。
   用**整词/整标识符**匹配，或先精确清点所有含该串的 token 再定替换范围。
4. **长串先于短串**：`content-center-backend` 要先于 `content-center` 替，否则残留后缀。

## 规则 4：只改文档，不动真实配置/代码

脱敏只作用于**文档及文档内的示例**。磁盘上真实运行的
`config/*.yaml`、`Makefile`、`*.go`、`migrations/*.sql` 等**保持原值**——
文档里的示例库名脱敏，真实 config 里的同名值不动（否则会改坏运行环境）。

## 规则 5：自检

替换后用 grep 复核**本次涉及的真实标识**零残留、且没有双重包裹
（`老项目 \`老项目`）、没有子串误伤（如 `interresource`）。
具体检查命令按本次替换的词自行组合，不固定。

# 配置加载封装设计(v6:合并回 internal/config 单包自包含)

> **当前形态(2026-06-24 合并后)**:回到**单包**——`pkg/xconfig` 的 viper 加载机制内联进 `internal/config`,变成两个**包内私有**函数 `loadFromYAML` + `override`。`pkg/xconfig` 目录已删除。
> - `internal/config` = **自包含**:类型化 `Config` + 内联的 viper 加载(`loadFromYAML`)+ 显式 env 覆盖(`override`)+ 显式校验(`validate`),全在一个包。新微服务复制整个目录,只改 `Config` 字段 / `override` 的 env 名 / `validate` 规则。
>
> v6 动机:v5 的"可复用库 `pkg/xconfig` + 项目 `internal/config`"两层拆分,前提是"新微服务通过共享 module **import** `pkg/xconfig`"。但现实是各微服务独立 module、config **各自复制**(兄弟项目 backend-rbac 就是独立 module、没用 xconfig)。复制模式下,1 个自包含包 比 "2 个包 + import 连线" 更简单、对 AI 更友好。前提失效 → 合并。详见下文"v6 演进"。

## 设计演变(为什么走到这里)

| 阶段 | 做法 | 问题 |
|---|---|---|
| v1 | `internal/config` + yaml.v3 + 4 个硬编码 os.Getenv | 不可复用 |
| v2 | `pkg/utils/xviper`(`Load(target any)`)+ `internal/config` | `any` + 反射 env 覆盖 —— **过度设计**(当时被否) |
| v3 | `pkg/xconfig`(自有 Config + 类型化 `Load(path)` + 显式覆盖) | 可用,但 Config 与 loader 耦合在 xconfig 里,跨项目复用时整个包都要改 |
| v4 | `pkg/xconfig` 只留**可复用 Loader**;项目 `Config` 移到 `internal/config` | 正确方向(loader 与 Config 分层),但 Loader 结构体 + 5 个 option 过度设计 |
| v5 | `pkg/xconfig` 精简为 **`Load`+`Override` 单文件**,删 functional options 与 Loader 结构体;tag 改回 `yaml:` | **最简**:API 表面只剩 2 个函数、零死代码;对齐 go-zero `conf.MustLoad` 一行哲学 |
| **v6(当前)** | 合并:`pkg/xconfig` 内联进 `internal/config`,成单包私有函数 `loadFromYAML`+`override`;删 `pkg/xconfig` 目录 | v5 的"可复用库"前提(跨 module **import** 共享)在多独立 module + AI-fork 现实下不成立、收益=0;复制模式下单包更简单、对 AI 更友好 |

**核心判断**(贯穿 v2→v6):反射/泛型是为"结构未知"准备的。**项目 Config 结构是已知的**(每个项目自己定义),所以环境变量覆盖、校验都该用**显式类型化代码**,不该反射遍历。但"读取机制"(viper 读文件 + 反序列化)是**跨项目通用的**。v4/v5 把这两者**物理分离**(通用机制进 `pkg/xconfig`、已知结构进 `internal/config`);**v6 重新审视了"物理分离"的代价**——见下文 v6 演进。

## v5 演进:为什么砍掉 Loader 结构体与 functional options(2026-06-23)

v4 把 `pkg/xconfig` 做成 `Loader` 结构体 + 5 个 functional option(`WithFile/WithSearchPaths/WithFileName/WithFileType/WithDefaults`)。落地后发现四点问题,全部源于过度设计:

1. **5 个 option 里 4 个是死代码**:`internal/config` 永远只调 `WithFile(path)`,`WithSearchPaths/WithFileName/WithFileType/WithDefaults` 从未使用。API 表面远大于实际需要。
2. **Loader 结构体的预留理由已作废**:v3 选结构体是为"未来 Reload/Watch/Get 挂 `*Loader` 上不破 API"(见下文问题 3)。但 [`04 蓝图`](04-三层架构与动态多租户配置蓝图.md) 已明确**动态配置走 L2 `sysconfig/Provider`**(DB + 本地缓存 + Redis Pub/Sub),**不靠扩展文件 Loader**。结构体的前向兼容前提作废 → 退回自由函数。
3. **tag 退化**:`mapstructure:` 是 viper 专属痛点(社区反复吐槽)。v5 用 `viper.Unmarshal(target, func(d *mapstructure.DecoderConfig){ d.TagName = "yaml" })` 让 viper 读 **yaml tag**,且 `TagName` 与 `DecodeHook` 互不影响,viper 默认的 `StringToTimeDurationHookFunc` 仍把 `"10s"` 解析为 `time.Duration`。
4. **两文件撑小库**:`xconfig.go` + `options.go` 合并为单文件。

### v5 的 `pkg/xconfig/`(单文件)

```go
func Load(path string, target any) error   // viper 读文件 → 解码到 target(yaml tag + duration)
func Override(dst *string, key string)      // os.LookupEnv,有就覆盖(含空串;见问题 8)
```

### v5 的项目层调用(`internal/config`)

```go
var cfg Config
xconfig.Load(path, &cfg)
xconfig.Override(&cfg.Database.Password, "DB_PASSWORD")
// …其余密钥 + validate
```

> 下文"设计过程中遇到的问题与决策"仍记录 v2→v4 的取舍(反射否决、AutomaticEnv 坑、set-to-empty 语义等),这些**结论在 v5 全部沿用**;仅 API 形态从"Loader 结构体 + options"变为"自由函数",tag 从 `mapstructure:` 改回 `yaml:`。下文 `## 目标(v4)` / `## pkg/xconfig/` / `## internal/config/` 几节的**代码片段是 v4 形态的历史记录**,以本节(v5)为准。

## v5.1 演进:Load 变可变参数 + base/overlay 合并(2026-06-23)

v5 的 `Load(path, target)` 只读单文件,多环境靠部署时 `-config` flag 选不同文件(见 [Step 17](../../step-17-deployment.md))。随后用户决定让**加载器 env 感知**,采用 **base `config.yaml` + `config.{APP_ENV}.yaml` overlay** 的合并模型(共享默认值在 base,各环境只写差异,DRY)。落地为对 `Load` 的小幅扩展:

```go
// v5.1:可变参数。paths[0]=base 用 ReadInConfig;paths[1:]=overlay 依次 MergeInConfig 合并
func Load(target any, paths ...string) error
```

项目层 `internal/config.Load(basePath)` 据 `APP_ENV` 推导 overlay 路径(`APP_ENV` 纯 opt-in:未设=仅 base,即 dev;设了=追加 `config.{env}.yaml`,缺失由 merge 步骤 fail-fast)。`-config` flag 仍指 base,**main.go 不动**。

**为什么这个扩展安全,且不违背 v5 哲学**:
1. **仍 2 个函数**(`Load` + `Override`)、零反射(反序列化仍交给 viper)、显式 env 覆盖、显式校验 —— 只是 `Load` 多了多文件合并能力。
2. **不碰 `viper.AutomaticEnv`**(rbac 根因坑)。`MergeInConfig` 改的是 viper 实例的 settings,`Unmarshal` 读到合并结果 —— 与 AutomaticEnv 的"Unmarshal 不查 env"坑无关,**文件合并安全**。
3. **viper 仍只在 `pkg/xconfig` import**;`internal/config` 不引 viper(边界不变)。

**已知 gotcha(测试钉死)**:`MergeInConfig` 对嵌套 map **深合并**;对标量与 slice,overlay 值**整体替换** base(slice 不追加)。故 overlay 里凡要改的 list 必须写全。见 `backend/internal/config/config_test.go::TestLoadYAML_MergeOverlay`。

> v5.1 不改 v5 的任何结论(反射否决、AutomaticEnv 坑、set-to-empty 语义等全部沿用);仅 `Load` 签名从 `Load(path, target)` 变为 `Load(target, paths...)`,tag 仍 `yaml:`。

## v6 演进:合并回 `internal/config` 单包(2026-06-24)

v5 的两层(`pkg/xconfig` 可复用库 + `internal/config` 项目结构)成立的前提是:新微服务通过共享 Go module **import** `pkg/xconfig`——这样加载逻辑一处维护、N 处用,DRY 成立。落地后审视发现这个前提**不成立**:

1. **现实复用模式是"复制",不是"import"**:各微服务是独立 Go module(兄弟项目 `backend-rbac` 就是),跨 module 无法 import 彼此的 `pkg/`;新微服务的 config 实际是**复制一份**。既然要复制,复制 1 个自包含的 `internal/config` 目录,比复制"2 个包 + 连 import 线"简单。
2. **可复用库收益 = 0**:全仓库只有 `internal/config` 一个消费者;`backend-rbac` 根本没用 xconfig(它自己一套更老的全局 viper `pkg/config`)。N=1,"一处改 N 处用"的 DRY 收益不存在。
3. **AI 写代码放大了这点**:AI 给每个微服务 fork 一份 config,不会去 import 一个共享库。多一个包 + 一层契约 + 文档要同步,只剩负担。

**合并做法**:`pkg/xconfig` 的两个自由函数(`Load` / `Override`)收为 `internal/config` 的**包内私有**函数(`loadFromYAML` / `override`),签名不变;公开 `Load(basePath)` 改调私有函数。`pkg/xconfig/` 目录删除。

### v6 的 `internal/config/`(单包自包含)

```go
// 内联的 viper 加载机制(私有,不随项目变)
func loadFromYAML(target any, paths ...string) error // viper 读 base(+overlay MergeInConfig)→ 解码到 target(yaml tag + duration)
func override(dst *string, key string)               // os.LookupEnv,有就覆盖(含空串)

// 项目专属(新项目改这里)
type Config struct { ... }                           // yaml tag
func Load(basePath string) (*Config, error)          // 拼 paths(+APP_ENV overlay)→ loadFromYAML → override 4 个密钥 → validate
func validate(c *Config) error                        // 显式、全覆盖
```

### v6 沿用 v5 的全部结论

合并只改"物理打包"(独立包的导出函数 → 同包私有函数),**不改任何机制**:
- 零反射(反序列化交给 viper)、显式 env 覆盖、显式校验 —— 全部沿用。
- **绝不用 `viper.AutomaticEnv`**(rbac 根因坑,见问题 7 / [`02-现状与问题总结.md`](02-现状与问题总结.md))—— 沿用。
- `set-to-empty` 覆盖语义 —— 沿用。
- viper gotcha(嵌套 map 深合并、slice 整体替换、duration 解码、yaml tag)—— **测试全部搬进 `config_test.go`**(原 `xconfig_test.go` 的 `TestLoad_*` 改名 `TestLoadYAML_*` 避撞、`TestOverride_*` 保留),gotcha 防护网不丢。

### v6 是 v1→v5 精简路线的同向下一步

v2 砍反射、v5 砍 Loader 结构体 + functional options、v5.1 加多文件合并 —— 一路在做减法。v6 砍掉最后的"独立可复用包"这层抽象(因其前提不成立),回到"一个自包含包"。**形态上接近 backend-rbac 的单包 `pkg/config`,但机制是修过的**(不静默、无全局、fail-fast、真测试)。

> 下文"设计过程中遇到的问题与决策"记录 v2→v5 的取舍(反射否决、AutomaticEnv 坑、set-to-empty 等),**结论在 v6 全部沿用**;仅物理形态从"两个包"变为"一个包"。下文 `## 目标(v4)` / `## pkg/xconfig/` / `## internal/config/` 几节的**代码片段是历史记录**(v4/v5 形态),**以本节(v6)为准**。

## 设计过程中遇到的问题与决策(重点)

> 这一节记录重构时真实碰到的取舍,供下次 AI 直接理解"为什么是现在这样"。

### 问题 1:用户要"跨系统复用",又坚持"不用反射" —— 二者本质冲突

- "可复用、不重写读取逻辑" ⟹ loader 要泛型/反射(库不知道调用方的 Config 结构)。
- "不用反射、类型化 Config" ⟹ 必须显式,每个项目自己写。

**解决**:承认这是两个层次的需求,拆开。
- **可复用层**(`pkg/xconfig`):只做"viper 读文件 + 反序列化到 `any`"。这一步天然复用,且我们代码不写反射(交给 viper)。
- **项目层**(`internal/config`):显式 `Override` + 显式 `validate`,因项目而异,本就该各自写。

即:**"不重写读取逻辑"指的是 viper 那套机制不重写;Config 字段/env 名/校验本就因项目而异,显式写在项目里是天经地义的,不算"重复劳动"。**

### 问题 2:反射 walker 方案被否决

重构初版曾提议"struct tag 驱动的反射 walker":给字段打 `env:"DB_PASSWORD"` / `default:"5432"` / `validate:"required"` 三种 tag,加载器内部 `reflect` 遍历一次性处理 env 覆盖 + 默认值 + 校验(类似 cleanenv / caarlos0-env)。

**用户明确否决**:"不使用反射,直接定义 type config 用就行,新项目改这个 config"。理由:配置结构已知,反射是过度设计。所以 v4 保持显式类型化,不引入 tag 驱动反射。

### 问题 3:API 形态 —— 自由函数 vs 结构体 Loader

候选:
- 自由函数 `Load(target, opts...)`(v3 风格,一次性)
- 结构体 `Loader`:`New(opts...)` + `(l).Load(target)`

**决策:选结构体 `Loader`**。理由:这是后台框架地基,未来 `Reload` / `Watch` / 运行时 `Get()` 都挂在 `*Loader` 上即可,**不破现有 API**;自由函数形态届时要改签名或另引类型。当前虽只用一次性 `Load`,但 Loader 已为扩展预留。(用户在"结构体 vs 现在这版"二选一时选了结构体。)

### 问题 4:env 覆盖如何"去硬编码"但又不反射

v3 是 4 个手写 `os.LookupEnv` if 块硬编码在 loader 里。v4 既要去硬编码、又不能用反射泛化。

**解决**:把"应用 env 覆盖"的机制抽成类型化 helper,env 名仍由项目显式列出:
```go
// pkg/xconfig(可复用机制)
func Override(dst *string, key string)   // LookupEnv,有就覆盖
```
```go
// internal/config(项目列出自己的密钥)
xconfig.Override(&cfg.Database.Password, "DB_PASSWORD")
xconfig.Override(&cfg.Redis.Password, "REDIS_PASSWORD")
```
**诚实的代价**:每个项目要写几行 `Override`(密钥名本就因项目而异,无法避免)。可复用的是 `Override` 机制 + viper 读取,不是密钥清单。只做 `string`(密钥都是 string);其他类型若要 env 覆盖,调用方自行 `os.LookupEnv`。

### 问题 5:校验如何"补全"但又不反射

v3 的 `validate` 只查 3 项。"补全校验"如果用 `go-playground/validator`(读 `validate:` tag,反射)会违反"不用反射"。

**解决**:`validate` 手写在项目层、补到全覆盖(port/mode/timeout/cors/db/redis/jwt/log)。**诚实代价**:每个项目写自己的 `validate`;好处是零反射依赖、所有规则一处可见。

### 问题 6:GracefulTimeout 新增字段"校验了却没用"

v4 给 `Server` 加了 `GracefulTimeout`(Gin 集成形态需要)。初版计划 main.go 不动,导致该字段被 `validate` 要求 >0 却无人使用(死字段)。

**解决**:在 main.go 的优雅关闭处用上它 —— `context.WithTimeout(ctx, cfg.Server.GracefulTimeout)`,替换硬编码 `30*time.Second`。顺带移除因此不再使用的 `"time"` import(那是 main 里唯一的 time 用法)。

### 问题 7(沿用 v3):绝不用 viper.AutomaticEnv

`AutomaticEnv` 与 `Unmarshal` 不兼容(`Unmarshal` 走 `AllSettings()`,不查 `AutomaticEnv`),嵌套 key 的环境变量覆盖**静默失效** —— 这是 rbac 兄弟项目的根因 bug。v4 同样走显式 `Override`。详见 `02-现状与问题总结.md`。

### 问题 8(沿用 v3):set-to-empty 覆盖语义

`Override` 用 `os.LookupEnv`(区分"未设置"与"设为空")。**设为空串也算覆盖** —— 用于显式清空某个密钥。不用 `os.Getenv`(空串=不覆盖,无法主动清空)。

## 目标(v4)

- **可复用加载库** `pkg/xconfig`:`Loader` + functional options + `Override`,整目录逐字复用
- **零反射(我们写的代码)**:不 import `reflect`;env/validate 全显式类型化
- **项目专属 Config 层** `internal/config`:自有 `Config` + `Load` + `validate`,新项目只改这里
- **类型化**:`Load` 返回 `*Config`,无 `any` 在项目层
- **自带测试**:`xconfig_test.go`(库行为)+ `config_test.go`(项目集成),均自包含
- **修掉 rbac 的坑**(见下表 + `02-现状与问题总结.md`)

## `pkg/xconfig/`(可复用,无反射)

**`xconfig.go`** —— `Loader` 结构体 + `New` + `Load` + `Override`:
```go
type Loader struct {
	file        string
	searchPaths []string
	fileName    string
	fileType    string
	defaults    map[string]any
}

func New(opts ...Option) *Loader        // functional options 配置
func (l *Loader) Load(target any) error // viper 读文件 + 反序列化到 target

// 显式 env 覆盖 helper(无反射;key 存在则覆盖,即使空串)。仅 string。
func Override(dst *string, key string)
```

**`options.go`** —— functional options:
```go
type Option func(*Loader)
func WithFile(path string) Option            // 显式文件路径,优先于 search paths
func WithSearchPaths(paths ...string) Option  // 搜索目录
func WithFileName(name string) Option         // 默认 "config"
func WithFileType(ft string) Option           // 默认 "yaml"
func WithDefaults(d map[string]any) Option    // viper.SetDefault 兜底默认值
```

> viper.Unmarshal 内部用 mapstructure(反射)是 viper 库的事,本包代码零反射、不 import reflect。

## `internal/config/`(项目专属)

**`config.go`** —— 自有 Config(仅 mapstructure tag)+ `Load` + `validate`:
```go
type Config struct {
	Server   ServerConfig   `mapstructure:"server"`
	Database DatabaseConfig `mapstructure:"database"`
	Redis    RedisConfig    `mapstructure:"redis"`
	JWT      JWTConfig      `mapstructure:"jwt"`
	Log      LogConfig      `mapstructure:"log"`
}
// ServerConfig 含 Port/Mode/ReadTimeout/WriteTimeout/GracefulTimeout/Cors
// CorsConfig 含 AllowedOrigins/Methods/Headers/AllowCredentials(供 Step 03 中间件)

func Load(path string) (*Config, error) {
	var cfg Config
	loader := xconfig.New(xconfig.WithFile(path))
	if err := loader.Load(&cfg); err != nil {
		return nil, err
	}
	xconfig.Override(&cfg.Database.Password, "DB_PASSWORD")
	xconfig.Override(&cfg.Redis.Password, "REDIS_PASSWORD")
	xconfig.Override(&cfg.JWT.AccessSecret, "JWT_ACCESS_SECRET")
	xconfig.Override(&cfg.JWT.RefreshSecret, "JWT_REFRESH_SECRET")
	if err := validate(&cfg); err != nil {
		return nil, fmt.Errorf("validate config: %w", err)
	}
	return &cfg, nil
}

func validate(c *Config) error { /* 显式、全覆盖:port 范围/mode 枚举/timeout>0/cors 非空/db 必填/redis addr/jwt 密钥与 TTL/log 枚举 */ }
```

## 为什么不用 viper.AutomaticEnv

见问题 7。`AutomaticEnv` 与 `Unmarshal` 不兼容,嵌套 key 覆盖静默失效。显式 `Override` 正确可见。

## 为什么不在包里用反射(我们的代码)

见问题 2/5。项目 Config 结构已知、静态。反射遍历是过度设计,且引入静默失败风险。显式类型化最直接、IDE 友好、可调试。可复用的是"读取机制",不是"结构处理"——结构处理本就该项目自己写。

## rbac 的坑 → 本方案 修复对照

| rbac `pkg/config/viper.go` 问题 | v4 方案 |
|---|---|
| `AutomaticEnv` 静默失效 | 显式 `xconfig.Override`(`os.LookupEnv`),正确可见 |
| 硬编码生产路径 | `WithFile(path)` / `WithSearchPaths`,path 由调用方传 |
| 死全局 `Get()` | 无全局;`Load` 返回 `*Config` 由调用方持有 |
| `fmt.Printf` + 不返错 | 全部返回 error,`%w` 包装 |
| 无校验 | 项目层 `validate`,全覆盖 |
| env 覆盖硬编码在 loader 里(改字段要动库) | env 清单移到项目层(`internal/config`),库只提供 `Override` 机制 |

## 复用模型(v6)

- **新微服务复制整个 `internal/config/` 目录**:它是自包含的(加载机制 + Config + validate 都在一个包)。
- **复制后只改**:`Config` 字段、`override` 的 env 名、`validate` 规则;`loadFromYAML` / `override` 是不随项目变的 viper 样板,原样保留。
- 复用模式是"**复制**"而非"import":各微服务是独立 Go module,跨 module 不 import 彼此 `pkg/`。故 v6 把加载机制内联回 `internal/config`,不再维护独立可复用库(`pkg/xconfig` 已删);`.claude/rules/reusable-package.md` 仍适用 xredis 等真正跨项目共享的库。

## 未来扩展(已在 Loader 预留)

`(l *Loader)` 上可追加,不破现有 API:
- `Reload()` —— 重新读文件 + 反序列化(需调用方持有 Loader)
- `Watch(onChange)` —— `viper.WatchConfig` + 回调;注意会原地改写调用方持有的 `*Config`,有数据竞争,需配合 `atomic.Pointer[Config]` 交换
- `Get()` —— 运行时读取最新配置

当前 v4 不实现(YAGNI),但 Loader 结构体形态让这些扩展不破坏 `New`/`Load` 签名。

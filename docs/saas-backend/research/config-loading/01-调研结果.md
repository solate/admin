# 配置加载方案调研

> 本轮(2026-06)为 Step 02 配置层选型/封装所做的调研。结论驱动了"提取可复用 Viper 封装"的决策。

## 背景

Step 02 基础设施层的配置加载当前是 ad-hoc 的 `yaml.v3 + os.ReadFile + 几个硬编码 os.Getenv`,只活在 admin/backend 一个项目里。同时 `backend-rbac` / `content-center-backend` 用的是 Viper 封装。观察到 **"Viper 加载机制基本不变,只有 config 结构体变"** —— 配置加载这一层值得抽成可复用加载器。

调研目的:弄清 2025 年 Go 社区配置加载的成熟方案,确认 Viper 是否仍是合理选择,还是有更优替代。

## 三方对比:Viper vs Koanf vs 纯 yaml.v3

| 维度 | **Viper** (`spf13/viper`) | **Koanf** (`knadh/koanf`) | **纯 `gopkg.in/yaml.v3`** |
|---|---|---|---|
| 定位 | 全功能默认选择 | 轻量 Viper 替代 | 够用就别上库 |
| 流行度 | ⭐⭐⭐⭐⭐ 最普及 | ⭐⭐⭐ 上升快 | ⭐⭐⭐⭐ 无处不在 |
| 支持格式 | JSON/TOML/YAML/HCL/INI/env/properties | JSON/TOML/YAML/env/CLI(可扩展) | 仅 YAML |
| 多文件合并 | ❌ 单文件 | ✅ 分层合并干净 | ❌ 手动 |
| 环境变量覆盖 | ✅ 内置 | ✅ 内置 | ❌ 手动 |
| 热重载(Watch) | ✅ 内置 | ✅ 通过 watcher | ❌ 无 |
| 性能 | 较重(反射 + 多依赖) | 轻量、模块化 | 最快 |
| API 复杂度 | 复杂、有全局状态 | 干净、可组合 | 最简单 |
| 全局状态魔法 | 有 | 无 | 无 |
| 适用场景 | 需要开箱即用全部能力(远程 KV:Consul/Etcd 等) | 想要灵活 + 速度的生产服务 | 小型、静态配置服务 |

## 2025 社区共识

- **Koanf 正被越来越多项目推荐为 Viper 替代**:更轻、模块化(provider/parser 可插拔)、多源合并干净、无全局状态魔法。
- **Viper 仍是"安全默认"**:生态最广、功能最全(远程 KV 存储)、团队熟悉度高。但代价是依赖重 + 全局状态。
- **纯 `yaml.v3` 对静态配置完全够用**:"别为了用库而用库" —— 一个简单 `yaml.Unmarshal` 能解决的事不必上完整配置库。
- **生产常见模式:分层加载** —— `defaults → 配置文件 → 环境变量 → CLI flags`。三方都能支持,Koanf 表达得最干净。

## 结论(驱动决策)

1. **保留 Viper**:用户现有两个项目(`backend-rbac`、`content-center-backend`)已是 Viper,选 Viper = 跨项目一致性最高、团队零学习成本。
2. **不引入 Koanf**:虽是更优的现代替代,但与现有 Viper 项目不一致,除非整体迁移,否则徒增一种风格。本轮 YAGNI。
3. **不退回纯 yaml.v3**:用户明确要"提取 Viper 封装"做可复用加载器。
4. **关键**:Viper 只用来做它真正擅长的 **文件加载 / 合并 / 反序列化**;环境变量覆盖**不依赖** Viper 的 `AutomaticEnv`(见 `02-现状与问题总结.md` 的不兼容坑),改由调用方显式 `os.LookupEnv` 完成。

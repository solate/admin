## 调研结论(驱动本篇的三层划分)

针对"SaaS 后端配置用什么",两轮外部 AI 调研结论高度一致,归纳为:

1. **静态/基础设施配置**(DB / Redis / JWT / Server / 第三方 Key):本地 YAML 文件 + 环境变量覆盖敏感值(12-Factor)+ 类型化 `Config` struct + 启动时 **fail-fast 校验**,经**依赖注入**传递。
2. **动态业务配置**(Feature Flag / 限流阈值 / 套餐参数):**业务数据库配置表 + 本地内存缓存 + 变更广播**(Redis Pub/Sub);或接入 SaaS 化 Feature Flag 平台。
3. **多租户个性化配置**(套餐配额 / 白名单 / 租户定制):**坚决放业务数据库**,通过请求上下文的 `TenantID` 动态加载并缓存,**绝不混入应用级配置中心**。
4. **演进路径**:初期保持极简(文件 + 库表);当**服务实例数增长到数十个、团队需要频繁批量调整运行时参数和审批流程**时,再平滑引入 Apollo / Nacos 等配置中心**接管 L2 动态配置**,而 **L1 静态文件加载机制保持不变**。

> 核心判断:**配置不是单一东西,而是三类生命周期完全不同的数据**。把它们混在一个加载器/一个文件/一个配置中心里,是大多数配置踩坑的根因。三层划分的目的是让每层用最合适的承载方式,且层间**互不污染**。

## 一、三层架构总纲

| 层 | 内容举例 | 承载 | 读取时机 | 变更方式 | 是否缓存 | 现状 |
|---|---|---|---|---|---|---|
| **L1 静态基础设施** | DB/Redis 连接、端口、JWT 密钥、超时、CORS、日志级别 | YAML 文件 + 环境变量 | **启动时读一次** | 改文件/改 env → **重启** | 否(读一次即固定) | ✅ 已实现 |
| **L2 动态业务配置** | Feature Flag、限流阈值、全局套餐默认参数 | 业务 DB 配置表 + 本地内存缓存 + Redis Pub/Sub | **运行时热路径读(走缓存)** | 写 DB → Pub/Sub 广播 → 各实例失效本地缓存 | **是(进程内)** | ❌ 蓝图 |
| **L3 多租户配置** | 租户套餐配额、租户白名单、租户级超时/品牌 | L2 配置表的 `scope=tenant` 行(全局默认 = `scope=global`) | **运行时按 `TenantID` 读(走缓存)** | 同 L2,但带 `tenant_id` 维度 | **是(按 tenant 分桶)** | ❌ 蓝图 |

### 层间边界(红线)

- **L1 不下沉到 L2/L3**:启动参数永远是文件+env,不放进 DB 表(否则没 DB 连不上 DB,鸡生蛋问题)。
- **L2/L3 不上浮到 L1**:会变的业务参数不进 YAML(改了要重启,失去"动态"意义)。
- **L3 不混入全局配置中心**:租户级覆盖是**业务数据**,按租户隔离;放进全局配置中心会绕过租户隔离规则(见 `.claude/rules/rbac-multi-tenant.md`)。
- **L2 和 L3 共用一张表、用 `scope` 区分**:不拆两套存储,合并为"系统配置表",`scope=global` 行服务于 L2,`scope=tenant` 行服务于 L3(见下表设计)。

## 三、L2 动态业务配置(实现蓝图)

### 3.1 适用判断:什么时候该用 L2 而不是 L1

只有同时满足**会变 + 不想重启**才进 L2。例如:Feature Flag(灰度开关)、限流阈值、套餐默认参数、维护公告开关。

> 反例:DB 连接池大小——虽然"会变",但改了通常需要重建连接,意义不大,留在 L1。
> YAGNI 提醒:**没有第一个真实的动态配置需求之前,不实现 L2**。本篇是蓝图,不是"现在就做"。

### 3.2 表结构:系统配置表(同时承载 L2 全局行与 L3 租户行)

> 遵循 `.claude/rules/junction-table-design.md`(独立主键 + 唯一约束 + 时间戳)与项目"`ID 全部 string`"约定(见 README 技术选型)。

```sql
CREATE TABLE sys_config (
    config_id   VARCHAR(20)   NOT NULL,               -- idgen.GenerateUUID(),项目统一 string 主键
    scope       VARCHAR(16)   NOT NULL,               -- 'global'(L2) / 'tenant'(L3)
    tenant_id   VARCHAR(20)   NOT NULL DEFAULT '',     -- scope=tenant 时填租户ID;global 固定 ''
    config_key  VARCHAR(64)   NOT NULL,               -- 自然键,如 'feature.new_dashboard'、'ratelimit.login'
    config_value JSONB        NOT NULL DEFAULT '{}',   -- 值,JSON(兼容 string/int/bool/object)
    value_type  VARCHAR(16)   NOT NULL DEFAULT 'json', -- string/int/bool/json(读取时按类型解码)
    description VARCHAR(255)  NOT NULL DEFAULT '',
    created_at  BIGINT        NOT NULL DEFAULT 0,
    updated_at  BIGINT        NOT NULL DEFAULT 0,
    PRIMARY KEY (config_id),
    UNIQUE (scope, tenant_id, config_key)              -- 同一 scope+租户下 key 唯一,防重复
);

-- L2 全局查询(按 key)
CREATE INDEX idx_sys_config_global ON sys_config(scope, config_key) WHERE scope = 'global';
-- L3 租户查询(按 tenant + key)
CREATE INDEX idx_sys_config_tenant ON sys_config(tenant_id, config_key) WHERE scope = 'tenant';
```

**设计要点**:
- **L2 与 L3 共表**:`scope` 字段区分。全局参数是 `scope='global'` 的行;租户覆盖是 `scope='tenant'` 的行。避免两套存储。
- **值用 JSONB**:动态配置值类型多变(布尔开关、数字阈值、对象),JSONB 最灵活;`value_type` 辅助读取端按类型解码。
- **租户行带 `tenant_id`**:受多租户隔离规则约束(见 L3)。全局行 `tenant_id=''`,属于"跨租户"读取范围。

### 3.3 接口设计:Store(持久层) + Provider(缓存+广播)

建议落点:`internal/sysconfig/`(与 `internal/config` 并列)。Store = Repository 角色;Provider = 业务热路径读入口(带缓存 + 订阅失效)。未来若需 HTTP 管理 API,再按域子包规范拆 `handler/sysconfig`、`service/sysconfig`。

```go
// internal/sysconfig/store.go —— 持久层(Repository 风格,用 GORM Gen)
package sysconfig

import "context"

// Row 是一行系统配置的持久层模型(对应 sys_config 表)。
type Row struct {
    ConfigID    string
    Scope       string // "global" / "tenant"
    TenantID    string // scope=tenant 时有值
    ConfigKey   string
    ConfigValue []byte // JSONB 原始字节,由调用方按 ValueType 解码
    ValueType   string
    UpdatedAt   int64
}

// Store 读写 sys_config 表。跨租户查询(全局行/管理后台)不加 TenantID 条件;
// 租户行查询由调用方(Provider)传入具体 tenant_id,见 rbac-multi-tenant 规则。
type Store interface {
    // GetGlobal 读 scope=global 的某 key(L2)。
    GetGlobal(ctx context.Context, key string) (*Row, error)
    // GetTenant 读 scope=tenant 的某租户某 key(L3 覆盖值)。
    GetTenant(ctx context.Context, tenantID, key string) (*Row, error)
    // Upsert 插入或更新(管理后台写)。写成功后由调用方负责发布失效广播。
    Upsert(ctx context.Context, row *Row) error
}
```

```go
// internal/sysconfig/provider.go —— 业务热路径读入口:本地缓存 + 订阅失效
package sysconfig

import "context"

// Provider 给业务代码用的配置读取入口。只读,带进程内缓存。
// 命中缓存直接返回;未命中回源 Store 并缓存。
type Provider interface {
    // GetGlobal 读 L2 全局动态配置;out 是调用方提供的指针(bool/int/string/struct)。
    GetGlobal(ctx context.Context, key string, out any) error
    // GetForTenant 读 L3:先查租户覆盖,缺则回退全局默认(见 §4.3)。
    GetForTenant(ctx context.Context, key string, out any) error
}
```

> 为什么 Store/Provider 分开:Store 只管 DB 读写(可测、无缓存);Provider 管缓存+广播+回退策略(有状态)。业务代码只依赖 `Provider`,不直接碰 Store。

### 3.4 本地缓存 + Redis Pub/Sub 变更广播

**失效模型**:写库后不直接更新各实例缓存,而是**发布失效消息**,订阅到的实例删除本地对应 key,下次读自然回源。配合**短 TTL 兜底**(防 Pub/Sub 丢消息)。

```go
// internal/sysconfig/cache.go —— 进程内缓存(示意骨架)
package sysconfig

import "sync"

type cacheKey struct { // 复合键,租户维度隔离,防串数据
    scope     string
    tenantID  string
    key       string
}

type localCache struct {
    mu     sync.RWMutex
    values map[cacheKey][]byte // key → JSONB 原始值
    exp    map[cacheKey]int64  // 简化:TTL 兜底时间戳;真实实现可只存 value + 统一 TTL 检查
}

func (c *localCache) get(k cacheKey) ([]byte, bool) { /* RLock 查 map + TTL 检查 */ }
func (c *localCache) set(k cacheKey, v []byte)      { /* Lock 写 */ }
func (c *localCache) del(k cacheKey)                { /* Lock 删 */ }
```

```go
// internal/sysconfig/broadcast.go —— Redis Pub/Sub 失效广播(基于现有 pkg/rdb)
package sysconfig

// 失效频道名:cfg:invalidate。消息体 = invalidateMsg 的 JSON。
const channelInvalidate = "cfg:invalidate"

type invalidateMsg struct {
    Scope    string `json:"scope"`
    TenantID string `json:"tenant_id"` // scope=global 时为 ""
    Key      string `json:"key"`
}

// publishInvalidation 在 Store.Upsert 成功后由 Provider 调用:写 DB → 广播失效。
func (p *provider) publishInvalidation(ctx context.Context, msg invalidateMsg) error {
    return p.rdb.Publish(ctx, channelInvalidate, mustJSON(msg)).Err()
}

// subscribeLoop 后台订阅协程:收到失效消息 → 删本地缓存对应 key。
// 在 main 启动(基础设施就绪后)起一个,随服务生命周期常驻。
func (p *provider) subscribeLoop(ctx context.Context) {
    sub := p.rdb.Subscribe(ctx, channelInvalidate)
    defer sub.Close()
    ch := sub.Channel()
    for {
        select {
        case <-ctx.Done():
            return
        case msg := <-ch:
            var m invalidateMsg
            if json.Unmarshal([]byte(msg.Payload), &m) == nil {
                p.cache.del(cacheKey{m.Scope, m.TenantID, m.Key})
            }
        }
    }
}
```

**关键设计**:
- **写后失效(不是写后更新)**:多实例下无法保证各实例缓存一致,统一"删缓存 + 下次回源",简单且正确。
- **TTL 兜底**:本地缓存项设短 TTL(如 60s),即使 Pub/Sub 丢消息,最多 60s 后自然回源修正。
- **订阅协程随 ctx 退出**:复用 main 的 `signal.NotifyContext`,优雅关闭时一并停掉(见 `cmd/server/main.go` 的 ctx 传播约定)。

### 3.5 接线点(未来实现时改哪里)

- `cmd/server/main.go`:`database.New` 后,`sysconfig.NewProvider(db, rdb, log)` → `p.SubscribeLoop(ctx)` 起订阅 → 注入需要的 service。
- 各业务 service:构造函数加 `cfg *sysconfig.Provider` 参数(依赖注入),热路径调 `p.GetGlobal(ctx, "feature.xxx", &flag)`。
- 配合 Step 05 的 `xcontext`:`GetForTenant(ctx, ...)` 内部取 `xcontext.GetTenantID(ctx)`(见 §4)。

## 四、L3 多租户配置(实现蓝图)

### 4.1 模型:全局默认 + 租户覆盖

- **全局默认**:`sys_config` 中 `scope='global'` 的行(如套餐默认配额)。
- **租户覆盖**:`scope='tenant'` 且 `tenant_id=X` 的行(某租户单独调高配额)。
- **合并语义**:`GetForTenant(ctx, key)` = 有租户覆盖用覆盖值,**否则回退全局默认**,再否则用调用方传入的代码内兜底默认。

> 这正是外部 AI 结论 3 的"全局默认 + 租户覆盖"模式,且**数据落在业务库**,不进配置中心。

### 4.2 与多租户隔离规则的契合(关键)

参考 `.claude/rules/rbac-multi-tenant.md`:
- 读**全局默认行**(`scope='global'`):属"跨租户查询",**不加** `TenantID` 条件。
- 读**租户覆盖行**(`scope='tenant'`):**必须**按 `tenant_id = xcontext.GetTenantID(ctx)` 过滤。
- **缓存键含 `tenant_id`**:不同租户的覆盖值绝不能共用缓存条目(复合键 `cacheKey{scope, tenantID, key}` 已保证)。
- 失效广播带 `tenant_id`:只失效对应租户的缓存条目,不影响其他租户。

> 注意:`sys_config` 不是 `rbac-multi-tenant.md` 列举的"全局表"(menus/permissions/tenants),也不是普通租户表——它是**用 `scope` 区分的混合表**。Repository 查询时**显式**按 `scope` + `tenant_id` 组合过滤,不套用"一律加 TenantID"或"一律不加"的简化规则。

### 4.3 读取流程(`GetForTenant`)

```
GetForTenant(ctx, key, out):
  1. tenantID = xcontext.GetTenantID(ctx)
  2. ck = cacheKey{scope:"tenant", tenantID, key}
  3. if v, ok := cache.get(ck); ok { return decode(v, out) }   // 命中租户缓存
  4. row = store.GetTenant(ctx, tenantID, key)                  // 查租户覆盖行
  5. if row != nil { cache.set(ck, row.Value); return decode(row.Value, out) }
  6. // 无租户覆盖 → 回退全局默认(走 L2 的 GetGlobal 逻辑)
  7. return GetGlobal(ctx, key, out)
```

> `GetGlobal` 自身也走缓存(`cacheKey{scope:"global", tenantID:"", key}`),全局默认只回源一次。

### 4.4 骨架(Provider 实现,接 §3.3 接口)

```go
// internal/sysconfig/provider.go(续)—— 租户感知读取,含回退
func (p *provider) GetForTenant(ctx context.Context, key string, out any) error {
    tenantID := xcontext.GetTenantID(ctx) // Step 05 起 xcontext 提供
    ck := cacheKey{"tenant", tenantID, key}
    if v, ok := p.cache.get(ck); ok {
        return decodeValue(v, out)
    }
    if row, err := p.store.GetTenant(ctx, tenantID, key); err == nil && row != nil {
        p.cache.set(ck, row.ConfigValue)
        return decodeValue(row.ConfigValue, out)
    }
    // 回退全局默认
    return p.GetGlobal(ctx, key, out)
}
```

> 写入租户覆盖:`Store.Upsert(scope="tenant", tenantID, key)` 成功后 `publishInvalidation({Scope:"tenant", TenantID, Key})`,只让相关租户缓存失效。

## 五、演进路径:何时引入配置中心(Apollo/Nacos)

**不要现在引入**。触发条件(满足任意即应考虑):

- 服务实例数增长到**数十个**,本地缓存 + Pub/Sub 的失效延迟/一致性不够用。
- 团队需要**批量调整运行时参数**(一次改几十个租户/Feature Flag)、**审计 + 审批流程**、**灰度发布按机房/集群分发**。
- 出现跨服务共享的动态配置(多个服务读同一份 Feature Flag),DB 表 + 各自缓存不再合适。

**平滑迁移的关键**:L2 的 `Provider` 接口是抽象边界。

- 迁移时**只换 Provider 实现**:从 `DBStore + 本地缓存 + Pub/Sub` 换成 `ApolloProvider`(内部用 Apollo 客户端订阅)。
- **业务代码零改动**:它们只依赖 `Provider.GetGlobal/GetForTenant` 接口。
- **L1 静态层不动**:文件 + env 加载机制保持不变,配置中心只接管 L2。
- **L3 多租户覆盖仍留业务库**:即使引入配置中心承载 L2 全局动态配置,租户级覆盖仍按结论 3 留在 `sys_config`(配置中心的租户隔离/审批通常不如业务库贴合 SaaS 的租户模型)。

> 这条演进路径正是外部调研结论的核心:"静态文件加载机制保持不变,配置中心只接管动态配置部分"。

## 六、实现阶段建议(决策:现在做什么)

| 阶段 | 做什么 | 时机 |
|---|---|---|
| **现在** | 只做 L1(已完成)。L2/L3 **不写代码**,本蓝图存档备查。 | 项目当前(Step 02,基础设施期) |
| **第一个动态配置需求出现时** | 落地 L2:`sys_config` 表迁移 + `Store` + `Provider`(缓存+广播)+ 接线到该需求。按 YAGNI 只做用到的那几个 key。 | 例如第一次要做 Feature Flag 灰度 |
| **第一个租户定制需求出现时** | 在 L2 基础上**开 L3**:给 `Provider` 加 `GetForTenant` + 回退逻辑(其实 L2 实现时若预留了 `scope` 字段,L3 几乎是免费的)。 | 例如租户要自定义配额/品牌 |
| **规模到门槛时** | 换 `Provider` 实现为 Apollo/Nacos,L1 不动。 | 满足第五节触发条件 |

**第一个 L2 需求出现时的接入清单**:
1. 加 `sys_config` 表 SQL(§3.2)到 `migrations/`(Step 04 的 migrations 目录)。
2. 实现 `internal/sysconfig/store.go`(GORM Gen,遵循 `.claude/rules/service-patterns.md` 规则 9)。
3. 实现 `internal/sysconfig/provider.go` + `cache.go` + `broadcast.go`(§3.3~3.4)。
4. `cmd/server/main.go`:db/rdb 就绪后 `NewProvider` + `go provider.SubscribeLoop(ctx)`,注入目标 service。
5. 单测:Store 用可注入的 `*gorm.DB`(测试库或 mock);Provider 测缓存命中/回源/失效广播(`miniredis` 或 mock `redis.Cmdable`)。
6. 验收:`go test ./internal/sysconfig/ -v` 全绿;手动写一行配置 → 请求命中 → 改库 → 观察缓存失效。

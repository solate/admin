# 现状与问题总结

> 对照 `admin/backend`(当前)与 `backend-rbac`(参考的 Viper 封装),梳理配置层现状与必须修掉的问题。

## 一、admin/backend 当前实现(纯 yaml.v3)

`internal/config/load.go`:

```go
func Load(path string) (*Config, error) {
	data, err := os.ReadFile(path)
	if err != nil {
		return nil, fmt.Errorf("read config: %w", err)
	}
	cfg := &Config{}
	if err := yaml.Unmarshal(data, cfg); err != nil {
		return nil, fmt.Errorf("parse config: %w", err)
	}
	if cfg.Server.Port == 0 {
		cfg.Server.Port = 8080
	}
	// 环境变量覆盖敏感字段(4 个硬编码)
	if v := os.Getenv("DB_PASSWORD"); v != "" { cfg.Database.Password = v }
	if v := os.Getenv("REDIS_PASSWORD"); v != "" { cfg.Redis.Password = v }
	if v := os.Getenv("JWT_ACCESS_SECRET"); v != "" { cfg.JWT.AccessSecret = v }
	if v := os.Getenv("JWT_REFRESH_SECRET"); v != "" { cfg.JWT.RefreshSecret = v }
	return cfg, nil
}
```

特征:
- 单文件、YAML-only,`-config` flag 指定路径
- 结构体用 `yaml:` tag
- 仅 1 个硬编码默认值(`port=8080`)
- 4 个硬编码 `os.Getenv` 覆盖敏感字段(用 `!= ""` 判空,无法区分"未设置"与"设为空")
- 无分层、无热重载、无校验、无全局单例

**优点**:零魔法、依赖最小、DI 友好(`Load` 返回 `*Config`,无全局)。
**缺点**:加载机制不可复用(只活在本项目);环境变量覆盖写死字段名。

## 二、backend-rbac 的 Viper 封装(`pkg/config/viper.go`)

封装的"加载核"(`viper.SetConfigType` → `AddConfigPath` → `ReadInConfig` → `MergeInConfig` 叠加 env 文件 → `Unmarshal` → `validateConfig`)本身是对的、可复用的。但它有 **5 个硬伤**:

### 坑 1:`AutomaticEnv` 静默失效(最严重)

```go
// viper.SetEnvPrefix("AB")                               // 被注释
// viper.SetEnvKeyReplacer(strings.NewReplacer(".", "_")) // 被注释
viper.AutomaticEnv() // 自动加载环境变量,优先级高
```

代码注释说"自动加载环境变量,优先级高",但**实际不生效**。根因见第三节。

### 坑 2:硬编码生产路径

```go
viper.AddConfigPath("/root/admin/admin-backend/") // 系统配置目录
```

换项目/换部署路径就失效,应参数化。

### 坑 3:死全局 `Get()`

```go
var globalConfig *Config
...
globalConfig = &cfg
...
func Get() *Config { return globalConfig }
```

真实代码全是依赖注入(`initLogger(cfg)`、`auth.NewService(..., cfg)` 等),`Get()` 实际无人调用 —— 死代码,且全局状态与 DI 风格冲突。

### 坑 4:`fmt.Printf` 打日志 + 失败不返错

```go
fmt.Printf("Loaded base config: %s\n", viper.ConfigFileUsed())
...
if err := viper.MergeInConfig(); err != nil {
	fmt.Printf("No environment-specific config file found for %s (this is OK)\n", env)
}
```

满屏 `fmt.Printf`,且 overlay 合并失败时只打印不区分"文件不存在(正常)"与"解析错误(异常)",一律吞掉。

### 坑 5:无默认值机制、无热重载

无 `viper.SetDefault(...)`;无 `viper.WatchConfig()`(fsnotify 作为间接依赖被拉进来却没用上)。校验 `validateConfig` 把 rbac 自己的字段名(`app.name`、`app.port`)写死,不可复用。

## 三、关键技术发现:`AutomaticEnv` + `Unmarshal` 不兼容

这是坑 1 的根因,也是本次封装设计最重要的约束。

**原理**:
- `viper.AutomaticEnv()` 的工作方式是拦截 `Get(key)` / `find(key)` —— 只有当某个 key 被**显式访问**时,viper 才去查对应环境变量。
- `viper.Unmarshal(target)` 内部走 `AllSettings()`,而 **`AllSettings()` 不查 `AutomaticEnv`**(它只读已绑定的 config map:文件 + flags 等,不触发环境变量查找)。
- 因此:`Unmarshal` 出来的结构体**永远不会**包含 `AutomaticEnv` 本应注入的环境变量覆盖。嵌套 key(如 `database.password`)的环境变量覆盖**静默失效**。

**`SetEnvKeyReplacer` / `SetEnvPrefix` 救不了**:它们只影响"当 key 确实被查询时"如何映射环境变量名;问题是 `Unmarshal` 根本不去查。

**证据/共识**:这是 Viper 长期存在的已知行为(github.com/spf13/viper issue 与社区讨论反复提及:`AutomaticEnv` 与 `Unmarshal`/`AllSettings` 不协同;要环境变量进 `Unmarshal` 必须显式 `BindEnv` 每个 key)。

### 本方案的对策

不在 wrapper 里用 `AutomaticEnv`。Viper 只负责 **文件加载 / 合并 / 反序列化**(它真正擅长的);环境变量覆盖由**调用方显式 `os.LookupEnv`** 完成:

- 行为正确可见(不会静默失效)
- 零魔法(符合 Step 02 既定的"无隐藏魔法"原则)
- 哪些字段被环境变量覆盖由各项目自己决定(本就是项目相关的事)

详见 `03-封装设计.md`。

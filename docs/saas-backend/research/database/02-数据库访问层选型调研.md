# 数据库访问层选型调研

> 本轮（2026-07）为 Step 02 数据库层选型所做的调研。老项目 A（老项目）用 **GORM + gorm/gen**，新 `backend/` 当前只引了裸 GORM（`gorm.io/gorm` v1.31.1 + `gorm.io/driver/postgres` v1.6.0）。本轮回答：站在 2026、目标 PostgreSQL、要 AI 生成友好，数据库访问层该怎么选。

## 背景与约束

老项目 A 的 repository 层用 gorm/gen 生成的类型安全查询 API（`r.q.Role.WithContext(ctx).Where(r.q.Role.TenantID.Eq(tenantID)).First()`），跑通了多租户 + RBAC 全套。新项目想借选型窗口重新评估。

硬约束（用户明确提出，逐条对齐）：

1. **比 ent 轻** —— ent 的 schema-as-code + 生成的代码量与概念负担被否掉。
2. **不写裸 SQL** —— sqlc 那种「手写 SQL 文件」的心智负担太高，尤其多条件 WHERE。
3. **动态多条件 WHERE 要好写** —— 列表查询的可选过滤（name/status/时间范围）是高频场景，这是选型的核心痛点。
4. **AI 生成友好** —— 类型可发现、API 规律性强，AI 补全/生成不易错。
5. **PostgreSQL 优先** —— 不需要跨库抽象，要能用 PG 原生特性（jsonb / array / upsert / RETURNING / CTE）。

本轮追加两条约束（决定性）：

6. **迁移自动化** —— 不想手写手维护 migration SQL，改 schema 后迁移应能自动 diff 生成。
7. **生成的 model 是确定类型** —— model 结构体字段类型确定、编译期可查，不接受 `map[string]interface{}` 或运行时反射拼装。

## 2026 Go 数据库访问层全景

| 方案 | 范式 | 真相源方向 | 自带迁移 | 确定类型 model | 一句话 |
|---|---|---|---|---|---|
| **GORM + gorm/gen** | 反射 ORM + 代码生成查询 API | 代码 → DB | AutoMigrate（弱）/ 配 Atlas | ✅ gen 生成 | 老项目在用；成熟、AI 熟、生态最大 |
| **Bob** (`stephenafamo/bob`) | DB-first 代码生成 + 运行时 builder | DB → 代码 | ❌ 需配 Atlas / sql-migrate | ✅ 从 DB 生成 | 2024+ 新星；按 PG spec 定制、动态查询一等公民 |
| **ent** (`ent/ent`) | schema-as-code | 代码 → DB | ✅ 内建 versioned | ✅ 从 schema 生成 | 一站式最全，但重、概念多（已被否） |
| **sqlc** | 静态 SQL 生成 | DB → 代码 | ❌ 需配 Atlas | ✅ 从查询生成 | 类型安全极佳，但动态查询硬伤 |
| **jet** (`go-jet/jet`) | schema 生成 SQL builder | DB → 代码 | ❌ | ✅ 从 DB 生成 | 类型安全 SQL 表达式，纯 builder |
| **Bun** (`uptrace/bun`) | 轻量 ORM/builder | 代码 → DB | 迁移器（手写） | ✅ struct tag | 轻、快，但迁移与类型生成偏手工 |
| **sqlboiler** | DB-first 生成 | DB → 代码 | ❌ | ✅ 从 DB 生成 | Bob 的前身，作者已把 Bob 定位为继任 |

> **真相源方向**是理解这张表的关键轴：**代码优先**（改 Go → 同步 DB，如 gorm/ent）vs **数据库优先**（改 schema → 生成 Go，如 bob/sqlc/jet）。这条轴决定了迁移与 model 生成的工作流走向。

## 痛点核心：动态多条件 WHERE（约束 3）

这是把 sqlc 直接淘汰的地方，不是错觉、是设计硬伤。sqlc 从**静态** SQL 生成代码，**天生不支持运行时拼条件**。官方 [Discussion #364](https://github.com/sqlc-dev/sqlc/discussions/364) 讨论多年，社区共识仍是「动态查询请另配 squirrel」——即 **sqlc + squirrel 两套并存**，复杂度反而上升，且 AI 要在两种范式间跳。

同样一个「可选 name / status / 时间范围过滤 + 分页」的列表查询，各方案写法：

**Bob** —— `Apply()` + 条件 mods，动态查询是一等公民：

```go
q := psql.Select(
    sm.From("users"),
    sm.Columns("id", "name", "status"),
)
if name != "" {
    q.Apply(sm.Where(psql.Quote("name").EQ(psql.Arg(name))))
}
if status != "" {
    q.Apply(sm.Where(psql.Quote("status").EQ(psql.Arg(status))))
}
if !start.IsZero() {
    q.Apply(sm.Where(psql.Quote("created_at").GTE(psql.Arg(start))))
}
q.Apply(sm.Limit(limit), sm.Offset(offset))
```

**GORM + gen**（老项目写法）—— 链式 + 条件判断：

```go
query := r.q.User.WithContext(ctx).Where(r.q.User.TenantID.Eq(tenantID))
if name != "" {
    query = query.Where(r.q.User.Name.Eq(name))
}
if status != "" {
    query = query.Where(r.q.User.Status.Eq(status))
}
if !start.IsZero() {
    query = query.Where(r.q.User.CreatedAt.Gte(start))
}
users, count, err := query.FindByPage(offset, limit)
```

**sqlc** —— 做不到上面任何一种；要么给每种过滤组合写一条静态查询（组合爆炸），要么 `COALESCE(sqlc.narg('name'), name)` 这类丑陋 hack，要么外挂 squirrel。**这就是它写着难受的根因。**

> Bob 的 `Apply()` 与 gorm/gen 的链式条件在动态 WHERE 上都很自然、AI 都好生成。差别在别处（见下）。

## 追加约束的影响：迁移自动化（约束 6）+ 确定类型 model（约束 7）

### 关键变量：Atlas 把「迁移自动化」这条约束抹平了

[Atlas](https://atlasgo.io)（`ariga/atlas`）是一个**独立的 schema-as-code 迁移引擎**，类似数据库界的 Terraform：声明期望的 schema 状态，Atlas 对比当前 DB、**自动 diff 生成迁移**。它支持两种工作流（[declarative vs versioned](https://atlasgo.io/concepts/declarative-vs-versioned)），且真相源可以是 **HCL / SQL schema 文件，也可以是 ORM provider（GORM / Drizzle / Django / SQLAlchemy）**。

这意味着：**「迁移自动化」不再是选 ORM 的约束**——无论选 Bob 还是 GORM，都能接 Atlas 做到「改 schema → 自动生成版本化迁移」，无需手写 migration SQL。

- **GORM + Atlas**：Atlas 的 [GORM provider](https://atlasgo.io/guides/orms/gorm/getting-started) 直接读你的 Go struct 作为期望状态，自动 diff 出迁移。真相源 = Go 代码。（比 GORM 自带的 `AutoMigrate` 强得多——`AutoMigrate` 只增不删、生产不安全，Atlas 生成可审查的版本化迁移。）
- **Bob / sqlc + Atlas**：Atlas 官方有 [sqlc versioned](https://atlasgo.io/guides/frameworks/sqlc-versioned) / [sqlc declarative](https://atlasgo.io/guides/frameworks/sqlc-declarative) 集成指南。Bob 本身是 database-first（[官方文档](https://bob.stephenafamo.com/docs/code-generation/intro/)明确「先建 schema、用 sql-migrate 之类管理迁移」），Atlas 正好补上自动迁移这一环：Atlas 管 schema/迁移 → Bob 从 DB 生成 model 与查询。真相源 = SQL/HCL schema。

> 结论：约束 6 由 Atlas 统一满足，不再是区分 Bob 与 GORM 的因素。真正的区分回到**查询体验**和**真相源方向偏好**。

### 确定类型 model（约束 7）：全部候选都满足

Bob / gorm-gen / ent / sqlc / jet / sqlboiler **都生成确定类型的 model 结构体**（字段类型编译期可查）。唯一要避开的是「裸 GORM 手写 struct + `map[string]interface{}` 更新」这种弱类型写法——而这正是老项目用 **gorm/gen** 而非裸 GORM 的原因：gen 生成 `r.q.User.Name` 这类类型安全字段引用。所以约束 7 也不构成区分，只是**否定了「新 backend 停留在裸 GORM」**这个选项。

## 加上两条约束后的选型矩阵

candidates 收敛到两个（sqlc 因约束 3 出局、ent 因约束 1 出局、jet/Bun/sqlboiler 相对小众或定位重叠）：

| 维度 | **GORM + gen + Atlas** | **Bob + Atlas** |
|---|---|---|
| 真相源方向 | 代码优先（Go struct） | 数据库优先（SQL schema） |
| 动态 WHERE | ✅ 链式条件（约束 3） | ✅ `Apply()` mods（约束 3） |
| 迁移自动化 | ✅ Atlas GORM provider 读 struct | ✅ Atlas 管 SQL schema |
| 确定类型 model | ✅ gen 生成 | ✅ 从 DB 生成 |
| PG 原生特性 | ✅ 支持，但经 ORM 抽象层 | ✅✅ 按 PG spec 定制，jsonb/array/upsert/RETURNING/CTE 贴原生 |
| AI 生成友好 | ✅ 语料最多、老项目已验证 | ✅ 类型可发现，但语料较新较少 |
| 轻量度 | 中（GORM 反射运行时） | 中（生成代码 + 轻运行时，比 ent 轻） |
| 团队/仓库一致性 | ✅ 与 老项目 A 完全一致 | ❌ 引入第二种范式 |
| 迁移成本（新 backend） | 低：补 gen + Atlas 配置即复刻老项目 | 中：新范式 + 新工具链学习 |
| 生态成熟度 | ✅ 最成熟稳定 | 活跃但年轻（2024+ 崛起，sqlboiler 继任者） |
| 学习/教学成本 | 低（已掌握） | 中（database-first 心智 + Bob API） |

## 结论（驱动决策）

加上「迁移自动化 + 确定类型 model」两条约束后，**Atlas 成为共同的迁移底座**，选型焦点回到「查询体验 + 真相源方向 + 一致性」。给出两条明确路线：

1. **求稳、快速拉齐、团队一致 → GORM + gorm/gen + Atlas（推荐默认）。**
   - 老项目 A 已用 gorm/gen 跑通全套多租户 RBAC，AI 与团队都熟，语料最多、生成最不易错。
   - 新 backend 现在只有裸 GORM，补上 **gorm/gen**（生成类型安全查询 + 确定类型 model，满足约束 7）+ **Atlas GORM provider**（读 struct 自动 diff 迁移，满足约束 6），即以近零成本复刻老项目体验并补齐两条新约束。
   - 动态 WHERE 用链式条件（约束 3 已满足）。承认 tradeoff：GORM 运行时反射比生成方案略重、PG 原生特性经抽象层——但对本项目非瓶颈。

2. **愿为更好的 PG 契合与更干净的动态查询付学习成本 → Bob + Atlas。**
   - Bob 是 2026 最贴合前 5 条约束的新方案：database-first、生成确定类型 model、`Apply()` 让动态条件成为一等公民、每个方言按 PG spec 定制（jsonb/array/upsert/RETURNING 贴原生）、同时能像 sqlc 那样从 `.sql` 生成静态查询——一套工具覆盖静态+动态两种模式，不用像 sqlc 外挂 squirrel。
   - 配 Atlas 管 SQL/HCL schema 与自动迁移，闭环成立。
   - 承认 tradeoff：引入与 老项目 A 不同的第二种范式（仓库风格分裂）、Bob 生态年轻语料少、database-first 心智与工具链有学习成本。

**推荐**：作为教学/演进项目，**默认走路线 1（GORM+gen+Atlas）**——最小成本补齐全部 7 条约束、与老项目一致、AI 最友好。若本 step 想借机做一次面向 PG 的技术升级、且接受仓库两种范式，则路线 2（Bob+Atlas）是 2026 最「新」的正解。**无论哪条，Atlas 都应作为迁移引擎引入**（替代 GORM AutoMigrate 手工/不安全的迁移）。

## 承认的 tradeoff（写进决策记录，不回避）

- 裸 GORM（现状）不满足约束 7 的「确定类型查询」精神（`map[string]interface{}` 更新是弱类型）→ 必须补 gorm/gen 或换 Bob。
- GORM `AutoMigrate` 只增不删、生产不安全 → 迁移交给 Atlas，`AutoMigrate` 仅限本地开发便利。
- 路线 2 引入第二种范式，与 老项目 A 风格不一致（类比日志层 slog vs zerolog 的取舍：新项目可用现代方案，老项目不迁）。
- Atlas 是额外的二进制工具与 CI 环节（`atlas migrate diff` / `apply`），团队需学最小工作流——但换来的是可审查、可回滚的版本化迁移，远优于手写 SQL。

## 若采纳的落地要点（下一步参考）

### 路线 1（GORM + gen + Atlas）
- **gorm/gen 配置**：仿照 老项目 A 的 `cmd/gen` / gen 配置，从 DB 或 model 生成 `internal/dal/query` + `internal/dal/model`，repository 层用 `r.q.XXX.WithContext(ctx)`。
- **Atlas 接入**：`atlas.hcl` 配 GORM provider（`data "external_schema" "gorm"` 跑 loader 输出 struct schema）→ `atlas migrate diff` 生成版本化迁移到 `migrations/` → `atlas migrate apply` 执行。开发期可留 `AutoMigrate` 便利，CI/生产走 Atlas。
- **多租户/排序规则**：延续既有 `.claude/rules`（TenantID 过滤、双排序字段兜底、Gen Where 等）。

### 路线 2（Bob + Atlas）
- **schema 真相源**：SQL schema 文件或 HCL，Atlas 管迁移。
- **Bob 代码生成**：psql driver 指向 DB/schema，生成 model + 类型安全 builder；静态查询写 `.sql` 让 Bob 生成，动态查询用 `psql.Select + Apply()`。
- **封装**：`pkg/database` 保持 `New(cfg) (*bob.DB, error)` 或 `(*sql.DB → bob.NewDB)`，repository 用 Bob query mods。

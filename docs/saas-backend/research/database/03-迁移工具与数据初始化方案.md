# 迁移工具与数据初始化方案调研

> 本轮（2026-07）承接 [02-数据库访问层选型调研.md](./02-数据库访问层选型调研.md) 的结论——数据库访问层方向已定为 **GORM + gorm/gen + Atlas（Go struct 优先）**。本轮回答两个更具体的问题：① 现用的 **golang-migrate** 与 **Atlas** 到底差在哪、该选哪个；② `api_resource` / 权限这类**初始化数据**，有没有比老项目更好的管理方式（老项目这套「不好用」）。

## 一、背景与本轮问题

02 文档已确定：schema 真相源用 **Go struct**，配 gorm/gen 生成确定类型 model/query，配 Atlas 做迁移自动化。方向不再动摇。本轮聚焦落地前的两个悬而未决点。

**用户现状（老项目 A）**：

- 迁移：**golang-migrate** + 手写 `.up.sql` / `.down.sql`
- 代码生成：`gen-db`（gorm/gen）从**实际数据库反射**生成 model（database-first）
- 初始化数据：一部分内联在 migration 的 `INSERT`，一部分靠独立 Go seeder（`scripts/init_data/`）

**老项目「问题太多」的病根（本轮探索实证，作为反面证据）**：

1. **schema 三源 drift**：同一套表结构在仓库里有三个互不同步的来源——
   - `migrations/`（golang-migrate）：只建了 **3 张表**（users / user_roles / role_permissions）
   - `scripts/dev_schema.sql`：另建了 **12 张表**（且 users 定义与 migration 里的互相矛盾）
   - `internal/dal/model/*.gen.go`：**57 个生成的 model**（人脸/视频/设备等几十张表，在任何迁移里都没有建表语句）

   **3 vs 12 vs 57 对不上**，就是 drift 的铁证。新人 `make init`（走 migration）只得到 3 张表，应用根本跑不起来。根因：golang-migrate 只是「SQL 执行器」，不理解 schema 的**状态**；`gen-db` 又是纯 database-first（读活库反射）。两者之间**没有任何一致性校验**，drift 是这套组合的必然结果，不是用错了。

2. **seed 数据散落进 migration**：对照同层级 老项目 B——**62 个 migration 里 25 个是数据类**，`api_resource` 权限数据散在 `000056`、`000062`… 被反复「补全」。根本矛盾是：`api_resource` 是**随代码演进、应覆盖式声明**的数据，却被塞进**只能追加、不能改**的 migration 序列，越滚越乱。

3. **正面对照**：
   - `go-wind-admin`（用 ent）把 **schema（struct）** 与 **seed（独立 `sql/postgresql-default-data.sql`，`TRUNCATE ... RESTART IDENTITY CASCADE` 覆盖式重建）** 彻底分离。
   - 老项目 A 的基础数据（菜单/部门/字典）其实用了**独立 Go seeder** 带幂等逻辑——**这部分做对了**，问题只在 schema 源头和部分 seed 塞进了 migration。

## 二、golang-migrate vs Atlas 深度对比

### 定位差异（一句话）

**golang-migrate 是「迁移执行器」**——它只负责「按版本号顺序跑你手写的 SQL 文件、记录跑到哪一版」。迁移 SQL 的内容全靠你手写。

**Atlas 是「schema 引擎」**——它理解 schema 的**状态**。你声明期望的 schema（或直接读 GORM struct），Atlas 对比当前 DB，**自动 diff 生成迁移 SQL**。

一句话：**golang-migrate 帮你「跑」迁移，Atlas 帮你「写」迁移。** 两者不在同一层——严格说 Atlas 是 golang-migrate 的超集（Atlas 也能只当执行器用，还能生成 golang-migrate 格式的迁移文件）。

### 逐维度对比

| 维度 | **golang-migrate**（现状） | **Atlas** |
|---|---|---|
| 定位 | 迁移执行器（runner） | schema-as-code 引擎 |
| 迁移 SQL 谁写 | ❌ 全手写 up + down | ✅ 自动 diff 生成（可再人工审查） |
| 真相源 | SQL 文件本身 | 期望 schema（**GORM struct** / HCL / SQL） |
| 改表流程 | 手写 `ALTER` 的 up + 反向 down | 改 struct → `atlas migrate diff` 自动生成 |
| drift 防护 | ❌ 无——与 model/实际库无校验 | ✅ `migrate lint` + schema diff 检测漂移 |
| 破坏性变更检测 | ❌ 无 | ✅ lint 规则（删列/改类型告警） |
| 失败后状态 | ⚠️ 留 **dirty version**，需手工 `force` 修 | ✅ 有 pre-migration 校验，失败处理更稳 |
| down 回滚 | 手写 down 文件（易与 up 不对称） | 自动生成 / declarative 无需 down |
| 与 GORM struct 集成 | ❌ 无关 | ✅ GORM provider 直接读 struct 当真相源 |
| 依赖/体积 | 单二进制，极简 | 单二进制，功能多、概念多 |
| 学习成本 | 极低（已会） | 中（HCL/diff/两种工作流） |
| 与本项目约束 6（迁移自动化） | ❌ 天生不满足（只跑手写 SQL） | ✅ 正是「迁移自动化」本身 |

### golang-migrate 的 dirty state 问题（官方公认）

Atlas 官方博客《The "dirty secret" of golang-migrate》直指其痛点：**迁移执行失败后，golang-migrate 会把 `schema_migrations` 表标记为 dirty，且不会自动回滚**——因为 golang-migrate 不在事务里做预校验，一条 SQL 中途失败，库处于半迁移状态，version 被标 dirty，此后所有迁移都被拒绝，必须人工 `migrate force <version>` 手动修正再继续。这在生产/CI 里是个常见的「深夜惊魂」。Atlas 对迁移有 lint 预检与更完善的失败处理。

### 用老项目 drift 作为实证

第一部分的 **3 vs 12 vs 57** 正是「golang-migrate 管不住一致性」的活样本：它只跑那 3 张表的 SQL，对 `dev_schema.sql` 的 12 张表、以及被手工建出来又被 `gen-db` 反射抓走的几十张表**一无所知**，也**无从校验**。换成 Atlas：GORM struct 是唯一真相源，`atlas migrate diff` 自动产出与 struct 一致的迁移，`migrate lint` 在 CI 拦截漂移——drift 从「必然发生」变成「被机制挡住」。

### 结论

- **结构变更为主（建表/加字段/改索引）→ 上 Atlas**：GORM provider 读 struct 自动 diff，补齐约束 6，并从机制上根治老项目的三源 drift。这是本项目的推荐路线。
- **纯 SQL 完全掌控 / 迁移常夹复杂数据搬迁 → 可保留 golang-migrate**：牺牲约束 6 换简单可控。但本项目 schema 变更为主，不满足这个「例外条件」。
- **折中（不少团队采用）**：Atlas 自动生成迁移 SQL，生成后**人工审查/微调**再落库——既自动化又保留控制权。Atlas 还能生成 golang-migrate 兼容格式，迁移平滑。

### 关键澄清：ent 与 Atlas 同源，ent 内建 Atlas 迁移引擎

选型时容易被忽略的一个事实——**ent 和 Atlas 出自同一批人（Ariga / Ariel Mashraki）**。ent 官方文档原话：*"Ent uses Atlas, an open-source tool for managing database schemas, created by the same people behind Ent."* 时间线上，**ent 从 v0.10.0（2022 年初）起把迁移引擎换成了 Atlas**——所以今天你用 ent 的迁移，底层跑的就是 Atlas。

这带来一个对本项目选型至关重要的推论：**本项目的两条候选路线，迁移引擎其实是同一个（Atlas），区别只在「谁来焊接」**：

| 路线 | ORM / model + query | 迁移引擎 | 集成方式 |
|---|---|---|---|
| **ent** | ent 自带（schema → typed model + query） | **内建 Atlas**（同源团队，无需单独装/配） | ✅ 一个工具链、一套心智，官方原生一体化 |
| **GORM + gen + Atlas** | GORM + gorm/gen（2 个工具） | **Atlas**（独立安装、自己配 GORM provider） | ⚠️ 三件套，用同一个 Atlas 引擎，但要自己拼装 |

换句话说：**ent 帮你把 Atlas 焊死在框架里，GORM 方案要你自己焊**。这把「ent vs GORM+Atlas」的取舍简化成一个纯粹的问题——

- 想要**开箱即用的一体化**（框架与迁移天然配合、像用户诉求的那样）→ 代价是接受 ent 的 schema-as-code 概念负担与代码生成量（也就是最初嫌它「重」的地方）。
- 想要**更轻、更贴近老项目 gorm/gen 经验**、自己拼装但可控 → 代价是三件套要自己配置、自己保证配合。

> 注：Atlas 也能独立于 ent 使用（配 GORM struct 就是本文档的推荐路线）。所以「Atlas」在本文档里指的是**独立使用的 Atlas**；ent 用户则通过 ent 的命令间接使用同一个引擎。**02 文档当初以「比 ent 轻」否掉 ent，本质上否的是「一体化的概念负担」，而非否掉 Atlas 引擎本身**——两条路线共用它。

## 三、数据初始化（seed）——三层数据分类法（核心）

老项目 seed 的乱，根子在**没有按「数据的变化节奏」分类**，而是一股脑要么塞 migration、要么临时写脚本。正确的做法是先分层，再对每层选匹配的机制。

按变化节奏，初始化数据分三层：

| 层 | 典型数据 | 变化节奏 | 谁是真相源 | 推荐机制 |
|---|---|---|---|---|
| ① **schema** | 表结构、索引、约束 | 随开发迭代 | GORM struct | Atlas versioned migration（从 struct diff） |
| ② **框架种子** | `api_resource`、菜单、权限点、字典 | **跟着代码走**（加接口/加菜单就变） | 代码 | **幂等 seeder（upsert / 覆盖式声明）**，与 schema 分离 |
| ③ **运行时数据** | `role_permissions` 绑定、租户业务数据 | 运行时由人操作 | 数据库 | 管理界面配置，**不 seed** |

**关键洞察**：老项目的错，是把第 ② 层当成第 ① 层管——`api_resource` 明明「跟着代码走、该覆盖式声明」，却被塞进「只能追加、不能改」的 migration 序列，于是每加几个接口就新建一个 migration 去补，越滚越乱（老项目 B 的 25 个数据类 migration 就是这么来的）。

分层之后：第 ① 层归 Atlas，第 ③ 层归业务运行时，**真正需要设计的是第 ② 层**——尤其是 `api_resource`，见下一节。

> 业界共识（entgo / Atlas 官方 data-migration 文档）：即便用版本化迁移承载数据，也应把 **data migration 与 schema migration 分文件存放**，便于独立测试与审查。本方案更进一步——第 ② 层的框架种子根本不该进版本化序列，而用幂等 seeder 覆盖式声明。

## 四、`api_resource` 的最优模式（用户痛点正解）

老项目痛点复述：**手写 SQL `INSERT` 散落多个 migration，每加一个接口就要新建 migration 补权限记录，越滚越乱**（且容易漏、容易和实际路由不一致）。

三个候选方案：

### 方案 A（推荐，针对 `api_resource`）：从 Gin 路由自动同步

**路由注册表即真相源**。程序里所有 API 本就要注册进 Gin 路由，那份注册信息（path / method / 分组）已经是最权威、最不会漏的 API 清单。做法：

- 启动时（或一条 `sync-api` 命令）遍历 `router.Routes()`，把每条路由 **upsert** 进 `api_resource` 表。
- 新增接口 → 自动登记；删除接口 → 标记失效（软失效，保留历史绑定）。
- 路由注册时带上元数据（`name` / `module` / `description`），一并写入，供前端权限管理界面展示。

**收益**：彻底消灭「手写权限列表」和「加接口忘补权限」。`api_resource` 永远和真实路由一致——drift 在这一层也被根除。参考 `gin-admin` 等成熟脚手架的思路。

```go
// 示意：启动时同步（真实实现放 Step 07/08 权限模块）
for _, r := range engine.Routes() {
    meta := routeMeta[r.Handler] // 路由注册时登记的 name/module
    repo.UpsertAPIResource(ctx, &model.ApiResource{
        Path: r.Path, Method: r.Method,
        Name: meta.Name, Module: meta.Module,
    })
}
```

### 方案 B（针对菜单/字典等相对稳定的初始数据）：独立 Go seeder + upsert 幂等

菜单、字典类型/字典项、初始角色这类数据不像 `api_resource` 能从代码结构自动推导，但变化慢、数量可控。沿用 `老项目 A/scripts/init_data/` 已验证的**独立 Go seeder** 模式，但统一改为 **upsert 语义**（老项目部分是 Count-then-insert，重跑不覆盖更新）：

- 用业务 model + `ON CONFLICT ... DO UPDATE`（或 GORM `clause.OnConflict`）保证幂等且可覆盖。
- 一条 `make seed` 命令随时重跑，结果收敛到「代码里声明的那份」。
- 与 schema migration 完全分离，不进版本化序列。

### 方案 C（否定用于 `api_resource`，仅限一次性数据订正）：Atlas data migration

Atlas 支持版本化的 data migration。它适合**一次性数据搬迁/订正**（如「把旧枚举值批量改名」），这类操作确实该版本化、只跑一次。但**不该**用于 `api_resource`——后者是「覆盖式声明」数据，塞进追加式序列就会重蹈 老项目 B 覆辙。**结论：方案 C 仅用于真正一次性的数据订正，不用于框架种子。**

### 关键补充：多环境一致性与版本可追溯问题（对方案 B 的重要修正）

前面方案 A/B/C 的对比有一个**隐藏的假设没讲清楚**：方案 B（纯 Go seeder）在「多环境一致性」和「版本可追溯性」上有致命缺陷，这是实战中的真实痛点。

**问题场景重现**：

```
v1.0 发布 → seeds/menus.go 声明 5 个菜单
v1.1 发布 → 加了 3 个菜单（现在 8 个）
v1.2 发布 → 又加 2 个、删 1 个（现在 9 个）

staging 环境出 bug，要回滚到 v1.1 调试。
```

**方案 B（纯 seeder）的行为**：
```bash
git checkout v1.1
make seed  # ❌ 跑的是 v1.1 代码里的 seeder（声明 8 个菜单）
# 但 seeder 不知道「当前库是什么状态」
# 它只会 upsert v1.1 声明的那 8 个菜单
# 如果库里已经有 v1.2 的 9 个菜单，第 9 个不会被删（seeder 没有「删除多余记录」逻辑）
# 结果：库里实际是 9 个菜单的混杂状态，不是纯净的 v1.1
```

**两个核心缺陷**：

1. **seeder 不记录「它跑过哪个版本」**——多次 `make seed` 它不知道库现在对应代码的哪个 commit，不像 migration 有明确的版本号记录在 `schema_migrations` 表。
2. **seeder 是全量覆盖的声明，但实际执行是 upsert（插入或更新）**——没有「删除不在声明里的记录」。除非你在 seeder 里写「先查已有记录、删除多余的、再 upsert」，但这让 seeder 变复杂，且仍然不版本化。

**对比：migration 的行为**：
```bash
git checkout v1.1
atlas migrate apply --version 20260615  # 停在 v1.1 对应的迁移版本
# DB 状态 = 精确的 v1.1（版本号在 schema_migrations 表有记录）
# 可审查、可回滚、多环境一致（同一版本号 = 同一状态）
```

**结论**：菜单/字典这类需要「跟着版本迭代、可追溯、多环境一致」的数据，**不能用纯 seeder**。必须版本化。但又不想退回「纯 SQL INSERT 散落多个 migration」的老路（无法看到完整状态、修改麻烦）。

### 方案 D（修正推荐）：版本化的声明式 seed 文件 + migration 触发

**核心思路**：seed 数据本身用**声明式文件**（YAML/JSON，好维护、可读），但它的**变更走 migration 序列**（版本化、可追溯）。

**目录结构**：
```
migrations/
  20260601_create_menus_table.sql        # schema migration
  20260601_seed_initial_menus.sql        # v1.0: 调用 seed（5 个菜单）
  20260615_seed_add_user_menus.sql       # v1.1: 追加 3 个（现在 8 个）
  20260707_seed_update_menus.sql         # v1.2: +2 -1（现在 9 个）
seeds/
  menus.yaml   # 当前版本的完整菜单列表（Git 版本化）
```

**seeds/menus.yaml**（声明当前完整状态，Git 管理）：
```yaml
# v1.2 时这个文件的内容
- menu_code: system
  name: 系统管理
  icon: settings
  sort: 1
- menu_code: user
  name: 用户管理
  icon: users
  sort: 2
# ... 共 9 个菜单的完整列表
```

**migrations/20260615_seed_add_user_menus.sql**（migration 触发统一的 seed 逻辑）：
```sql
-- 不是直接写 INSERT，而是调用统一的 seed 应用器
-- Atlas 支持在 migration 里执行外部命令
\! go run scripts/apply_seed.go menus
```

**scripts/apply_seed.go**（统一的 seed 应用器，幂等 + 全量同步）：
```go
func main() {
    seedType := os.Args[1]  // "menus"
    data := loadYAML(fmt.Sprintf("seeds/%s.yaml", seedType))
    
    // 策略 1：全量替换（简单粗暴，适合无外键依赖的表）
    db.Exec("DELETE FROM menus WHERE menu_code NOT IN (?)", extractCodes(data))
    for _, item := range data {
        db.Clauses(clause.OnConflict{
            Columns: []clause.Column{{Name: "menu_code"}},
            DoUpdates: clause.AssignmentColumns([]string{"name", "icon", "sort"}),
        }).Create(&item)
    }
    
    // 策略 2：增量 diff（复杂但安全，适合有外键的表）
    // ... 对比 YAML 与库里现有记录，增删改
}
```

**收益（结合两者优点）**：

1. ✅ **版本可追溯**：
   ```bash
   git checkout v1.1
   atlas migrate apply --version 20260615
   # seeds/menus.yaml 是 v1.1 的版本（Git 历史）
   # migration 20260615 跑的就是那个版本的 seed
   # DB 状态 = 精确的 v1.1（8 个菜单）
   ```

2. ✅ **声明式 + 可读**：`seeds/menus.yaml` 一个文件看到完整的 9 个菜单（当前版本），不像散落的 SQL INSERT 要心算拼接。

3. ✅ **修改方便**：改菜单直接编辑 YAML、提交新 migration 调用 `apply_seed`，不用每次小改都手写 `UPDATE` SQL。

4. ✅ **多环境一致**：同一个 migration 版本号 → 同一个 seed 状态，CI/CD 跑 `atlas migrate apply` 自动同步。

**Git 工作流示例**：
```bash
# v1.1 开发：加 3 个菜单
vim seeds/menus.yaml  # 在数组里追加 3 项（现在 8 个）
atlas migrate diff --name seed_add_user_menus  # 生成 migration（调 apply_seed.go）
git add seeds/menus.yaml migrations/20260615*
git commit -m "feat: add user management menus (v1.1)"

# v1.2 开发：改 1 个、删 1 个、加 2 个
vim seeds/menus.yaml  # 改数组（现在 9 项）
atlas migrate diff --name seed_update_menus
git add seeds/menus.yaml migrations/20260707*
git commit -m "feat: update menus (v1.2)"

# staging 回滚到 v1.1
git checkout v1.1
atlas migrate apply  # 自动跑到 v1.1 对应的 migration 版本
# 此时 seeds/menus.yaml 是 v1.1 的 8 个菜单（Git 历史版本）
# DB 里也精确是 8 个
```

**api_resource 仍然例外**：它的真相源是**路由注册代码本身**，不是配置数据。方案 A（启动时从路由自动同步）仍是最优解——同一 Git commit → 路由代码相同 → 生成的 api_resource 相同，版本一致性由代码保证，不需要 migration。

### 四种方案最终对比

| 方案 | 版本可追溯 | 多环境一致 | 声明式/可读 | 修改方便 | 适用数据 |
|---|---|---|---|---|---|
| **纯 SQL INSERT 塞 migration** | ✅ | ✅ | ❌（散落多文件） | ❌（每次小改新建 migration） | 一次性数据订正 |
| **纯 Go seeder**（方案 B 初版） | ❌ **致命** | ❌ **致命** | ✅ | ✅ | ❌ 不推荐 |
| **YAML seed + migration 触发**（方案 D，修正推荐） | ✅ | ✅ | ✅ | ✅ | **菜单/字典/初始角色** |
| **路由自动同步**（方案 A） | ✅（代码即版本） | ✅ | ✅（代码） | ✅ | **api_resource** |

**最终推荐（修正后）**：

- **菜单 / 字典 / 初始角色**：方案 D（YAML seed + migration 触发），兼顾版本化与声明式
- **api_resource**：方案 A（路由自动同步），真相源是代码
- **role_permissions 绑定**：运行时管理界面，不 seed
- **一次性数据订正**：Atlas data migration（纯 SQL）

## 五、推荐组合（承接「Go struct 优先」，已修正）

把前面各层的结论串成一套完整工作流：

| 关注点 | 机制 | 真相源 |
|---|---|---|
| schema 迁移 | GORM struct → `atlas migrate diff` → versioned migration → `apply` | Go struct |
| `api_resource` | 路由自动同步（方案 A），启动/命令 upsert | Gin 路由注册表 |
| 菜单 / 字典 / 初始角色 | Go seeder + upsert 幂等（方案 B），`make seed` | 代码声明 |
| `role_permissions` 绑定 | 运行时管理界面配置（不 seed） | 数据库 |
| model / query 代码 | gorm/gen 生成确定类型 model + query | DB 或 struct |
| 一次性数据订正 | Atlas data migration（方案 C，独立文件） | 版本化迁移 |

这套组合逐条命中 02 文档的 7 条约束，且把老项目的两大病根（三源 drift、seed 散落）都从**机制层面**堵死。

## 六、承认的 tradeoff（不回避）

- **Atlas 是额外的二进制 + CI 环节**（`atlas migrate diff` / `lint` / `apply`），团队需学最小工作流——换来的是可审查、可回滚、防 drift 的迁移。
- **方案 A 依赖路由注册规范**：要让 `api_resource` 有可读的 `name`/`module`，路由注册时就得带这些元数据，是一次性的改造成本 + 后续约定（每条路由登记描述）。若不带，自动生成的记录只有 path/method，前端展示不友好。
- **方案 B 的 upsert 需要稳定的业务主键/唯一键**：靠 `code` 之类的自然键做冲突目标，不能用自增 id，否则重跑会重复插入。
- **三套机制并存**（Atlas + seeder + 路由同步）比「一把梭全塞 migration」概念多，但每套都简单、职责单一，整体反而比老项目「三源互相打架」清晰。

## 七、落地要点（下一步参考，本轮不实施）

- **Atlas 接入**：`atlas.hcl` 配 GORM provider（`data "external_schema" "gorm"` 跑 loader 输出 struct schema）→ `atlas migrate diff` 生成迁移到 `migrations/` → `atlas migrate apply`。开发期可留 `AutoMigrate` 便利，CI/生产走 Atlas。
- **路由同步（方案 A）**：在 Step 07/08 权限模块落地。定义路由元数据登记方式（中间件或注册包装函数），提供 `repo.UpsertAPIResource` + 启动钩子或 `make sync-api` 命令。
- **Seeder（方案 B）**：仿 `老项目 A/scripts/init_data/` 结构，改 upsert 语义，出一个 `make seed`。菜单/字典/初始角色各一个 `seeds/*.go`。
- **迁移规范**：schema 变更走 Atlas；一次性数据订正走 Atlas data migration 独立文件；框架种子一律不进 migration。
- **配套规则**：可新增 `.claude/rules` 约定——「api_resource 禁止手写 SQL，统一路由同步」「seed 一律 upsert 幂等」「schema 变更只改 struct + atlas diff，禁止手写建表」。

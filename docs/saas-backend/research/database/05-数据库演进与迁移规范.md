# 数据库演进与迁移规范

> 本轮（2026-07）承接 [02-数据库访问层选型调研.md](./02-数据库访问层选型调研.md)、[03-迁移工具与数据初始化方案.md](./03-迁移工具与数据初始化方案.md)、[04-schema优先与数据库优先.md](./04-schema优先与数据库优先.md)。前四份解决**「用什么工具」**（GORM+gen+Atlas、迁移引擎、seed 分层、真相源方向）；本轮回答一个更本质的问题——**「成熟项目是怎么演进的：数据库字段怎么演进、里面的数据怎么演进，有没有成熟规范？」**

## 一、背景与本轮问题

前四份文档把「用什么工具建库、生成 model、跑迁移、灌种子」讲清楚了。但工具只是地基，真正每天会碰到、也最容易出事故的是**演进**：

- 上线跑了半年，要给 `users` 表加一个 `NOT NULL` 字段、重命名一列、把一个字段拆成两张表——**怎么改才不锁库、不停服、能回滚？**
- 加了新字段，几百万行历史数据的默认值/派生值**怎么回填（backfill）**，才不会一条 `UPDATE` 把库压垮？
- 团队多人、多环境、灰度发布，**新旧代码同时在线**时，schema 变了老实例还在读旧字段，怎么保证不炸？

这些不是「选型问题」，是**演进规范问题**。好消息是：这套规范业界已经非常成熟，有经典著作（Martin Fowler & Pramod Sadalage《Refactoring Databases》）、有公认模式（Expand-Contract / Parallel Change）、有数据库层面的安全 DDL 清单。本文把它们系统整理成一份可执行的规范，并说明如何嫁接到本项目已选定的 Atlas + gorm/gen 工具链上。

**一句话总纲**：**任何破坏性变更，都拆成若干个「向后兼容的小步」，每步单独部署、可回滚——绝不「一步到位」。**

## 二、核心模式：Expand-Contract（Parallel Change）

这是零停机 schema 演进的**唯一主干模式**，其他技巧都是它的细节。Martin Fowler 把它命名为 [Parallel Change](https://martinfowler.com/bliki/ParallelChange.html)，运维/DBA 圈更常叫 **Expand-Contract**（扩展-收缩）。

### 核心思想

一次「破坏性」逻辑变更（重命名列、改类型、拆表、加约束）**不能在一次部署里完成**，因为灰度/滚动发布期间，**新旧两版应用代码会同时连着同一个库**。若一步到位，旧实例立刻就崩（它还在读写已被删/改的列）。

正解：拆成三个**各自向后兼容**的阶段，每阶段一次独立部署：

| 阶段 | 动作 | 数据库状态 | 应用行为 |
|---|---|---|---|
| **① Expand（扩展）** | 加新结构，**旧结构保留** | 新旧列/表并存 | 老代码照常用旧列，无感知 |
| **② Migrate（迁移/过渡）** | 双写 + backfill 历史数据 | 新旧列都有完整数据 | 新代码**同时写新旧**、读时以新为准 |
| **③ Contract（收缩）** | 删旧结构 | 只剩新列/表 | 所有实例已只用新列，安全删旧 |

关键：**相邻两阶段之间，新旧代码可以任意混跑**——这正是滚动发布与随时回滚的安全保证。

### 完整案例：把 `users.email` 重命名为 `email_address`

**❌ 天真做法（一次搞定，会炸）**：
```sql
ALTER TABLE users RENAME COLUMN email TO email_address;
```
灰度期老实例仍执行 `SELECT email FROM users` → 立即报「列不存在」。整个滚动发布窗口都在故障。

**✅ Expand-Contract（三次部署）**：

```sql
-- ── 部署 v1：Expand ── 只加列，不动旧列
ALTER TABLE users ADD COLUMN email_address VARCHAR(255);
```
```go
// 部署 v2：Migrate —— 应用双写，读以新列优先、回退旧列
func (u *User) SetEmail(v string) {
    u.Email = v          // 旧列：兼容灰度期老实例
    u.EmailAddress = v   // 新列
}
func (u *User) GetEmail() string {
    if u.EmailAddress != "" {
        return u.EmailAddress
    }
    return u.Email       // 回退：backfill 未覆盖的老行
}
```
```sql
-- 部署 v2 配套：后台分批 backfill 历史数据（详见第五节）
UPDATE users SET email_address = email
WHERE email_address IS NULL AND id BETWEEN :lo AND :hi;
```
```sql
-- ── 部署 v3：Contract ── 确认无实例再读 email 后，删旧列
ALTER TABLE users DROP COLUMN email;
```

每次部署都保证「上一版代码在这个 schema 下仍能跑」，于是**滚动发布无损、任何一步都能回滚到上一版**。

### 适用范围

Expand-Contract 适用于**所有破坏性变更**：重命名列/表、改列类型、拆分/合并列、拆表、加 `NOT NULL`、改外键。**非破坏性变更**（纯加一张新表、加一个可空列、加索引）不需要三阶段，一步即可——但仍要遵守第四节的安全 DDL。

## 三、Schema 演进 vs Data 演进：必须分离

前面的「改列名」案例混杂了两件事：① 加列（schema migration），② 把几百万行的 `email` 值 copy 到 `email_address`（data migration / backfill）。业界铁律：**这俩必须分开执行**，因为性质完全相反。

### 对比表

| 维度 | Schema Migration | Data Migration（Backfill） |
|---|---|---|
| **定义** | 结构变更：`CREATE TABLE` / `ADD COLUMN` / `ADD INDEX` | 数据转换：填默认值、清洗、派生字段计算、归档 |
| **执行时机** | 部署期，跟随 migration 脚本自动跑 | 部署后，独立脚本手动或定时触发 |
| **事务** | 在事务内（DDL 失败整个回滚） | **事务外**（大表长事务会锁表） |
| **耗时** | 毫秒~秒级（PostgreSQL 多数 DDL 是元数据操作） | 分钟~小时级（正比于数据量） |
| **幂等** | 不强制（migration 只跑一次） | **必须幂等**（中断重跑不能重复/遗漏） |
| **工具** | Atlas / golang-migrate 自动跑 `.sql` | 独立 Go 脚本（`scripts/backfill_*.go`） |

### 为什么分离

**反例（把 data 混在 schema migration）**：
```sql
-- migrations/20260707_add_user_status.sql
ALTER TABLE users ADD COLUMN status VARCHAR(20);
UPDATE users SET status = 'active' WHERE last_login_at > NOW() - INTERVAL '30 days';
UPDATE users SET status = 'inactive' WHERE status IS NULL;
```

问题：
1. **锁库时间不可控**：`UPDATE` 扫全表，百万行需要几十秒——这段时间 `users` 表被长事务锁住，所有 INSERT/UPDATE 卡死。
2. **无法限速**：migration 一气呵成，压垮数据库连接池/磁盘 IOPS。
3. **失败难恢复**：跑到 80% 崩了，下次重跑会不会重复处理前 80%？

**正解（分离）**：
```sql
-- migrations/20260707_add_user_status.sql （快）
ALTER TABLE users ADD COLUMN status VARCHAR(20);
```
```go
// scripts/backfill_user_status.go （慢但安全）
func main() {
    for {
        result := db.Exec(`
            UPDATE users
            SET status = CASE
                WHEN last_login_at > NOW() - INTERVAL '30 days' THEN 'active'
                ELSE 'inactive'
            END
            WHERE status IS NULL AND id BETWEEN $1 AND $2
        `, rangeStart, rangeStart+1000).RowsAffected
        
        if result == 0 { break }
        rangeStart += 1000
        time.Sleep(100 * time.Millisecond)  // 限速，避免压垮库
    }
}
```

这样 migration 秒完，backfill 分 1000 行一批、每批后 sleep 100ms，既不锁库也能随时 Ctrl+C 中断、重跑幂等。

### 与 03 文档 seed 分层的关系

[03-迁移工具与数据初始化方案.md](./03-迁移工具与数据初始化方案.md) 的「方案 D」处理的是**配置类种子数据**（menus / 敏感词字典 / 权限模板）的**声明式演进**——用 YAML 记录期望状态，每个版本 merge 进去，migration 触发 `apply_seed.go` 对账。

本节的 **data migration（backfill）** 处理的是**业务历史数据的一次性转换**——算派生字段、清洗脏数据、归档冷数据。两者互补：

- **Seed（方案 D）**：配置数据，声明式，多次幂等执行，Git 版本化
- **Backfill（本节）**：业务数据，过程式，一次性，脚本 + 手动触发

## 四、PostgreSQL Safe DDL 清单

并非所有 DDL 都能秒完。下表列出 PostgreSQL 常见 DDL 的**锁表风险 + 安全替代写法**。

| 操作 | 是否锁表/重写 | 安全做法 |
|---|---|---|
| `ADD COLUMN`（无 `DEFAULT` / `NOT NULL`） | ✅ 不锁，仅元数据 | 直接执行 |
| `ADD COLUMN ... DEFAULT x` | ⚠️ PG 11+ 常量默认已优化为元数据；PG 10- 全表重写 | **PG 10-**：先 `ADD COLUMN`，backfill 分批填值，最后 `ALTER ... SET DEFAULT` |
| `CREATE INDEX` | ❌ 锁表（ShareLock 阻塞 INSERT/UPDATE/DELETE） | **`CREATE INDEX CONCURRENTLY`**（仅阻塞其他 DDL，DML 照常） |
| `ADD CONSTRAINT` (CHECK / FK) | ❌ 验证阶段全表扫描 + 锁 | **`ADD CONSTRAINT ... NOT VALID`** → 后台跑 **`VALIDATE CONSTRAINT`**（分两步，VALIDATE 时只加 ShareUpdateExclusiveLock） |
| `ALTER COLUMN ... SET NOT NULL` | ❌ 全表扫描验证 | ① 先加 `CHECK (col IS NOT NULL) NOT VALID` → ② `VALIDATE CONSTRAINT` → ③ backfill 补齐 NULL → ④ 改 `SET NOT NULL` |
| `DROP COLUMN` | ✅ 快（逻辑删除，标记不可见） | 直接执行，但需**先摘应用对该列的引用**（呼应 expand-contract 的 contract 阶段） |
| `ALTER COLUMN TYPE` | ❌ 全表重写（多数情况） | **方案 A**：expand-contract（加新列 → backfill → 删旧列）；**方案 B**：兼容类型转换（如 `VARCHAR(50)` → `VARCHAR(100)` PG 12+ 仅元数据，但 `INT` → `BIGINT` 仍重写） |

### 必备兜底设置

在所有 migration 前加：
```sql
SET lock_timeout = '2s';          -- 拿锁超 2 秒放弃，避免排队雪崩
SET statement_timeout = '30s';    -- 单条 SQL 跑超 30 秒强制中断
```

**作用**：如果 DDL 因意外拿不到锁（前面有长事务占着），2 秒后快速失败返回错误，而不是无限等待、堆积后续请求把库压垮。Atlas 可以在 migration 文件头统一加这段。

### Atlas `migrate lint` 的作用

Atlas 提供 [`migrate lint`](https://atlasgo.io/versioned/lint) 命令，能静态分析 migration SQL，检测：
- 破坏性变更（`DROP TABLE` / `DROP COLUMN` 无保护）
- 可能锁表的 DDL（`CREATE INDEX` 未用 `CONCURRENTLY`）
- 数据丢失风险（改列类型不兼容）

配合 CI 在 PR 阶段就拦住危险 migration——这是第六节「演化式数据库设计」原则的工具化。

## 五、大表在线变更

### 为什么大表危险

表有几千万行时，即使「安全 DDL」也可能扛不住：
- `ADD COLUMN DEFAULT` (PG 10-) / `ALTER TYPE` 需要全表重写 → 锁几小时
- `CREATE INDEX CONCURRENTLY` 虽不阻塞 DML，但扫全表建索引仍吃大量 IO，影响线上查询

此时需要**分批 + 限速 + 进度可查**的工具/脚本。

### MySQL：gh-ost / pt-online-schema-change

- **[gh-ost](https://github.com/github/gh-ost)**（GitHub 出品，推荐）：从 binlog 捕获增量变更（**无触发器**），分批 copy 原表到 ghost 表，追上后原子 rename。
- **pt-online-schema-change**（Percona）：用触发器同步增量，老方案但成熟。

gh-ost 核心流程：
```bash
gh-ost --host=prod-db \
       --database=mydb --table=users \
       --alter="ADD COLUMN status VARCHAR(20)" \
       --execute
```
1. 创建 `_users_gho`（ghost 表，应用新 schema）
2. 分批 copy `users` → `_users_gho`（每批 1000 行，可配置）
3. 从 binlog 实时捕获增量 INSERT/UPDATE/DELETE → 同步到 ghost 表
4. 追上后原子 `RENAME TABLE users TO _users_old, _users_gho TO users`

**优势**：无锁切换、可暂停/恢复、可测试（先在从库跑，确认无误再上主库）。

### PostgreSQL：分批 backfill + `pg_repack`

PG 因为 MVCC + 多数 DDL 元数据化，通常**不需要 gh-ost 这类工具**。危险场景（改列类型、PG 10- 加默认值）用 **expand-contract + 分批 backfill** 即可：

```go
// scripts/backfill_users_new_column.go
func main() {
    var lastID int64
    for {
        var maxID int64
        db.QueryRow(`
            SELECT MAX(id) FROM users
            WHERE new_column IS NULL AND id > $1
            LIMIT 10000
        `, lastID).Scan(&maxID)
        if maxID == 0 { break }
        
        db.Exec(`
            UPDATE users
            SET new_column = <派生逻辑>
            WHERE id > $1 AND id <= $2 AND new_column IS NULL
        `, lastID, maxID)
        
        lastID = maxID
        time.Sleep(200 * time.Millisecond)  // 限速
        log.Printf("Processed up to ID %d", maxID)
    }
}
```

**[pg_repack](https://github.com/reorg/pg_repack)**：类似 gh-ost，重建表去碎片/改物理存储。但用于「表膨胀回收」，不是日常 schema 变更的主力。

### 何时才需要

| 表大小 | DDL 类型 | 方案 |
|---|---|---|
| < 100 万行 | 任意 | 直接用第四节的安全 DDL |
| 100 万 ~ 1000 万 | 加索引 / 加列 | `CONCURRENTLY` / 分批 backfill |
| > 1000 万 | 改列类型 / 大范围 UPDATE | expand-contract + 独立脚本分批 + 监控，或 gh-ost(MySQL) |

**教学/小项目**（表始终 < 10 万行）几乎用不到这些——但要**知道边界在哪**，以免哪天表大了直接 `ALTER` 锁库几小时。

## 六、演化式数据库设计原则（Martin Fowler）

前面的 expand-contract、schema/data 分离、安全 DDL 都是**战术**。它们背后有一套**战略**——Martin Fowler 与 Pramod Sadalage 在 [Evolutionary Database Design](https://www.martinfowler.com/articles/evodb.html) 与《Refactoring Databases》里总结的四条核心原则。理解这四条，才知道前面的战术为什么这么设计。

| 原则 | 含义 | 对本项目的落地 |
|---|---|---|
| **① 所有变更都是 migration** | 任何 schema/data 变更都写成版本化脚本，**禁止手动改库**。开发/测试/生产走同一批脚本。 | Atlas 版本化迁移 + `scripts/backfill_*.go`；严禁 SSH 进生产手敲 `ALTER`。呼应 03 文档「三源 drift」教训。 |
| **② 变更有过渡期（transition period）** | 破坏性变更不是瞬间切换，新旧结构**并存一段时间**，等所有消费者迁移完再收尾。 | 这正是 expand-contract 的三阶段：Expand 与 Contract 之间就是过渡期，长度取决于灰度/回滚窗口。 |
| **③ 人手一个数据库（everybody gets their own）** | 每个开发者有独立本地库，能随意重建、试迁移，不互相干扰。 | 本地 Docker PG + `make reset-db`（跑迁移/schema.sql 建库）。呼应 02/04 落地要点。 |
| **④ 频繁集成（integrate frequently）** | migration 尽早合入主干、配 CI 自动跑，避免多人迁移脚本冲突到最后一刻才爆。 | CI 每次 PR 跑 `atlas migrate apply`（临时库）+ `atlas migrate lint`，第四节的 lint 拦截在这里生效。 |

**关键洞察**：这四条把「数据库演进」拉到和「代码演进」同一水平——**schema 和 data 的变更，享受与应用代码一样的版本控制、code review、CI、可回滚**。老项目的乱（03 文档的 3/12/57 drift）本质就是违反了原则 ①（有人手动建表、绕过 migration）。

## 七、与前四份文档的衔接

本文是「规范」，前四份是「工具」。规范如何嫁接到已选的工具链上：

### 与 02/04（真相源方向）：规范与方向正交

不管选 **schema 优先**（Go struct 真相源）还是 **数据库优先**（SQL 真相源），expand-contract、schema/data 分离、安全 DDL **全都适用**——它们约束的是「变更怎么落地」，与「真相源在哪」无关。

- schema 优先：改 struct（先加新字段、保留旧字段）→ Atlas diff → 分阶段迁移。
- 数据库优先：改 SQL schema（同样加新留旧）→ Atlas diff → 分阶段迁移。

两者的 expand-contract 流程一模一样，只是「改哪个真相源」不同。

### 与 03（迁移引擎 + seed 分层）：Atlas 承载 expand-contract，backfill 补齐 data 维度

- **Atlas 承载多阶段迁移**：expand-contract 的每个阶段就是一个（或一组）Atlas versioned migration。`migrate lint` 在 CI 拦截「未拆阶段的破坏性变更」（如直接 `DROP COLUMN`）。
- **03 方案 D（seed 演进） vs 本文 backfill（业务数据演进）分工明确**：

| 维度 | 03 方案 D：Seed | 本文：Backfill |
|---|---|---|
| 数据性质 | 配置类（menus/字典/权限模板） | 业务历史数据 |
| 语义 | 声明式（YAML 期望状态对账） | 过程式（一次性转换脚本） |
| 执行次数 | 多次幂等（每次部署对账） | 一次性（跑完即弃） |
| 触发 | migration 触发 `apply_seed.go` | 部署后手动/定时跑 `backfill_*.go` |

两者都遵守「data 与 schema 分离」，只是 seed 是「配置数据的声明式演进」，backfill 是「业务数据的一次性演进」。

## 八、承认的 tradeoff（不回避）

- **expand-contract 把一次逻辑变更拆成 3 次部署**：改个列名要 3 个 PR、3 次发布，比一条 `RENAME` 慢得多。代价换来的是零停机 + 可回滚。**小项目/内部工具/表很小**时，停服几秒直接 `ALTER` 反而更省事——规范要按规模裁剪，不是教条。
- **双写期的代码复杂度**：Migrate 阶段应用要同时读写新旧字段，多一层兼容逻辑，且容易忘记清理（Contract 阶段没做，旧字段永远留着）。需要有「技术债台账」跟踪未收尾的 contract。
- **backfill 脚本是一次性代码**：写完跑完就废弃，但仍要 code review、要幂等、要限速——容易被当作「随手脚本」不走质量流程，反而在生产出事。建议 backfill 脚本也进仓库、留记录。
- **本项目当前用不到大表工具**：gh-ost/pg_repack 对教学项目是过度设计。列在此处是为了「知道天花板在哪」，而非现在就引入。

## 九、落地要点（下一步参考，本轮不实施）

- **可提炼为 `.claude/rules` 迁移规范**（未来实现迁移模块时）：
  - 破坏性变更（改列名/类型/加 NOT NULL/拆表）**必须走 expand-contract 三阶段**，禁止一步到位。
  - schema migration 与 data backfill **分文件**：结构进 Atlas migration，数据进 `scripts/backfill_*.go`。
  - backfill 脚本**必须分批 + 限速 + 幂等**（`WHERE ... IS NULL` + `LIMIT` + `sleep`）。
  - DDL **默认加** `SET lock_timeout` / `statement_timeout`；建索引用 `CONCURRENTLY`；加约束用 `NOT VALID` + `VALIDATE`。
  - migration **必过 `atlas migrate lint`**（CI 拦截破坏性/锁表变更）。
- **CI 集成**：PR 阶段跑 `atlas migrate lint` + 临时库 `atlas migrate apply`，落实原则 ④。
- **本地环境**：`make reset-db` 支持一键重建，落实原则 ③。

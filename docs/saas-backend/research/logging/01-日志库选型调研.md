# 日志库选型调研

> 本轮（2026-06）为 Step 02 日志层选型所做的调研。新 `backend/` 当前用 zerolog，而 Go 标准库自 1.21 起内置了 `log/slog`。结论驱动了"新项目用 slog、`backend-rbac` 维持 zerolog"的决策。

## 背景

Step 02 基础设施层当前用 [`github.com/rs/zerolog`](https://github.com/rs/zerolog)：`pkg/logger/logger.go` 约 40 行，`LogConfig{Level, Format}`，stdout 输出，无文件轮转，`logging-style.md` 强制单行链式 `.Str().Msg()`。这是 2023 年前的主流选择。

但 Go 1.21（2023-08）把结构化日志收进了标准库 —— [`log/slog`](https://pkg.go.dev/log/slog)。到 2026 年，生态已经收敛：新项目应用代码默认写 `*slog.Logger`。于是要回答一个问题：**站在 2026 年，新 `backend/` 该继续 zerolog，还是改用 slog？**

调研目的：弄清 2026 年 Go 日志库的真实格局（性能、API、维护、成熟项目选型），给出明确推荐。

## 2026 Go 日志库全景

| 库 | 定位 | 标准库 | 一句话 |
|---|---|---|---|
| **`log/slog`** | 2026 新默认 | ✅ 是 | 标准库前端 + `Handler` 可换后端；生态已对齐 |
| **zerolog** (`rs/zerolog`) | 极致性能 | ❌ | 原生 API 下最快的成熟库；零分配 JSON |
| **zap** (`uber-go/zap`) | 高性能 + 可组合 | ❌ | Uber 规模验证；`zapcore.Core` 组合最强 |
| **phuslu/log** | 极限零分配 | ❌ | 跑分第一，但社区小（~840 star）、单人维护 |
| **logrus** (`sirupsen/logrus`) | 上一代标杆 | ❌ | **维护模式**，README 明确不再加新特性 |
| **charmbracelet/log** | CLI 美化输出 | ❌ | 给人看的终端日志，非生产后端 |

> 后端服务（机器消费日志）的真正候选只有四个：slog / zerolog / zap / phuslu。logrus 已过时，charm/log 是 CLI 专用。

## 性能 benchmark

来源：[Dash0《Choosing a Go Logging Library in 2026》](https://www.dash0.com/guides/golang-logging-libraries)，16 核机器写 `io.Discard` 隔离编码开销，测的是生产主流模式（请求级字段 attach 一次、每请求多次日志）。

### ① 原生 API

| 库 | ns/op | B/op | allocs/op |
|---|---|---|---|
| phuslu/log | 25 | 0 | 0 |
| **zerolog** | **26** | 0 | 0 |
| zap | 51 | 0 | 0 |
| zap (sugar) | 82 | 16 | 1 |
| **slog** | **101** | 0 | 0 |
| logrus | 9126 | 3078 | 55 |
| charm/log | 16786 | 9353 | 61 |

phuslu 与 zerolog 并列第一（~25 ns、零分配），zap 次之，**slog 标准处理器 ~101 ns、零分配**。logrus/charm 是另一个数量级。

### ② 作为 slog 后端（`slog.Handler`）

| 后端 | ns/op | B/op | allocs/op |
|---|---|---|---|
| phuslu/log | 38 | 0 | 0 |
| zap | 70 | 0 | 0 |
| slog (标准) | 101 | 0 | 0 |
| **zerolog** | **1180** | 1442 | 16 |

> ⚠️ **关键洞察**：zerolog 原生 26 ns、零分配，但它的 **slog 桥接暴跌到 ~1180 ns（慢 46×）**。原因是 zerolog 原生把 `WithAttrs` 字段预算序列化进复用 buffer，而它的 slog 桥接把字段存成 `[]slog.Attr` 每次 `Handle()` 重新编码。**所以"slog API + zerolog 后端"是个陷阱 —— 既丢掉了 slog 的简洁，又丢掉了 zerolog 的速度。**

## 成熟项目怎么选

| 项目 | 选型 | 备注 |
|---|---|---|
| **Kubernetes** | `klog` + [`logr`](https://github.com/go-logr/logr) 接口 | [KEP-1602](https://github.com/kubernetes/enhancements/blob/master/keps/sig-instrumentation/1602-structured-logging/README.md) 结构化、1.24 起 context logging，长期方向是往 slog 对齐（logr 已有 slog handler） |
| **controller-runtime / Operator SDK** | zap 作为 `logr` 后端 | Kubernetes operator 生态默认 |
| **Docker / Moby** | logrus | 历史遗留，logrus 已进维护模式，新代码不该再选它 |
| **Cloud66** | zerolog | 2025 年公开表示全线 Go 项目标准化 zerolog |
| **2025/26 新项目与库** | slog | [JetBrains Go 生态 2025](https://blog.jetbrains.com/go/2025/11/10/go-language-trends-ecosystem-2025/) 显示 slog 快速上升为新默认 |

规律：**库 / 抽象层**（不想强加依赖）→ slog 或 logr 接口；**要极致性能的应用** → zerolog/zap；**遗留大项目** → 各自的历史选型（logrus/klog）。

## 社区共识与维护状态

- **slog 是新默认**：[Go 官方 blog](https://go.dev/blog/slog)、[Dash0 2026 指南](https://www.dash0.com/guides/golang-logging-libraries) 开篇即"新项目应用代码直接用 slog"。原因不是最快，而是**标准库、生态对齐、后端可换**。
- **zerolog 仍健康维护**：[pkg.go.dev](https://pkg.go.dev/github.com/rs/zerolog) 最新发版 **2026-04**，社区活跃。所以"`backend-rbac` 留 zerolog"无任何风险。
- **logrus 进维护模式**：README 明确不再加新特性，性能落后 slog 约 90×，新项目别用。
- **slog 仍在完善**：如多 handler 分发（`MultiHandler`）在社区提案 [golang/go#65954](https://github.com/golang/go/issues/65954) 推进中；OTel 集成靠 [`otelslog`](https://pkg.go.dev/go.opentelemetry.io/contrib/bridges/otelslog) 桥接。
- **社区口吻**（Reddit r/golang / HN）：多数场景"just use slog, it'll be fine"；要极限吞吐或偏爱流式 API 的人留 zerolog/zap。

## 对本项目的选型矩阵

只比两个真正候选（zap/phuslu 对 Web 后端属过度设计，已排除）：

| 维度 | **slog（标准库）** | **zerolog（维持现状）** |
|---|---|---|
| 外部依赖 | ✅ 零（stdlib） | ❌ 一个第三方依赖 |
| 契合 config 层"极简依赖/零反射"哲学 | ✅ 完全契合 | ⚠️ 多一个依赖 |
| API 风格 | `slog.Info("msg", "k", v)` / `slog.Attr` 强类型 | 流式 `.Str().Int().Msg()`，更顺手 |
| 原生性能 | 101 ns（够用，零分配） | 26 ns（顶级，零分配） |
| 后端可换（不改动调用点） | ✅ `Handler` 原生支持 | ⚠️ 只有原生 API 才快（桥接慢 46×） |
| OpenTelemetry 就绪 | ✅ `otelslog` 一行接入 | ❌ 无官方 OTel 路径 |
| 与 `backend-rbac` 一致性 | ❌ 仓库会有两种风格 | ✅ 一致 |
| 教学价值（2026 现代标准） | ✅ 教正确的新方式 | ⚠️ 教 2023 前的主流 |
| `logging-style.md` 单行规则 | 需改写（见落地要点） | 已就位 |
| 迁移成本（仅 `backend/`） | 中：~40 行 logger + 15 调用 + GORM 适配器 + 规则 | 零 |

> Web 后端的瓶颈是 DB / Redis / 网络（毫秒级），日志编码（纳秒级）**根本不是瓶颈**。所以性能那 4× 差距（101 vs 26 ns）对本项目无意义 —— 决策应看依赖、可演进性、教学价值。

## 结论（驱动决策）

1. **新 `backend/` 教程项目采用 `log/slog`**（`slog.NewJSONHandler`）。理由：2026 生态默认、零外部依赖（与 config 层"极简依赖/零反射"哲学一致）、`Handler` 解耦后端可换、性能对 Web 后端毫无瓶颈且零分配、`otelslog` 直通 OTel（SaaS 可观测性关键）、教程应教 2026 现代标准。
2. **`backend-rbac/` 维持 zerolog 不迁**：384 处调用、zerolog 2026-04 仍活跃发版、迁移成本高收益低。两个后端是不同年代（rbac 是成熟在跑、`backend/` 是 2026 全新脚手架），风格不一致可接受。
3. **否定 "slog API + zerolog 后端" 混合**：zerolog 的 slog 桥接慢 46×，混合等于两边优势都丢。若未来真要极致性能，正解是 **slog + phuslu/zap 后端**（标准 API + 近零分配），但对 Web 后端属过度设计，本轮 YAGNI。

**承认的 tradeoff**（写进决策记录，不回避）：
- 与 `backend-rbac` 日志风格不一致（可接受，见上）。
- slog 的 key-value 弱类型 API（`slog.Info("msg","k",v)`）易写错（漏一个参数、key/value 颠倒都静默产出脏日志）→ 用 `slog.Attr` 强类型构造器 + [`sloglint`](https://github.com/go-simpler/sloglint) 静态检查兜底。
- slog 无 `Fatal` 级别（zerolog 有 `.Fatal()`）→ main 启动失败用标准库 `log.Fatal` / `os.Exit`。
- GORM 适配器需照现有 `gormZerologger` 结构重写一份 slog 版（工作量小）。

## 若采纳 slog 的落地要点（下一步参考，本轮不实施）

- **`pkg/logger` 改造**：`New(cfg) *slog.Logger`，用 `slog.NewJSONHandler(out, &slog.HandlerOptions{Level: &levelVar, AddSource: true})`；`console` 格式用 `slog.NewTextHandler` 或自定义 Handler；级别用 `slog.LevelVar` 支持运行时调整。
- **GORM → slog 适配器**：实现 `gormlogger.Interface`，结构照搬现有 `gormZerologger`，把 `Info/Warn/Error/Trace` 映射到 `slog.Logger` 的对应级别（`Trace` 正常 Debug、出错 Error，带 `elapsed`/`rows`/`sql` 字段）。
- **`logging-style.md` 规则改写**：从"zerolog 单行链式"改为——① 用 `slog.Attr` 强类型、禁止裸 key-value；② 优先 context 变体（`InfoContext` 等）便于 trace 关联；③ 禁止裸 `fmt.Printf` 调试输出；④ 引入 `sloglint` 进 `golangci-lint`。
- **请求级字段**：用 `logger.With("request_id", ..., "tenant_id", ...)` 生成子 logger 透传，或挂到 `context.Context`（slog 原生支持 `Logger.Handle` + ctx）。
- **OTel（可选，后续 Step）**：`otelslog.NewLogger(...)` 替换 Handler，日志即 OTel 信号，自动关联 trace/span。

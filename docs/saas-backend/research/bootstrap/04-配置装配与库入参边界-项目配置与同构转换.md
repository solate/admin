# 配置装配与库入参边界：项目配置与同构转换

> 2026-07。本文回答组合根里一个真实的设计边界问题：**`internal/config.Config`（项目专属、带 YAML tag）与 `pkg/xgorm.Config` / `pkg/xredis.Config` / `pkg/xslog.Config`（可复用库入参、无 tag）为什么故意是两个类型、不合并成一个？组合根怎么「翻译」它们？手搬字段啰嗦，有没有更优雅的连接方式？**
>
> 结论先行（可移植性优先）：**项目配置与库入参故意分离**——前者绑 viper 方言、每项目字段不同，后者纯 Go struct、可整目录 copy；合并会让 pkg 反向依赖 internal（逆依赖）或长出 mapstructure tag（反向污染）。对于**字段同构**的纯数据配置（db/redis），用 Go 1.8+ 的 **struct 类型转换** `xgorm.Config(cfg.Database)` 一行替掉手搬 9 行字段，编译期逐字段校验、比手写映射更安全；对于**带行为字段**的构造参数（xslog），保持显式 `xslog.Config{...}` + 代码注入行为——这不是设计缺陷，是日志领域特性（slog/zap 都如此）。项目↔库的边界始终在，只是连接方式从「手搬字段」升级为「同构转换」。
>
> 关联：装配组织见 [02](./02-依赖装配与分层对象化-手工注入与struct封装.md)，生命周期编排见 [01](./01-应用启动与组件生命周期-main组合根与gin-cron编排.md)；落地约束参照 [domain-architecture.md](../../../../.claude/rules/domain-architecture.md)、[reusable-package.md](../../../../.claude/rules/reusable-package.md)。
>
> 日常写代码看 `backend/cmd/server/main.go` 里三行实例即可；想搞明白「为什么不把三个 pkg Config 合并进 config.Config」「xslog.Config 为何带函数字段」时看这里。

## 结论速览

组合根里的配置装配，一张表说清「项目配置」与「库入参」的边界：

| 维度 | `internal/config.Config` | `pkg/x*.Config`（xgorm/xredis/xslog） |
|------|-------------------------|-----------------------------------|
| 归属 | 项目专属（每项目字段不同） | 可复用库（可整目录 copy，见 [reusable-package.md](../../../../.claude/rules/reusable-package.md)） |
| 内容 | 项目全部配置清单 | 单个库的构造入参 |
| 序列化 tag | 有（`mapstructure:"..."`，绑 viper 方言） | 无（纯 Go struct，不认识 YAML） |
| 依赖方向 | 组合根 import 它 + 各 pkg | pkg **不**反向 import 它（依赖单向） |
| 字段性质 | 纯数据（从 YAML 反序列化） | xgorm/xredis 纯数据，**xslog 含行为字段**（func/io.Writer） |
| 连接方式 | 同构纯数据 → 类型转换一行 | 带行为或不同构 → 显式构造 |

**核心判据**：库入参与项目配置**同构纯数据** → `xgorm.Config(cfg.Database)` 转换；**带行为或不同构** → `xslog.Config{Level: cfg.Log.Level, ...}` 显式构造。两者都**不合并类型、不反转依赖方向**——项目↔库的边界始终在，只是连接优雅度不同。

被刻意否掉的方向：让 pkg import `internal/config`（逆依赖）、把 config 挪回 `pkg/config`（语义拧巴）、把 `xgorm.Config` 内嵌进 `config.Config`（反向污染 + xslog 根本嵌不进）。

## 一、为什么故意是两个类型：三种诱人但错误的走法

组合根里配置喂进各 pkg 构造函数时，直觉上「把三个 pkg 的 Config 合并进 `config.Config` 成一个 struct」最省事——一个类型贯穿到底、零翻译层。但这打破了**项目↔库的可移植性边界**，有三种看似省事实则错误的走法：

### 走法 1：让 pkg import `internal/config`

```go
// pkg/xgorm/xgorm.go 直接吃项目配置
func New(cfg *config.DatabaseConfig, log *slog.Logger) (*gorm.DB, error)
```

**代价**：pkg **反向依赖** internal，从此绑死本项目——`pkg/xgorm` 失去「整目录 copy 去别的项目」的可移植性。违反 [reusable-package.md](../../../../.claude/rules/reusable-package.md)「x 包不依赖宿主 internal」与 [domain-architecture.md](../../../../.claude/rules/domain-architecture.md) 的依赖方向「pkg 不 import internal」。哪天另一个项目想复用 xgorm，得先把 `internal/config` 一起拖过去，或者改 xgorm 签名——**可复用库成了项目专属代码**。

### 走法 2：把 config 挪回 `pkg/config`

把 `internal/config` 整个挪到 `pkg/config`，让 pkg 能同级 import。

**代价**：`Config` 结构体是**每项目不同的专属清单**（这个项目有 JWT/CORS，下个项目可能换 OAuth2/GRPC），塞进「可复用层」**语义拧巴**——它根本不可复用。pkg 的定位是「可整目录 copy 的通用封装」，放个「项目 A 的配置清单」进去自相矛盾。而且你想「复制 pkg/ 去新项目」时，会发现 `pkg/config` 里的 `Config` 还是得全改字段——那它放 pkg 有何意义？

### 走法 3：把 `xgorm.Config` 内嵌进 `config.Config` 做字段

```go
// internal/config/config.go
type Config struct {
    App      AppConfig
    Server   ServerConfig
    Database xgorm.Config  `mapstructure:"database"`  // 直接内嵌 pkg 类型
    Redis    xredis.Config `mapstructure:"redis"`
    Log      xslog.Config  `mapstructure:"log"`
    JWT      JWTConfig
}
```

这次依赖方向合法（internal → pkg），但有两个隐蔽代价：

1. **反向污染**：xgorm.Config 现在**没有 tag**，mapstructure 靠字段名大小写不敏感匹配，YAML 里 `max_idle_conns` 匹配不上 `MaxIdleConns`（下划线 vs 驼峰）。要让它工作，得给 `pkg/xgorm.Config` 加上 `mapstructure:"max_idle_conns"` tag——**可复用库的 Config 长出了 viper 方言**。污染方向反过来了，但污染还在。
2. **xslog 根本嵌不进**（硬伤）：`xslog.Config` 带 `Output io.Writer` / `ContextExtractors []func` / `ReplaceAttr func` 三个**行为字段**，YAML 填不了、只能代码注入。一旦内嵌进 `config.Config`，你的「配置总清单」就变成**一半能从 YAML 填、一半只能代码填**的混合体，「这个 struct 代表配置文件内容」这条最基本的心智模型就破了（见第二节）。

**结论**：三走法要么逆依赖（走法 1）、要么语义拧巴（走法 2）、要么反向污染 + 硬伤（走法 3）。所以**项目配置与库入参故意分离**，组合根承担「翻译」职责——把 `config.Config` 的子块喂进各 pkg 构造函数。这正是 README 核心设计原则 #4「各 pkg 自有 Config，pkg 不知道 YAML」的体现。

## 二、xslog 的例外：构造参数集 vs 配置文件映射

`xgorm.Config` / `xredis.Config` 是**纯数据**（Host/Port/PoolSize 全是标量，YAML 能填满），但 **`xslog.Config` 不是**——它带三个 YAML 无法表达的字段：

```go
// pkg/xslog/config.go（节选）
type Config struct {
    Level     string    // 数据：从 YAML 来
    Format    Format    // 数据：从 YAML 来
    AddSource bool      // 数据：从 YAML 来

    // ---- 行为：YAML 填不了，代码注入 ----
    Output            io.Writer              // 往哪写（测试时注入 bytes.Buffer，生产是 os.Stdout）
    ContextExtractors []ContextExtractor     // 怎么从 ctx 提字段（接 OpenTelemetry 的口子）
    ReplaceAttr       func(...) slog.Attr    // 怎么改写字段（脱敏 password/token）
}
```

这三个字段天生是**运行时对象与逻辑**，写不进配置文件：

- `Output io.Writer` — 接口，YAML 没法序列化一个 writer
- `ContextExtractors []func` — 函数切片，提取逻辑是代码不是数据
- `ReplaceAttr func` — 函数，「如何脱敏」是逻辑不是配置项

所以 `xslog.Config` 不是「配置文件的映射」，是**「构造 logger 的参数集」**——数据与行为混装很正常。YAML 只能填前三个字段（Level/Format/AddSource），后三个必须在组合根里用代码注入：

```go
// backend/cmd/server/main.go（节选）
log := xslog.New(xslog.Config{
    Level:     cfg.Log.Level,       // 从配置文件来
    Format:    cfg.Log.Format,      // 从配置文件来
    AddSource: cfg.Log.AddSource,   // 从配置文件来
    // Output/ContextExtractors/ReplaceAttr 留 nil，xslog.New 内部有零值默认（os.Stdout/内建提取器/无脱敏）
}).With("service", cfg.App.Name, "env", cfg.App.Env)  // 资源标签在代码里绑实例
```

**这不是 xslog 设计缺陷，是日志领域特性**：

- **Go 标准库 `log/slog` 的 `HandlerOptions.ReplaceAttr` 本身就是 `func`** — 官方亲自示范「日志构造参数含行为」。
- **[uber-go/zap](https://github.com/uber-go/zap) 用 functional options 更彻底** — 连 struct 都不给，`zap.New(core, zap.WrapCore(...), zap.Hooks(fn))` 全是行为注入。
- **日志器的三大不可配置需求**（往哪写 / 脱敏逻辑 / 上下文提取）在任何成熟日志库都是「参数集的一部分」而非「配置文件的一部分」。数据库连接恰好只需数据（Host/Port/Password），不是它「设计更好」，是领域需求本就不同。

所以 log 那段保持显式 `xslog.Config{...}` 构造，**不勉强用类型转换**——因为 `LogConfig`（3 个数据字段）与 `xslog.Config`（3 个数据 + 3 个行为）不同构。

### 说清楚：log 不是「不该」转换，是「编译不过」

这里容易误读成「log 我们选了另一种风格」。不是——`xslog.Config(cfg.Log)` **写出来根本编译不过**。Go 的 struct 类型转换有硬前提：两个 struct 字段的**名、类型、顺序完全相同**（仅 tag 可不同，见第三节）。log 这对类型两条都不满足：

| | `config.LogConfig`（3 字段） | `xslog.Config`（6 字段） |
|---|---|---|
| 1 | `Level string` | `Level string` |
| 2 | `Format string` | `Format Format` |
| 3 | `AddSource bool` | `Output io.Writer` ← 插在中间 |
| 4 | — | `AddSource bool` ← 顺序错位到第 4 |
| 5 | — | `ContextExtractors []ContextExtractor` |
| 6 | — | `ReplaceAttr func(...) slog.Attr` |

两处不同构，任一处就让转换编译失败：**① 字段数量不同**（xslog 多三个行为字段）；**② 连顺序都错位**——`AddSource` 在 `LogConfig` 是第 3 个，在 `xslog.Config` 因为 `Output` 插在中间被挤到第 4 个。

所以 log 段的显式 `xslog.Config{Level: ..., Format: ..., AddSource: ...}` 不是「换个风格」，是**唯一能编译的写法**。那三个行为字段不写、留 nil，靠 `xslog.New` 内部零值默认兜底（`os.Stdout` / 内建 contextFieldsExtractor / 无脱敏）——数据从 YAML 来、行为留默认，各得其所。

## 三、优雅连接：同构 struct 直接转换

`config.DatabaseConfig` 与 `xgorm.Config` 字段**同构**（名、类型、顺序全同，仅 tag 不同）：

```go
// internal/config/config.go
type DatabaseConfig struct {
    Host            string `mapstructure:"host"`
    Port            int    `mapstructure:"port"`
    User            string `mapstructure:"user"`
    Password        string `mapstructure:"password"`
    DBName          string `mapstructure:"dbname"`
    SSLMode         string `mapstructure:"sslmode"`
    MaxIdleConns    int    `mapstructure:"max_idle_conns"`
    MaxOpenConns    int    `mapstructure:"max_open_conns"`
    ConnMaxLifetime int    `mapstructure:"conn_max_lifetime"`
}

// pkg/xgorm/config.go
type Config struct {
    Host            string
    Port            int
    User            string
    Password        string
    DBName          string
    SSLMode         string
    MaxIdleConns    int
    MaxOpenConns    int
    ConnMaxLifetime int
}
```

**Go 1.8+ 规则**：两个 struct 若字段的名、类型、顺序都相同，仅 tag 不同，可以直接类型转换。这是编译期逐字段校验——任一方增删字段而另一方未同步，转换处立刻编译报错（比手搬字段更安全，手搬漏一个编译器不报错）。

手搬字段可以塌缩成一行：

```go
// ❌ 手搬 9 行：啰嗦，且漏一个字段编译器不报错
db, err := xgorm.New(xgorm.Config{
    Host: cfg.Database.Host, Port: cfg.Database.Port, User: cfg.Database.User,
    Password: cfg.Database.Password, DBName: cfg.Database.DBName, SSLMode: cfg.Database.SSLMode,
    MaxIdleConns: cfg.Database.MaxIdleConns, MaxOpenConns: cfg.Database.MaxOpenConns,
    ConnMaxLifetime: cfg.Database.ConnMaxLifetime,
}, log)

// ✅ 同构转换一行：编译期逐字段校验，漏/错字段直接编译不过（比手搬更安全）
db, err := xgorm.New(xgorm.Config(cfg.Database), log)
```

`xredis.Config` 与 `config.RedisConfig` 同样同构，一样塌缩成一行。

### 同构转换的性能真相：零成本，别把它当序列化

常见疑虑：`xgorm.Config(cfg.Database)` 是不是比手搬字段慢、是不是有隐藏开销？**没有，两者性能字节级等价。**

关键先厘清一个误解：**struct 类型转换不是反射、不是序列化**——它跟 `json.Marshal` / mapstructure decode 是两码事。后者要在运行期遍历字段、查 tag、装箱拆箱；而 struct 转换是**编译期**的类型身份检查：编译器确认两个类型内存布局完全相同后，允许你「重新解释」这块内存，运行期只剩一次**值拷贝**（把结构体字节整块 copy）。

对照手搬字段：`xgorm.Config{Host: cfg.Database.Host, Port: ...}` 逐字段拷进新结构体，最终也是一次值拷贝。两种写法编译出的机器码**基本一致**，都是「把这块内存拷到那块」。更何况 `xgorm.New(cfg)` 是**按值传参**——无论转换还是手搬，这一次拷贝都躲不掉，转换既没省掉它、也没多出别的。

```go
xgorm.Config(cfg.Database)          // 编译期类型检查 + 运行期一次值拷贝
xgorm.Config{Host: ..., Port: ...}  // 逐字段赋值 + 运行期一次值拷贝 —— 机器码基本相同
```

**结论**：转换的收益纯在**安全性（编译期逐字段校验）+ 行数（9 行塌成 1 行）**，不在性能。性能维度上转换与手搬完全等价，选转换不必担心开销，选手搬也不会更快。

## 四、组合根里的最终形态

`backend/cmd/server/main.go` 里三段——纯数据的用转换、带行为的保持显式：

```go
// 2. 初始化日志 — 带行为字段 → 显式构造（行为字段留给代码注入），再 .With 绑资源标签
log := xslog.New(xslog.Config{
    Level:     cfg.Log.Level,
    Format:    cfg.Log.Format,
    AddSource: cfg.Log.AddSource,
}).With("service", cfg.App.Name, "env", cfg.App.Env)

// 3. 连接数据库 — 同构纯数据 → 类型转换一行
// xgorm.Config 与 config.DatabaseConfig 字段同构（名/类型/顺序一致，仅 tag 不同），
// 直接用 Go 的 struct 类型转换替代逐字段搬运：编译器逐字段校验，任一方增删字段
// 而另一方未同步会编译失败——比手写映射更安全，且两个类型仍独立（隔离带保留）。
db, err := xgorm.New(xgorm.Config(cfg.Database), log)
if err != nil {
    return fmt.Errorf("connect database: %w", err)
}
defer xgorm.Close(db)

// 4. 连接 Redis — 同上，xredis.Config 与 config.RedisConfig 同构，直接类型转换
rdbClient, err := xredis.New(xredis.Config(cfg.Redis))
if err != nil {
    return fmt.Errorf("connect redis: %w", err)
}
defer rdbClient.Close()
```

判据：库入参与项目配置**同构纯数据** → 类型转换；**带行为或不同构** → 显式构造。两者都**不合并类型、不反转依赖方向**——那条项目↔库的边界始终在，只是连接方式从「手搬字段」升级为「同构转换」。

## 五、成本与 tradeoff（已知并接受）

- **同构转换要求字段严格对齐**：`xgorm.Config(cfg.Database)` 依赖两个 struct 字段名/类型/顺序完全一致，任一方增删字段，转换处会立刻编译报错。这是**特性不是负担**——它强制「项目配置」与「库入参」同步，比手搬字段（漏一个编译器沉默）更安全。哪天 xslog 那样长出行为字段、不再同构，就退回显式构造，不勉强转换。
- **项目↔库边界的维护成本**：两个类型分离意味着给 `DatabaseConfig` 加字段时，`xgorm.Config` 也要同步加（否则转换处编译报错）。接受——这正是「让 pkg 可移植」的代价，只有项目专属字段（如 `TenantID`）确实不该进 pkg 入参时，才有摩擦。那时手工过滤掉那一个字段传其余，或退回显式构造，都比让 pkg 反向依赖 internal 划算。
- **行为字段的界定**：`xslog.Config` 带行为字段是显然的（`func`/`io.Writer`），但哪些是「可能长出行为字段」的领域、该预防性用显式构造？经验判据：**日志 / 监控 / tracing / 序列化**这类「可插拔扩展点」的库，构造参数天然含行为；**连接类**（DB/Redis/HTTP client）纯数据居多。不必预判，同构就转换，长出行为字段后编译器会在转换处报错，届时退回显式构造即可。
- **`.With("service", "env")` 的位置**：资源标签（`service`/`env`，对应 OpenTelemetry 的 `service.name` / `deployment.environment`）绑在 logger 实例上是日志可观测性领域的标准做法——它们是「这条日志来自谁」的身份标签，不是「这次请求发生了什么」的业务字段。本地单服务开发时看着冗余，生产集中式日志（Loki/ELK）时是基础过滤维度。不与「配置数据 vs 行为」的主线纠缠，属于日志使用约定，不展开。

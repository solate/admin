# 从单机到多节点：重复跑与拆调度器

> 2026-07。本文回答任务调度从单机走向多节点时的**第一个、也是最常见的坑**——同一份代码部署成多个副本后，定时任务会被跑 N 遍，怎么办？
>
> 结论先行：**真正的分水岭不是「副本数」、更不是「用哪个库」，而是「调度器要不要单独拆成一个服务」。** 把定时任务和业务打进同一个二进制、再 `replicas: 3`，同一任务就会被 3 个副本各触发一次。解决它有两条互斥的路——**路 A（库层面）**用 gocron + Redis 锁把 N 个抢跑的副本压成一个，是 best-effort；**路 B（架构层面，首选）**把调度器单拆成 `replicas: 1`，全局只有一个进程会触发，「跑一次」天然成立，零锁零 Redis。路 B 对中小项目更干净——它不是「解决」共识问题，而是让共识问题**根本不出现**。
>
> 关联：本文是全系列的枢纽——单机段（[02](./02-单机执行模型-从ticker到持久队列的四档.md) 执行模型、[03](./03-cron库选型-robfig与gocron对比.md) 库选型）到多节点段的入口。路 A 里 Redis 锁「为什么只是 best-effort」的根因见 [06](./06-分布式共识-选主仲裁与不重复的本质.md)；「漏一次都不行」的持久化需求见 [02](./02-单机执行模型-从ticker到持久队列的四档.md) 第四档 River。
>
> 日常不必读；服务要上多副本、纠结「定时任务会不会重复跑 / 要不要上分布式锁」时看这里。

## 一、多副本下定时任务会发生什么

**多副本几乎从不是为定时任务开的**，而是业务服务为了高可用/负载均衡顺带的结果：k3s/k8s `replicas: 3`、多台机器、滚动更新时新旧版本并存。如果你把定时任务代码和业务代码打进**同一个二进制**、再 `replicas: 3` 部署，会发生什么：

k3s 拉起 3 个一模一样的 Pod，每个进程都执行了同一段「注册定时任务」的代码，它们**互不知道对方存在**，各跑各的调度循环。到了 `0 2 * * *`，**3 个 Pod 各自触发一次 → 同一个任务被执行 3 遍**。

后果取决于任务性质：

| 任务类型 | 跑 3 遍的后果 |
|---|---|
| 幂等（清理过期 session、`DELETE WHERE expired`） | 没事。3 个删同一批，结果一样，顶多浪费点 DB 查询 |
| 累加/统计（把今日订单数写进报表表） | **数据错**。可能算 3 次，或 3 个并发读到中间态互相覆盖 |
| 有外部副作用（发邮件、短信、扣费、调第三方 API） | **事故**。用户收到 3 封邮件、扣 3 次费 |
| 写文件/生成导出 | **竞争**。3 个同时写同一路径，文件损坏或互相覆盖 |

**关键：cron 库（robfig / gocron 单机模式 / ticker）完全不知道自己在多副本里，它没有任何机制阻止这件事。** 这不是库的 bug——它的职责就只是「到点触发」，协调是别人的事。

## 二、两条路：解决「多副本跑 N 遍」

要让「到点只跑一次」，有两条**互斥**的路。

### 路 A：库层面——上 gocron + Redis Locker

cron 和业务仍挤在同一个多副本部署里。3 个 Pod 到点都想跑，但先去 Redis 抢一把锁，只有抢到的那个真跑，另外俩看到锁被占就跳过。这就是 gocron 的 `WithDistributedLocker` / `WithDistributedElector` 干的事。

```go
// 选项 1：Locker（基于 Redis/etcd 的分布式锁，任一时刻只一个副本执行该任务）
redisLocker := gocronredis.NewRedisLocker(rdbClient)
s, _ := gocron.NewScheduler(gocron.WithDistributedLocker(redisLocker))
s.NewJob(
    gocron.CronJob("0 2 * * *", false),
    gocron.NewTask(heavyReport),
    gocron.WithSingletonMode(gocron.LimitModeReschedule),  // 拿不到锁→下次再试
)

// 选项 2：Elector（基于 Redis/etcd 选主，leader 独占全部周期任务）
redisElector := gocronredis.NewRedisElector(rdbClient)
s, _ := gocron.NewScheduler(gocron.WithDistributedElector(redisElector))
// 不再需要每任务加 Singleton——整个 scheduler 只在 leader 跑
```

**Locker vs Elector**：
- **Locker**（任务粒度）：每个任务独立抢锁，A 任务在副本 1 跑、B 任务在副本 2 跑——适合任务间独立、希望负载分散。
- **Elector**（scheduler 粒度）：选出一个 leader 副本、它独占全部周期任务——适合任务少 + 要统一协调。

代价与边界：
- **依赖更重**：引 gocron + 依赖 Redis + 每任务配 Singleton。
- **且是 best-effort**：锁续期竞态、时钟偏移下，极端情况仍可能两个副本都跑，**不保证严格一次**。有副作用的任务该幂等还得幂等。**为什么 Redis 锁做不到严格一次、什么才能——根因见 [06](./06-分布式共识-选主仲裁与不重复的本质.md)。**

> 注：老项目手搓的 `SetNX` 锁就是 Locker 的业务层重新发明。gocron 的 `gocron-redis-lock` 包已提供生产级实现（自动续期、防死锁、Lua 脚本原子操作），比手搓省事——但「省事」不等于「严格正确」，它和手搓锁在共识谱系上是同一档（见 [06](./06-分布式共识-选主仲裁与不重复的本质.md) 第五节）。

### 路 B：架构层面——把调度器单拆成 `replicas:1`（首选）

业务还是 `replicas: 3`（但这些 Pod 里**不注册** cron），另起一个只有 `replicas: 1` 的调度器部署单元。全局只有 1 个进程会触发定时任务，「跑一次」天然成立，**零锁、零 Redis、零 gocron**。robfig 薄封装（甚至 stdlib ticker）照样够。

落地「调度器单副本」三选一，都比分布式锁简单：

- **配置开关（最贴合单体架构）**：同一个二进制加个 `ENABLE_SCHEDULER` 配置。业务 Deployment 跑 `replicas: N` + `ENABLE_SCHEDULER=false`；另起一个 Deployment 跑 `replicas: 1` + `ENABLE_SCHEDULER=true`，只有它注册 cron。代码一份，部署两份。
- **独立部署**：把调度器拆成单独的小服务/二进制，`replicas: 1`。
- **K8s CronJob**：干脆让 k8s 定时拉起 Job pod，连进程内调度器都不要。

### 两条路对比

| | 路 A：库层面（gocron） | 路 B：架构层面（拆调度器，首选） |
|---|---|---|
| 做法 | cron 和业务挤在同一多副本部署，靠 gocron + Redis 锁去重 | 调度器单拆 `replicas:1`，业务无状态多副本 |
| 依赖 | gocron + Redis + 每任务 Singleton 配置 | 无（robfig/ticker 即可） |
| 保证 | best-effort，极端情况仍可能重复跑 | 全局只有一个进程会触发，天然只跑一次 |
| 复杂度 | 分布式锁的续期/防死锁/时钟问题都要理解 | 一份代码 / 一个部署单元 |

## 三、为什么拆调度器是首选：消灭问题 vs 解决问题

这是本篇的核心立场。两条路的本质区别，不在「省不省事」，而在**面对的问题根本不同**：

- **路 A 是「解决共识问题」**：承认有 N 个对等副本，引入一个外部存储（Redis）去仲裁「这次谁跑」。这需要分布式共识——而共识很难做对（[06](./06-分布式共识-选主仲裁与不重复的本质.md) 会讲透 Redis 锁为什么只是 best-effort）。
- **路 B 是「消灭共识问题」**：干脆让 N=1。只有一个进程，不存在「谁跑」的争议，连仲裁都不需要，纯内存的 robfig/ticker 就够。

对中小项目，**消灭问题永远优于解决问题**。你不需要理解分布式锁的续期、防死锁、时钟偏移，不需要多运维一个 Redis 的强一致性，只需要一个 `replicas: 1` 的部署声明。gocron 的 Locker/Elector 解决的正是「我不想拆、就想让挤在一起的多副本靠 Redis 协调成一个」这个前提——你一旦选路 B，这个前提不存在，gocron 的招牌功能也就归零。

**什么时候路 A 才有意义？** 当你有大量定时任务、单个调度器进程触发不过来、需要把任务分摊到多个调度节点时——但那已经是「吞吐/规模轴」的问题了（见 [01](./01-任务调度全景-两根正交轴与知识地图.md) 两根轴、[07](./07-一致性哈希与分片调度.md) 分片调度），中小项目几乎到不了。

## 四、边界：拆调度器无 HA

路 B 唯一的代价（与选库无关）：调度器单副本**没有高可用**——它重启/发布那几秒正好到点，这一次触发会漏。

- 周期维护任务（清理、拉配置、统计）漏一次下次补上即可，无所谓。
- **如果「漏一次都不行」**——那不是 cron 库的问题，也不是拆不拆的问题，是你需要**持久化 + 崩溃恢复**：任务落库、崩溃重启后能接着跑。这是持久队列 River 的活，见 [02](./02-单机执行模型-从ticker到持久队列的四档.md) 第四档，和选 robfig 还是 gocron 完全无关。

换句话说：**路 B 的「无 HA」缺口，正确的补法是 River（可靠性轴往上走），而不是退回路 A 的 Redis 锁**（那只是把「跑几遍」的协调做成 best-effort，并不解决「崩溃丢任务」）。别把两个问题混为一谈。

## 五、best-effort 的定位：本篇只下结论，根因留给 06

路 A 的 Redis 锁是 best-effort，本篇只需记住这个**结论**并据此决策（有副作用的任务要幂等、严格一次上 River）。至于**为什么** Redis `SETNX` 锁做不到严格一次、而 etcd/ZK/Postgres 这些「天然多副本安全」的系统能——那是分布式共识的话题，[06](./06-分布式共识-选主仲裁与不重复的本质.md) 专门讲：

- best-effort 的**事实**（gocron Locker 是 best-effort）→ 已在本篇路 A 记下；
- best-effort 的**架构应用**（所以中小项目优先拆调度器绕开它）→ 本篇第三节；
- best-effort 的**根因**（Redis 非共识系统、无 fencing、主从切换 split-brain）→ [06](./06-分布式共识-选主仲裁与不重复的本质.md)。

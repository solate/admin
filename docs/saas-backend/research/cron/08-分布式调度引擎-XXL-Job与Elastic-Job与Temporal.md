# 分布式调度引擎：XXL-Job、Elastic-Job 与 Temporal

> 2026-07。本文回答系列的最后一问——**当单机调度器、拆调度器、持久队列都不够时，成熟的「分布式调度引擎」（XXL-Job / Elastic-Job / Temporal）在做什么、各自什么范式、什么时候才真需要它？**
>
> 结论先行：**分布式调度引擎不是升级链的顶端，而是「吞吐/规模轴」末端的岔路。** 它解决的是「job 多到 / 重到一个节点算不完，要把任务打散到几十个节点」这个**扩展**问题——而这个问题多数中小项目一辈子遇不到。绝大多数「后台任务」的真实需求是「可靠性」（不丢、重试、崩溃恢复），那是持久队列（River，见 [02](./02-单机执行模型-从ticker到持久队列的四档.md)）的活，不是分布式引擎。**引它之前先自查：你是撞上了吞吐墙，还是只是把可靠性需求误当成了规模需求？**
>
> 关联：本文是 [01](./01-任务调度全景-两根正交轴与知识地图.md) 「吞吐/规模轴」的终点展开；Elastic-Job 的两大支柱——选主用共识（见 [06](./06-分布式共识-选主仲裁与不重复的本质.md)）、分片用一致性哈希（见 [07](./07-一致性哈希与分片调度.md)）——在前两篇已铺垫；「可靠性轴」的终点 River 见 [02](./02-单机执行模型-从ticker到持久队列的四档.md)。
>
> 日常不必读；被「要不要上 XXL-Job / Temporal」这类问题绊住、或想搞清它们和前面几档什么关系时看这里。

## 一、先自查：你真的需要分布式调度引擎吗

这是本文最重要的一节。**分布式调度引擎是重型基建**（引入并运维一套中心调度器 + 执行器集群 + 依赖 ZK/DB/存储），上它之前必须先分清你撞上的是哪一堵墙——这两堵墙在 [01](./01-任务调度全景-两根正交轴与知识地图.md) 的「两根正交轴」里已经立过：

| 你的真实痛点 | 在哪根轴上 | 该上什么 |
|---|---|---|
| 任务不能丢、要重试、崩溃要恢复 | **可靠性轴** | 持久队列 River（[02](./02-单机执行模型-从ticker到持久队列的四档.md)），**不是**分布式引擎 |
| 多副本下别重复跑 | 协调面 | 拆调度器 `replicas:1`（[05](./05-从单机到多节点-重复跑与拆调度器.md)），够不着引擎 |
| job 数量/单个耗时大到**一个节点算不完** | **吞吐/规模轴** | 这才是分布式调度引擎的战场 |

**最常见的误判**：把「可靠性问题」当成「规模问题」。「我的任务很重要不能丢，所以要上 XXL-Job」——错。不能丢是可靠性，River 用一个 PG 就解决了；XXL-Job 也不会让你的任务更「不丢」（它的可靠性来自 DB 存元数据 + 重试，本质和 River 同源，却多背了一整套中心调度器）。

**真正需要引擎的信号**（吞吐轴走到尽头）：
- job 数量到**十万/百万级**，单个节点的调度循环 + 执行都扛不住；
- 单个 job 是**重计算**（跑几分钟到几小时），必须**横向拆到多个节点并行**才能在窗口内跑完（典型：对账、大批量数据处理）；
- 需要**跨语言/跨服务**统一调度（一个中心台管所有业务线的定时任务，带 web 界面、手动触发、执行历史）。

**99% 的中小项目止步于「拆调度器 + River」**——单点触发一秒钟跑完，没有吞吐问题；要不丢就上 River。只有当你确认自己在吞吐轴上撞了墙，才往下读。

## 二、XXL-Job：中心调度 + 执行器分离

[XXL-Job](https://github.com/xuxueli/xxl-job) 是国内使用极广的分布式任务调度平台，架构是**「调度中心」与「执行器」分离**：

- **调度中心（xxl-job-admin）**：一个带 web 界面的中心服务，负责「到点了」这个决策、任务的增删改查、执行日志、手动触发、失败告警。元数据（任务定义、执行记录、锁）存在 **MySQL**。
- **执行器（业务侧）**：业务服务内嵌一个 xxl-job SDK，注册到调度中心。到点后调度中心通过 HTTP 把任务**派发**给执行器集群里的某个/某些节点执行。

**多副本安全怎么保证**：调度中心自己也可以多实例部署，靠 **MySQL 悲观锁/行锁**保证「同一个任务同一时刻只有一个调度中心实例触发」——本质是把「谁来触发」的仲裁托管给数据库（回扣 [06](./06-分布式共识-选主仲裁与不重复的本质.md)：用 DB 的原子性代替自搓共识）。触发决策是**集中**的，所以「不重复触发」相对好保证。

**路由策略**（触发后派给哪个执行器）：轮询 / 随机 / 一致性哈希（同一 job 固定打到同一执行器，利于本地缓存）/ 故障转移 / **分片广播**（把 job 拆成 N 片，每个执行器跑一片，见下）。

**分片广播**是 XXL-Job 处理「单 job 太重」的手段：调度中心给每个执行器实例传一个 `(分片序号, 分片总数)`，执行器按这个自己认领数据的一部分（如 `WHERE id % total = index`）。这是「把重计算横向拆开」的典型，也是吞吐轴的核心能力。

**定位与优缺点**：
- ✅ 中心化管理、web 界面、执行历史、手动触发/重试、告警——**运维友好**，对「要一个统一台子管全公司定时任务」的场景很顺手。
- ✅ 触发集中，不重复触发好保证。
- ⚠️ 需要**独立部署运维调度中心 + MySQL**，是实打实的基建成本。
- ⚠️ 触发靠 HTTP 派发，调度中心与执行器之间有网络耦合。

## 三、Elastic-Job：去中心 + ZooKeeper 选主 + 一致性哈希分片

[Elastic-Job](https://github.com/apache/shardingsphere-elasticjob)（现属 Apache ShardingSphere）走的是**去中心化**路线，没有独立的中心调度服务，调度逻辑内嵌在每个业务节点里，用 **ZooKeeper** 做协调中枢。它恰好把本系列前两篇的两个概念都用上了：

- **选主(leader election)用共识**：多个业务节点通过 ZooKeeper（ZAB 共识，见 [06](./06-分布式共识-选主仲裁与不重复的本质.md)）选出一个 leader，由 leader 负责**计算分片分配表**（哪个节点负责哪几片）。ZK 保证所有节点对「现在有哪些节点、谁是 leader」有一致视图——这正是 [07](./07-一致性哈希与分片调度.md) 第五节强调的「分片必须垫一层共识做成员管理，否则视图不一致会重复认领」。
- **分片(sharding)用一致性哈希思想**：把一个逻辑 job 拆成 N 个分片项，按分片规则分给各节点。节点增减时 ZK 触发**重分片(rebalance)**，只迁移受影响的分片——这就是 [07](./07-一致性哈希与分片调度.md) 讲的「节点变动只重排一部分」。

**作业分片模型**：你声明一个 job「分 4 片」，Elastic-Job 通过 ZK 把 `{0,1,2,3}` 分给当前存活的节点（比如 2 个节点各拿 2 片）。每个节点在自己的分片项上跑业务逻辑（`switch shardingItem { case 0: ... }`）。加一个节点，ZK 重新分配成 3 节点各拿 1~2 片。

**定位与优缺点**：
- ✅ 去中心、无单独调度服务；分片能力原生，适合「单 job 拆多片并行」的重计算。
- ✅ 弹性伸缩：加减节点自动 rebalance。
- ⚠️ **强依赖 ZooKeeper**——多一套要运维的强一致组件（ZK 本身要集群部署保证 HA）。
- ⚠️ 概念比 XXL-Job 重（分片项、分片策略、作业类型），学习曲线陡。

## 四、Temporal / Cadence：工作流引擎，另一种范式

[Temporal](https://temporal.io/)（源自 Uber 的 [Cadence](https://github.com/cadence-workflow/cadence)）和前两者**本质不同**——它不是「定时触发器」，而是**持久化工作流引擎(durable execution)**。放进本文是因为它常被拿来和「分布式调度」并列，但要讲清它解决的是另一维问题：

- **XXL-Job / Elastic-Job**：面向「**定时触发**一个（可分片的）任务」，核心是「何时跑 + 派给谁 + 怎么分片」。
- **Temporal**：面向「**编排一个长流程**」——一个业务流程有多个步骤（调 A、等审批、调 B、失败补偿），可能跨天跨周，中间任何一步崩溃都要能**从断点精确恢复**。

**durable execution 的核心机制**：Temporal 把工作流的**每一步执行结果都持久化**（event sourcing——记录事件日志），进程崩溃/重启后通过**重放(replay)**事件日志把工作流状态恢复到崩溃前那一刻，接着往下跑。你的工作流代码写得像普通顺序代码（`a(); approve(); b()`），但每个 `await` 点的状态都落了库，天然崩溃可恢复、天然多副本安全（状态在 Temporal server 的存储里，worker 无状态）。

**什么时候才是 Temporal 的场景**：多步骤、长周期、要精确断点恢复、要补偿(saga)的**业务流程编排**——如订单履约、跨系统数据迁移、审批流。**它对「每天凌晨 2 点清一次表」这种单步定时任务是杀鸡用牛刀**（虽然它也能定时触发工作流）。

**成本**：Temporal 是重型基建——要部署 Temporal server 集群 + 持久化存储（Cassandra/PostgreSQL/MySQL）+ 可见性存储（Elasticsearch 可选）。对中小项目而言，除非真有复杂长流程编排需求，否则严重过重。

## 五、横向对比

| 维度 | XXL-Job | Elastic-Job | Temporal | 对照：River（[02](./02-单机执行模型-从ticker到持久队列的四档.md)） |
|------|---------|-------------|----------|------|
| 范式 | 中心调度 + 执行器 | 去中心 + 分片 | 工作流编排(durable execution) | 持久队列 |
| 主要解决 | 统一管理 + 分片 | 单 job 分片并行 | 长流程断点恢复 | 必达 + 重试 + 事务性入队 |
| 在哪根轴 | 吞吐/规模 | 吞吐/规模 | 可靠性 + 编排 | 可靠性 |
| 协调机制 | MySQL 锁 | ZooKeeper 选主 | 内部共识 + 事件日志 | PG advisory lock |
| 分片 | 分片广播 | 原生作业分片 | 无（编排非分片） | 无 |
| 触发 | cron，中心触发 | cron，节点自调度 | 支持定时启动工作流 | 周期任务 + 按需入队 |
| 新基建 | 调度中心 + MySQL | ZooKeeper 集群 | Temporal 集群 + 存储 | 无（复用栈内 PG） |
| 运维成本 | 中 | 中高（ZK） | 高 | 低 |
| 适用规模 | 中大型、多业务线 | 大型、重计算分片 | 复杂长流程 | 中小型通用 |

## 六、钉回两根轴：它们不是「gocron 的下一级」

回到 [01](./01-任务调度全景-两根正交轴与知识地图.md) 的核心框架，把本文三个引擎钉回坐标，破掉「线性升级链」的错觉：

- **XXL-Job / Elastic-Job 坐在「吞吐/规模轴」的末端**——它们的价值是「把海量/重 job 分片到多节点」。如果你没有吞吐问题，它们相对拆调度器 + River **没有任何净收益**，只有多背一套基建的净亏损。
- **Temporal 跨在「可靠性轴 + 编排」维度**——它不是「更强的定时器」，是「持久化的流程引擎」。拿它当 cron 用是错配。
- **它们都不是「gocron / robfig 的下一级」**——不存在「gocron 不够了就升 XXL-Job」这条线。gocron 是单机触发库，撞墙时的下一步取决于你撞的是哪堵墙：可靠性墙 → River；重复跑墙 → 拆调度器；真·吞吐墙 → 才轮到这些引擎。

**一句话**：分布式调度引擎是「吞吐/规模轴」的专用重型工具，不是通用升级终点。先用 [01](./01-任务调度全景-两根正交轴与知识地图.md) 的两根轴定位你的真实痛点——绝大多数「后台任务」需求，答案是 River 或拆调度器，而不是这里的任何一个引擎。

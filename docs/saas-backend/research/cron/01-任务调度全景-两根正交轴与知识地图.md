# 任务调度全景：两根正交轴与知识地图

> 2026-07。本文是「任务调度」系列的门户——**从单机 cron、库选型，到多节点重复跑、共识、一致性哈希，再到时间轮、分布式调度引擎，这些东西各自解决什么、彼此什么关系？**
>
> 结论先行：**任务调度不是一条线性升级链，而是两根正交的轴 + 若干各管一段的技术。** 一根是「可靠性轴」（任务丢不丢得起：可丢 → 必达），一根是「吞吐/规模轴」（一个节点触发/执行够不够：够 → 海量 job 算不完）。绝大多数项目只在可靠性轴上走，终点是持久队列（River）；吞吐轴的终点（分布式调度引擎）是**岔路、不是顶点**，海量 job 才需要。三个高频误解要先钉死：**时间轮**是单机数据结构（性能优化）、**一致性哈希**是分片手段（不保证不重复）、**「只跑一个」的本质是共识**（不是加把锁）——这三件事互相正交，别混成一锅。
>

>
> 日常写代码不必读；想系统理解「任务调度这一大摊子」或纠结「是不是该上某个重方案」时，从这篇入门。

## 一、任务调度是三件独立的事

「任务调度」是个过载词，实际至少揉了三个正交的问题。分不清它们，就会把「时间轮 / 一致性哈希 / 分布式锁 / 持久队列」这些不同层面的东西错误地串成一条升级链。

| 子问题 | 解决什么 | 典型手段 | 归属篇 |
|---|---|---|---|
| **触发（何时跑）** | 到点、按间隔、按 cron 表达式把任务拉起来 | `time.Ticker`、robfig/cron、gocron、时间轮（底层数据结构） | 02 / 03 / 04 |
| **协调（谁来跑 / 跑几遍）** | 多个进程同时在跑时，保证「只有一个执行」 | 拆调度器单副本、分布式锁、共识/选主、一致性哈希分片 | 05 / 06 / 07 |
| **执行保证（丢不丢）** | 崩溃/重启不丢任务、失败重试、恰好一次 | 持久队列（River/asynq）、事务性入队、幂等 | 02 / 06 |

一句话记住：**触发是「闹钟」，协调是「几个闹钟别同时响」，执行保证是「响了必须有人应」**。三者可以独立组合——单机单副本只需要「触发」；多副本才引出「协调」；关键任务才引出「执行保证」。

## 二、两根正交轴（全系列的组织框架）

把上面三件事再压缩，会得到两根决定「该用多重方案」的**正交轴**。任何一个调度方案都能钉在这张二维图上。

**可靠性轴（任务丢不丢得起）**：

```
可丢（下次再跑即可） ─────────────────────────► 必达（崩溃不丢 / 重试 / 恰好一次）
  time.Ticker          gocron / robfig            River（持久队列）
```

**吞吐/规模轴（一个节点够不够）**：

```
单点触发够用 ──────────────────────────────► 海量 job，一个节点触发/算不完
  单进程调度器          拆调度器单副本            分布式调度引擎（XXL-Job/Elastic-Job）
```

两根轴正交，任一方案的坐标：

| 方案 | 可靠性轴位置 | 吞吐轴位置 | 说明 |
|---|---|---|---|
| `time.Ticker` | 可丢 | 单点 | 零依赖地板 |
| robfig / gocron | 可丢（内存态） | 单点 | 进程内调度器 |
| 拆调度器 `replicas:1` | 可丢 | 单点（有意约束成 1） | 用架构消灭「多副本协调」问题 |
| River | **必达** | 单点~中等 | 持久队列，崩溃恢复 |
| XXL-Job / Elastic-Job | 看配置 | **海量** | 分片到多节点，吞吐轴终点 |
| Temporal / Cadence | 必达 | 中~大 | 工作流编排，跨两轴 |

**最重要的一条心智**：**分布式调度引擎不是「gocron 的下一级」**。它在吞吐轴的末端，解决「job 多到一个节点算不完」；而绝大多数业务的真实需求（崩溃不丢）在可靠性轴上，终点是 River。把「可靠性需求」误当「规模需求」去上分布式引擎，是最常见的过度设计。详见 [08](./08-分布式调度引擎-XXL-Job与Elastic-Job与Temporal.md)。

## 三、先纠正三个高频误解

这三个概念常被混为「让任务调度更强大/更分布式」的同类项，其实各管一段、互相正交。这里给速览，详情各有专篇。

**误解 1：时间轮是分布式/多副本方案。**
错。时间轮（timing wheel）是**单机内**管理海量定时器的数据结构，把定时器的插入/删除/到期扫描从最小堆的 O(log n) 降到 O(1)。它是**性能优化**，和「多副本会不会重复跑」完全正交——单机 gocron 里可以用时间轮，一样不解决多副本。Kafka/Netty 用它是为了单机扛百万定时器，不是为了多副本安全。详见 [04](./04-时间轮-单机海量定时器的数据结构.md)。

**误解 2：一致性哈希保证数据一致 / 不重复跑。**
错。一致性哈希（consistent hashing）名字里的「一致」是历史误译，它保证的是**节点增减时映射的稳定性**（只迁移约 1/N 的 key），是**负载分片**手段。它既不是 CAP 里的 consistency，也不保证「同一任务不被两个节点同时跑」——不重复永远靠共识 + fencing + 幂等。详见 [07](./07-一致性哈希与分片调度.md)。

**误解 3：「只跑一个」靠加把锁就行。**
不够。「N 个对等副本，此刻谁来跑」本质是**分布式共识问题**。etcd/ZooKeeper/Kafka/Postgres 能做到「天然只跑一个」，是因为它们内部用 Raft/ZAB/ACID 把共识解决了；而 Redis `SETNX` 不是共识系统，主从切换会 split-brain、锁续期有竞态，只能是 **best-effort**。详见 [06](./06-分布式共识-选主仲裁与不重复的本质.md)。

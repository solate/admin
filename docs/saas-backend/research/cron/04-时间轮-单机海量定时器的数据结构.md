# 时间轮：单机海量定时器的数据结构

> 2026-07。本文回答一个**原理层**问题——一个进程里要同时管理成千上万乃至百万个定时器（每个连接一个超时、每条消息一个延迟投递），调度器底层用什么数据结构才高效？这就是**时间轮（timing wheel）**。
>
> 结论先行：**时间轮是一种单机内的数据结构，把定时器的插入/删除/到期扫描从最小堆的 O(log n) 降到均摊 O(1)。它解决的是「一个进程里多快能调度海量定时器」这个性能问题，和「多副本会不会重复跑」完全正交——它不是分布式方案，别把它当协调手段。** 业务 cron（几个到几十个周期任务）根本用不到时间轮，robfig/gocron 底层用的也不是它。
>
> 关联：本文是 [01](./01-任务调度全景-两根正交轴与知识地图.md) 知识地图里「触发层性能」的深挖，属单机段收尾；「跑几遍」的协调问题见 [05](./05-从单机到多节点-重复跑与拆调度器.md) 与 [06](./06-分布式共识-选主仲裁与不重复的本质.md)。
>
> 日常不必读；好奇 Kafka/Netty 的延迟队列底层、或被「时间轮能解决多副本」之类说法搞混时看这里。

## 一、问题：海量定时器怎么存

「定时器」的核心操作有三个：**添加**一个「T 秒后触发」的任务、**取消**一个还没触发的任务、每个时刻**找出所有到期**的任务执行。

最直觉的实现是**最小堆/优先队列**（按到期时间排序）：

- 添加：O(log n)——插入并上浮。
- 取消：O(log n)——删除并调整。
- 取最近到期：O(1) 看堆顶，弹出 O(log n)。

n 是几十、几百时，O(log n) 毫无压力——**这正是业务 cron 的量级，最小堆绰绰有余**。但当 n 到几十万、上百万（比如网络框架里「每个 TCP 连接一个空闲超时」、消息队列里「每条延迟消息一个投递定时器」），每次增删都 O(log n)、且频繁增删，堆调整的开销就变得可观。时间轮就是为这个量级设计的。

## 二、时间轮原理：环形数组 + 指针

时间轮借用钟表的比喻：一个**环形数组**，每个格子（slot/bucket）代表一个时间单位（tick，比如 1 秒），一根**指针**每 tick 前进一格，走到头绕回开头。

- **数组有 N 个格子**，每格挂一个链表，存「将在这一格到期的所有任务」。
- **添加任务**：算出它在几个 tick 后到期，`slot = (当前指针 + delay) % N`，直接挂到那个格子的链表——**O(1)**，不需要和其他任务比较排序。
- **取消任务**：从链表摘掉——**O(1)**（配合一个 `任务 → 节点` 的 map）。
- **推进**：指针每 tick 前进一格，取出当前格链表里的所有任务执行——**均摊 O(1)**，不用扫描整个结构找「谁到期了」。

对比最小堆：时间轮用「**空间换比较**」——不排序，靠「到期时间 → 数组下标」的直接映射定位，把 log n 的比较开销消掉了。代价是精度受 tick 粒度限制（1 秒的轮做不了毫秒级），以及超过一圈的延迟需要额外处理（见下）。

## 三、分层时间轮：解决时间跨度 vs 精度

单层时间轮有个矛盾：**格子数有限，覆盖的时间跨度 = 格子数 × tick**。要精度高（tick=1s）又要跨度大（能表达「7 天后」），单层就得开 60 万个格子——浪费。

**分层时间轮（hierarchical timing wheel）**照搬钟表的时/分/秒三针：

- 第一层：秒轮，60 格，tick=1s，覆盖 1 分钟。
- 第二层：分轮，60 格，tick=1min，覆盖 1 小时。
- 第三层：时轮，24 格，tick=1h，覆盖 1 天。
- ……

一个「1 小时 23 分 5 秒后」的任务先挂在时轮。当时轮指针推进到它那一格，把它**降级**重新分配到分轮（还剩 23 分 5 秒）；分轮推进到那格再降级到秒轮（还剩 5 秒）；秒轮到点才真正触发。这样**少量格子就能覆盖很大跨度**，且保持底层精度。Kafka 的时间轮就是这种多层结构 + 溢出时动态加更高层。

## 四、工业实现

时间轮不是学术玩具，主流基础设施里到处是它：

- **Kafka**：`DelayedOperationPurgatory`（延迟操作管理，如 producer acks 超时、fetch 等待）底层是分层时间轮 + `DelayQueue` 推进。管理海量延迟操作正是它的场景。
- **Netty**：`HashedWheelTimer`——单层哈希时间轮，用于海量连接的空闲检测、请求超时。Netty 文档明确说它适合「大量超时任务、但精度要求不高」，且提醒 tick 粒度和轮大小要按场景调。
- **Linux 内核**：内核定时器（`timer_list`）历史上就是多级时间轮（cascading timing wheel）管理内核态海量定时器。
- **Go 生态**：`time.Timer`/`time.Ticker` 底层是运行时的**四叉最小堆**（per-P timer heap），**不是**时间轮——所以 robfig/gocron 这类基于 `time.Timer` 的调度器底层也是堆。Go 社区有独立的时间轮库（如 `RussellLuo/timingwheel`），但标准库没走这条路，因为 Go 程序里定时器数量通常不到需要时间轮的量级。

## 五、和本系列前几篇的关系

把时间轮放回知识地图（[01](./01-任务调度全景-两根正交轴与知识地图.md)）：它坐在**触发层的最底下**，是「到点触发」这件事的一种高性能实现。

- **robfig/cron、gocron（[03](./03-cron库选型-robfig与gocron对比.md)）底层不是时间轮**，是 `time.Timer`（最小堆）。因为业务 cron 是几十个任务的量级，堆足够快，没必要上时间轮。
- **时间轮只在「单机高吞吐定时器」场景才需要**：网络框架的连接超时、消息队列的延迟投递，这些是几十万上百万定时器、且增删极频繁。业务后台的周期任务永远到不了这个量级。
- 所以：**你写 admin 后台的定时任务，不需要关心时间轮**。了解它是为了理解 Kafka/Netty 这类基础设施的底层，以及——破除下面这个常见误解。

## 六、关键澄清：时间轮 ≠ 多副本协调

这是本篇最重要的一句，也是很多人被搞混的点：

**时间轮解决的是「一个进程内，多快能管理和触发海量定时器」——纯粹的单机性能问题。它和「多个副本会不会把同一个任务跑多遍」毫无关系。**

- 你在单机 gocron 里可以用时间轮，一样是纯内存、一样在多副本下每个副本各跑一次。
- Kafka 能多副本安全，**靠的不是时间轮**，是它的分区独占 + controller 选主（共识，见 [06](./06-分布式共识-选主仲裁与不重复的本质.md)）；时间轮只是每个 broker 进程内管理延迟操作的数据结构。

所以「用了时间轮就能多副本」这个因果**根本不成立**。时间轮回答「多快」，不回答「跑几遍」。「跑几遍」是[05](./05-从单机到多节点-重复跑与拆调度器.md)（拆调度器）和 [06](./06-分布式共识-选主仲裁与不重复的本质.md)（共识）的题目，和数据结构无关。

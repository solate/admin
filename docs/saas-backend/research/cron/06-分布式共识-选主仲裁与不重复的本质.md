# 分布式共识：选主、仲裁与「不重复」的本质

> 2026-07。本文回答一个被 [05](./05-从单机到多节点-重复跑与拆调度器.md) 留下的根因问题——**为什么 Redis `SETNX` 锁只是 best-effort，而 etcd / ZooKeeper / Postgres 这些系统「天然多副本安全」？「让多副本只跑一个」到底难在哪？**
>
> 结论先行：**「多副本只跑一个」的本质是一个分布式共识问题**——N 个对等进程要就「这次谁跑」达成一致。共识很难，所以别自己搓；etcd/ZK/Kafka/Postgres 之所以「天然多副本」，是它们内部已用 Raft/ZAB/ACID 把共识解决了，你把「谁来跑 + 状态存哪」外置给它们，就继承了它们的保证。**「不重复」= 共识（选出唯一 owner）+ fencing token（挡住过期 owner）+ 幂等（兜底），三者缺一不可。** Redis `SETNX` 不是共识系统——单点、无 fencing、主从切换会 split-brain——所以只能是 best-effort。
>
> 关联：本文是 [05](./05-从单机到多节点-重复跑与拆调度器.md) 里「best-effort」的根因展开，也是 [01](./01-任务调度全景-两根正交轴与知识地图.md) 三个误解里「只跑一个 ≠ 加把锁」的主场。这些原理支撑了 [02](./02-单机执行模型-从ticker到持久队列的四档.md) River 的 leader 选举，也会在 [08](./08-分布式调度引擎-XXL-Job与Elastic-Job与Temporal.md) 的 Elastic-Job 里复现。
>
> 日常不必读；想搞懂「分布式锁为什么不可靠 / 为什么某些系统能天然多副本」时看这里。

## 一、问题重述：从「best-effort」到「什么才是真的只跑一次」

[05](./05-从单机到多节点-重复跑与拆调度器.md) 里我们下了个结论：gocron 的 Redis Locker 是 best-effort，不保证严格一次。本篇要回答的是**为什么**——以及，如果真要「严格一次」，靠什么。

先把问题抽象干净：N 个对等进程（副本），到了同一时刻都想执行同一个任务，我们要让**其中恰好一个**真正执行。这看起来只是「加把锁」，但它其实是分布式系统里最难的一类问题——**共识（consensus）**：多个节点要对「谁是那个唯一」达成一致的判断，且这个判断在节点崩溃、网络分区、消息延迟的情况下依然正确。

## 二、共识算法速览：Paxos / Raft / ZAB

共识算法解决的核心问题是：**一组节点如何对某个值达成一致，即使部分节点故障或网络不可靠。**

- **Paxos**（Lamport, 1998）：理论奠基，正确但难懂难实现。
- **Raft**（2014）：为「可理解性」重新设计，把共识拆成 leader 选举 + 日志复制 + 安全性三块。etcd、Consul、TiKV 都用它。
- **ZAB**（ZooKeeper Atomic Broadcast）：ZooKeeper 的共识协议，思路与 Raft 相近（原子广播 + 崩溃恢复）。

它们的共同保证：**在多数派（quorum，> N/2 节点）存活时，系统对「当前值 / 当前 leader」有唯一且线性化的答案。** 关键词是「多数派」——共识不依赖任何单个节点存活，这正是它区别于「单点 Redis 锁」的根本。

对任务调度，我们不需要自己实现共识，只需要用它派生出的一个能力：**选主（leader election）**。

## 三、选主与 fencing token：「不重复」的三件套

「让多副本只跑一个」落到工程上，是三件事的叠加，缺一不可：

**1. 共识选出唯一 owner。** 通过 Raft/ZAB 或数据库原子操作，选出一个 leader（或某任务的锁持有者）。共识保证同一时刻**至多一个** owner。

**2. Fencing token 挡住「过期的 owner」。** 这是最容易被忽略、也是 Redis 锁最致命的缺口。设想：副本 A 拿到锁，然后它 GC 停顿了 10 秒（或网络分区），锁 TTL 到期被释放，副本 B 拿到锁开始跑。此时 A 从停顿中恢复，**它并不知道自己的锁已过期**，继续往下写——于是 A 和 B 同时在跑。

Fencing token 的解法：每次授予锁都附带一个**单调递增的序号**（token）。B 拿到的 token 比 A 大。下游存储（DB / 文件系统）只接受「token 不小于已见过的最大值」的写入——A 带着旧 token 来写，被存储拒绝。这样即使 A 误以为自己还持有锁，它的写也无效。**没有 fencing token 的锁，本质上都无法防住这种「过期持有者」竞态。**

**3. 幂等兜底。** 即便前两者到位，工程上仍建议任务幂等（用 `execution_id` 去重表、`INSERT ... ON CONFLICT`）。共识 + fencing 把重复压到极低概率，幂等则让「万一重复」也无害。这也是为什么 [05](./05-从单机到多节点-重复跑与拆调度器.md) 反复强调「有副作用的任务该幂等还得幂等」。

**一句话：不重复 = 共识（选唯一）+ fencing（挡过期）+ 幂等（兜底）。** 只做第一步（比如裸 Redis 锁），就是 best-effort。

## 四、为什么 etcd / ZK / Kafka / Postgres「天然多副本」

理解了三件套，就能看清这些系统「天然多副本安全」的共同套路：**副本自己保持无状态、对等，把「谁来跑 + 状态存哪」外置到一个内部已解决共识的强一致存储。**

| 系统 | 共识/原子原语 | 怎么仲裁出「只有一个」 |
|---|---|---|
| **etcd** | Raft | 内建 leader election；`CAS`（compare-and-swap）+ `lease`（带 TTL 的租约，续约由多数派共识保证）+ revision 号做 fencing |
| **ZooKeeper** | ZAB | 临时有序节点（ephemeral sequential）+ watch 实现选主；zxid 单调递增天然是 fencing token |
| **Kafka** | 副本 ISR 日志 + controller（KRaft/Raft） | 一个 partition 在一个消费组里**只分配给一个消费者**（单一 owner）；controller 负责分配 |
| **Postgres** | ACID 事务 + advisory lock / `SELECT FOR UPDATE SKIP LOCKED` | 单写者串行化：leader 选举用 advisory lock，任务领取用行锁，数据库保证同一行只被一个 worker 抢到 |

共同点一句话：**「只有一个跑」这个不变量，不是靠副本之间互相商量，而是靠一个提供了原子/线性化操作的外部存储来裁决。** 副本只管去问它「我能跑吗」，存储原子地回答「能/不能」，并用序号/revision 挡住过期请求。

这也解释了为什么「天然多副本」往往**同时**给了两个东西：**协调**（谁来跑，靠共识原语）+ **持久化**（状态在外部存储，副本崩了状态还在，别的副本接着跑）。这两个属性的绑定，正是 [02](./02-单机执行模型-从ticker到持久队列的四档.md) 里 River「多副本天然安全」的来源。

## 五、Redis SETNX 为什么不是真共识

回到最初的问题。Redis `SETNX`（或 `SET NX EX`）做锁，缺的正是上面几条：

1. **单点，不是多数派共识。** 单实例 Redis 挂了，锁信息全丢。它的「原子」只是单机命令原子，不是分布式共识。
2. **无 fencing token。** `SETNX` 返回的是「成功/失败」，没有单调序号。第三节那个「A 停顿 → 锁过期 → B 拿锁 → A 恢复继续写」的竞态，Redis 锁无法防。
3. **主从切换 split-brain。** 生产 Redis 多是主从 + Sentinel。主写入锁后、还没同步到从就宕机，Sentinel 把从提为主——新主上没有这把锁，另一个副本又拿到了。**两个副本同时持锁**。
4. **锁靠时钟 TTL。** 续期依赖客户端时钟和网络，时钟漂移或续期消息延迟都会让锁提前失效或迟迟不放。

**Redlock 的争议**：Redis 作者提出 Redlock（多个独立 Redis 实例投票）试图补强，但 Martin Kleppmann 有著名的批评——Redlock 依赖「时钟不漂移」和「进程不长时间停顿」这类不安全假设，且仍无 fencing token，无法在异步网络模型下证明正确。结论：**要严格正确的分布式锁，用带 fencing 的共识系统（etcd/ZK）或数据库，而不是 Redis。**

这就是「为什么 etcd 直接能多副本、Redis 锁却只能 best-effort」的根因——**多数派共识 + fencing vs 单点原子命令，不是一个量级。**

## 六、回扣：本系列各方案站在共识谱系的哪一档

把前面的方案钉回这根谱系，就看清了它们的可靠性梯度：

- **裸 Redis `SETNX` / gocron Redis Locker**（[05](./05-从单机到多节点-重复跑与拆调度器.md) 路 A）——单点原子命令，无 fencing，best-effort。适合幂等任务去重，不适合严格一次。
- **gocron Elector 接 etcd**（[03](./03-cron库选型-robfig与gocron对比.md) 能力表）——若后端换成 etcd，选主本身有共识保证；但 gocron 层面是否用了 fencing token 下沉到业务写入，仍需自行确认。接口可换后端是它的优点。
- **River 的 PG advisory lock leader**（[02](./02-单机执行模型-从ticker到持久队列的四档.md) 第四档）——leader 选举 + 任务领取都靠 Postgres 的 ACID 与行锁，`FOR UPDATE SKIP LOCKED` 保证同一行只被一个 worker 抢到，是数据库级的强一致。这是为什么 River「多副本天然安全」。
- **拆调度器 `replicas:1`**（[05](./05-从单机到多节点-重复跑与拆调度器.md) 路 B）——**根本不进入这根谱系**：只有一个进程，没有「谁跑」的争议，连共识都不需要。这正是它对中小项目最优的原因。

**最实用的一条**：绝大多数中小项目，与其纠结「我的分布式锁够不够强」，不如用「拆调度器 `replicas:1`」让这个问题消失。真需要共识级保证时，用已经把共识做对的系统（Postgres/River、etcd），而不是自己在 Redis 上搓。

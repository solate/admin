# 为什么需要 Redis：进程内缓存 vs 集中式缓存

> 本篇（2026-07）不谈「用哪个 Redis 客户端库、怎么封装」（那是 [01-redis-客户端封装选型调研](./01-redis-客户端封装选型调研.md) 的题目），而回答更上游的一问：**这个项目到底为什么要引入 Redis？以前很多项目不用也跑得好好的，凭什么现在要多加一个组件？自己封装一个进程内 cache 不行吗？**
>
> 结论先摆这里：**本项目瞄准 k3s 多副本部署，Redis 是必选项**——不是因为「大家都用」，而是因为多副本一旦成立，JWT 黑名单 / 验证码 / 限流 / 分布式锁这几类状态就没有进程内的活路。唯一能留在进程内的是权限缓存（读极多、DB 是真相源、秒级延迟可接受），但它的跨副本刷新协调仍要借 Redis。本篇把这套「什么状态放哪里」的决策框架讲透，并对齐成熟团队的真实做法。

## 一、背景与困惑

用户的原始困惑，逐条摆出来：

1. **以前的项目不用 Redis 也活得好好的，为什么现在要用？**
2. **多引入一个三方组件是有成本的**（要部署、要监控、要备份、要考虑它挂了怎么办），这个 payoff 到底在哪？
3. **不加 Redis，自己用 `sync.Map` / LRU 封装一个进程内 cache，会有什么问题？**
4. **成熟团队是怎么抉择的？** 有没有一套可依据的框架，而不是「感觉该上就上」。

这些困惑都是对的——**增加基础设施必须有明确 payoff，否则就是过度设计**。本篇不灌「Redis 很强你就该用」的鸡汤，而是给一把能自己判断的尺子。

### 本项目现状（诚实前提）

先说清楚现在代码是什么样，避免把「计划」说成「现状」：

- 整个 `backend/` 是**极早期脚手架**。`internal/` 下的 service / handler / middleware / rbac / repository 等目录**基本全空**，唯一建模的业务表是自动生成的 `system_config`。
- **Redis 只连上了、一行业务都没用**：`main.go` 建连探活后把 `*redis.Client` 存进 `server.rdb` 字段，**之后从未被读写**。
- `pkg/cache` **不存在**；规则文档里描述的 RBAC `PermissionCache`（内存加载 + 事件刷新）**代码未实现**（`internal/rbac/` 是空目录）；JWT 黑名单 / 验证码 / 限流 **全部不存在**。

所以本篇是一次**设计期选型**，不是对既有代码的重构——正好在动手写业务前把「状态该放哪」定下来。

### 为什么判断是「多副本」而非「单实例小项目」

Redis 的必要性几乎完全由「单副本 vs 多副本」决定，所以先确认部署形态。本项目有三处信号指向多副本：

- `internal/config/config.go` 注释提到 **k3s** 靠挂载覆盖配置——目标运行环境是 k8s 系。
- `go.mod` 引入了 `gorm.io/plugin/dbresolver`（读写分离）——在为规模化做准备。
- `pkg/xredis` 注释专门写了「上集群只需把 `NewClient` 换成 `NewUniversalClient`」——预留了集群迁移路径。

这三点合起来：**这不是一个跑单实例、图省事的内部小工具，而是奔着高可用 / 横向扩容去的 SaaS 后台**。这个判断是后面所有结论的地基。

## 二、根本差异：单副本 vs 多副本

这是整个决策的**第一个轴**。老项目不用 Redis 能活，新项目必须用，几乎都是这个轴决定的。

| | 单副本（老项目常态） | 多副本（k8s/k3s 标配） |
|---|---|---|
| **进程内状态是否安全** | ✅ 唯一进程，内存就是真相 | ❌ 每个 pod 独立进程，状态分裂 |
| **JWT 黑名单存 `sync.Map`** | ✅ 用户登出，撤销立即生效 | ❌ pod-A 撤销，pod-B 仍认 token 有效（**安全漏洞**） |
| **验证码存内存** | ✅ 生成→校验走同一进程 | ❌ 生成在 pod-A、校验落 pod-B → 验证码不存在（**用户无法登录**） |
| **限流计数器** | ✅ 本进程准确限流 | ❌ 每个 pod 独立计数 → 限流失效（配 10 req/min × 3 pods = 实际 30） |
| **分布式锁** | ✅ 单进程用 `sync.Mutex` | ❌ 每个 pod 内部锁，跨 pod 无互斥（**定时任务重复执行、脏写**） |
| **缓存一致性** | ✅ 更新立即对所有请求生效 | ⚠️ 各 pod 独立缓存，更新后其他 pod 仍读旧数据（**最终一致性问题**） |

**核心结论**：

- **单副本**：进程内状态就是全局状态，`sync.Map` / 全局变量是安全的。老项目跑单机 + 小流量 + 不追求高可用，所以不需要 Redis。
- **多副本**：每个 pod 是独立进程，进程内状态只在本 pod 可见。**任何需要跨副本即时一致的状态，必须放到外部共享存储**——Redis / Memcached / Etcd，选哪个看场景，但必须选一个。

这不是「Redis 比内存好」，而是**多副本下进程内状态根本做不到跨副本一致**。JWT 黑名单如果各 pod 独立存，用户在 pod-A 登出、下一个请求落 pod-B 仍能通过认证，这是安全事故级别的问题。

### 为什么老项目不用 Redis 也活得好

老项目不用 Redis 有两种原因：

1. **跑单副本**（最常见）：一台机器一个进程，流量不大、不追求高可用（挂了重启就好）。这种场景进程内状态是安全的，用 Redis 反而是**画蛇添足**——多了运维成本、多了网络延迟、还得处理 Redis 挂了怎么办。
2. **全部状态都在 DB，不做缓存**：每次请求都查数据库（可能套了 ORM 的一级缓存），能接受 DB 查询延迟。这在 QPS < 100 的管理后台是可行的，但到了 QPS > 1000 或有热点数据（首页配置、商品详情）就扛不住了。

**本项目的不同**：一开始就瞄准 k3s 多副本 + 横向扩容，所以跟老项目的前提不一样——不是「功能一样为什么现在要加组件」，而是**部署形态变了，必须的组件也变了**。


## 三、决策框架：什么状态放哪里（核心）

这是成熟团队真正依据的东西——不是「要不要用 Redis」，而是**「每一类状态该放哪个存储」**，Redis 只是其中一个选项。

### 底层原则：12-Factor App 的「无状态进程」

[12-Factor App](https://12factor.net/processes) 的第 VI 条讲得很直白：**进程应当是无状态的（stateless），任何需要持久化的数据都要存到外部后端服务**（DB、Redis、对象存储）。

原因就是上一节讲的：进程会被随时销毁重建（滚动更新、扩缩容、崩溃重启、pod 漂移），任何存在进程内存里的状态都会在这些时刻丢失或分裂。**无状态进程 + 外部状态存储**是云原生部署的地基，不是可选的优化。

这条原则一旦接受，问题就从「要不要用 Redis」变成了「**外部状态存储该选谁**」——DB？Redis？对象存储？下面这棵决策树给答案。

### 决策树

```
需要存储一份状态
  │
  ├─ Q1: 是否需要跨副本即时一致？
  │   （一个 pod 写了，另一个 pod 立刻要读到）
  │
  ├─ 否 ──→ 单副本部署吗？
  │          ├─ 是 → 进程内 sync.Map / LRU 可以（但不面向未来扩容）
  │          └─ 否 → 大概率 Q1 答错了，重新想：多副本下真的不需要一致吗？
  │
  └─ 是 ──→ Q2: 是否需要持久化（重启 / 宕机不能丢）？
             │
             ├─ 是 ──→ 数据库（PostgreSQL / MySQL）
             │         （订单、用户、权限配置——真相源永远在 DB）
             │
             └─ 否 ──→ Q3: 读写特征？
                       │
                       ├─ 极高读（读:写 > 1000:1）
                       │  且能容忍秒级延迟
                       │  且 DB 是真相源
                       │      → 进程内缓存 + 短 TTL + 变更广播刷新
                       │        （如 PermissionCache）
                       │
                       └─ 其他（写频繁 / 读写均衡 / 需立即一致 / 有 TTL 语义）
                              → Redis
                                （黑名单、验证码、限流、分布式锁、会话）
```

### 关键轴：「跨副本即时一致」

整棵树的第一个分叉——**是否需要跨副本即时一致**——是最重要的判断。把本项目几类状态套进去：

| 状态 | 跨副本即时一致？ | 归属 | 一句话理由 |
|---|---|---|---|
| **JWT 黑名单** | ✅ 必须 | Redis | 撤销后下一个请求（可能落任意 pod）必须立即被拒 |
| **验证码** | ✅ 必须 | Redis | 生成和校验请求可能落不同 pod，必须共享 |
| **限流计数** | ✅ 必须 | Redis | 各 pod 独立计数 = 限流阈值被乘以副本数，失效 |
| **分布式锁** | ✅ 必须 | Redis | 定时任务去重、幂等，跨 pod 互斥 |
| **权限缓存** | ⚠️ 可容忍秒级延迟 | 进程内 + 刷新 | 权限改动后旧权限多生效几秒可接受，DB 是真相源 |
| **订单 / 用户 / 配置** | ✅ 且需持久化 | 数据库 | 真相源，绝不能只在内存 |

可以看到：**大部分需要「立即一致但不需持久化」的状态都落在 Redis**，这正是 Redis 在后端架构里的经典定位——DB 和进程内存之间的那一层共享、快速、带 TTL 的存储。


### 成熟团队的真实做法（不是教科书，是生产默认）

把「大家实际都怎么干」摊开，你会发现这些选择高度收敛——几乎所有主流框架的生产配置都指向同一批答案：

1. **会话 / Token 状态几乎都进 Redis**
   - Spring Session、Laravel、Django、Rails 的生产 session store 默认或首选就是 Redis。
   - **即使用了无状态 JWT，登出黑名单 / refresh token 轮换仍然要 Redis**——因为 JWT 的「无状态」恰恰意味着它没法主动撤销，黑名单是补这个洞的，而黑名单必须跨副本共享。

2. **验证码 / 短信码存 Redis**，用 `SETEX` 带 TTL，过期自动清理，天然契合「几分钟有效」的语义。

3. **限流用 Redis**：固定窗口（`INCR` + `EXPIRE`）、滑动窗口（`ZSET`）、令牌桶（Lua 脚本保证原子）。网关层（Kong、Sentinel、Spring Cloud Gateway）的分布式限流后端基本都是 Redis。

4. **分布式锁用 Redis**：`SET NX EX` 或 Redlock 算法（Redisson 是 Java 生态的事实标准）。用于定时任务去重、防止并发重复处理。

5. **热点数据缓存用 Redis**：cache-aside 模式（先查 Redis，miss 再查 DB 回填），扛住读放大，配合 CDN 分层。

6. **权限 / 配置这类「读极多」的缓存是唯一有分歧的地方**：
   - 中小规模（副本数不多）：**进程内缓存 + 短 TTL + 变更时广播刷新**（用 Redis Pub/Sub 或消息队列通知各副本），兼顾极致读性能和最终一致。
   - 超大规模：干脆统一放 Redis 做集中式 L1，省掉每个副本各存一份的协调成本。

**一个反面提醒：不要自己实现「分布式缓存」。** 自己写一致性哈希 + 副本间 gossip 同步 + 失效传播，本质是在**重新发明一个简陋且没人测过的 Redis**。这件事成熟团队都不做——要跨副本共享内存态数据，用现成的 Redis / Memcached / Hazelcast，而不是手搓。这也是本篇对「自己封装 cache」这个问题的根本回答的一半（另一半见第四节）。

## 四、自己封装进程内 cache 会遇到什么问题

回到用户最实在的一问：**不引入 Redis，我自己用 `sync.Map` + TTL 写一个 `pkg/cache`，不行吗？**

单副本时完全行。**多副本时，你会逐个撞上下面这些墙，而每一堵墙 Redis 都已经替你砌好了门**：

| 问题 | 自封装进程内 cache 的表现 | Redis 现成能力 |
|---|---|---|
| **跨副本状态分裂** | JWT 黑名单只存在 pod-A，pod-B 完全不知情 → 已登出的 token 在 pod-B 照样通行（**安全漏洞**） | 所有副本读写同一份数据 |
| **TTL 要手写** | 验证码过期得自己起定时器扫描删除，还要处理并发删除 | `SETEX` / `EXPIRE` 原生，服务端自动过期 |
| **原子操作缺失** | 限流 `get → +1 → set` 三步非原子，高并发下计数丢失（race） | `INCR` 单命令原子；复杂逻辑用 Lua 脚本原子执行 |
| **内存不可控** | 无淘汰策略，缓存只增不减 → 最终 OOM，pod 被 kill | `maxmemory` + `allkeys-lru` / `volatile-lru` 自动淘汰 |
| **刷新协调困难** | 权限变了，怎么通知另外 4 个 pod 刷新？只能自己写 pub/sub 或让各 pod 轮询 DB 的 dirty flag | Redis Pub/Sub / Keyspace Notification 现成 |
| **无持久化** | 进程重启，所有缓存清零，冷启动瞬间打爆 DB | RDB 快照 / AOF 日志可选持久化 |

**核心结论**：多副本下自封装 cache，为了正确工作，你迟早要给它加上「跨副本同步 + TTL + 原子操作 + 淘汰 + 失效广播」——**加完就是一个自制 Redis，而且没有 Redis 二十年的生产打磨和生态**。这笔账怎么算都是直接用 Redis 划算。

**唯一的例外**是第三节决策树右下角那类状态：**读极多、DB 是真相源、能容忍秒级不一致**（如 PermissionCache）。这类可以进程内缓存，因为它不追求「即时一致」，靠 TTL 兜底最终一致即可——但即便如此，「变更后主动刷新」这一步跨副本协调，仍然要借 Redis Pub/Sub。所以 Redis 不是被绕开了，是退到了协调者的位置。

## 五、Redis 的实际收益与边界（不夸大）

把 Redis 买到的东西列清楚，也把它**不能**做的说清楚：

**收益**：

- **跨副本即时一致**——黑名单 / 验证码 / 限流 / 锁的立身之本。
- **TTL 原生**——「N 分钟后自动消失」的语义免费获得。
- **原子操作**——`INCR`、`SETNX`、Lua 脚本，天然适配计数与锁。
- **内存淘汰**——LRU / LFU 防止无界增长。
- **可选持久化**——RDB / AOF，重启不必冷启动。
- **Pub/Sub**——跨副本广播（如权限刷新），省掉自建消息通道。
- **成熟生态**——`redis_exporter` 监控、RedisInsight GUI、主从 / 哨兵 / 集群高可用方案，都是现成的。

**边界（Redis 不是银弹）**：

- **Redis 不能替代数据库**。它是内存存储，真相源永远在 DB。Redis 挂了重启，丢的是 session（用户重登，可接受）、验证码（重新获取，可接受）；但业务数据（订单、权限配置）**必须在 DB**，绝不能只在 Redis。
- **Redis 的持久化不等于 DB 级可靠**。AOF `everysec` 仍可能丢最后一秒的写。把它当「可以丢的快数据」，不当「不能丢的账本」。

## 六、成本与 tradeoff（不回避）

引入 Redis 实打实的代价：

- **多一个组件**：要部署、监控、备份、升级、做高可用（主从 / 哨兵），运维复杂度 +1。
- **网络延迟**：本地内存访问 ~100ns，Redis 一次网络往返 ~1ms（局域网）——慢约 4 个数量级。所以 Redis 适合「比 DB 快很多、比本地内存慢」的中间层，不是用来替代本地变量。
- **序列化成本**：Go struct ↔ Redis（JSON / msgpack 编解码）的 CPU 与内存开销。
- **又一个故障点**：Redis 挂了，依赖它的 session / 验证码 / 限流全部失效。所以生产环境要主从 + 哨兵，这又叠加运维成本。

**什么时候可以不用 Redis：**

- 单副本 + 小流量 + 不追求高可用——进程内状态完全够用，上 Redis 是过度设计。
- 所有状态都能放 DB、不做缓存、能接受每请求直查 DB 的延迟（低 QPS 场景可行）。

**什么时候必须用 Redis：**

- 多副本部署（k8s / k3s / 多实例）——本项目属于此类。
- JWT 黑名单 / 强制登出（安全要求，不容许「已登出仍可用」的窗口）。
- 验证码 / 短信码（跨请求、跨副本的临时状态）。
- 限流（防刷，必须跨副本共享计数）。
- 分布式锁（定时任务去重、幂等）。
- 热点数据缓存（DB 扛不住读放大）。

一句话：**Redis 的成本，在你选择「多副本部署」的那一刻就已经注定要付**——因为不用 Redis，你就得自己实现跨副本状态共享，那更贵、更容易错。

## 七、落到本项目：逐场景结论

把决策框架套到本项目每一类状态上，直接作为后续实现的 checklist：

| 场景 | 当前状态 | 推荐方案 | 理由 |
|---|---|---|---|
| **JWT 黑名单**（登出 / 撤销） | 未实现 | **Redis**：`SET blacklist:{tokenID}`，TTL = token 剩余有效期 | 跨副本即时一致，安全底线 |
| **验证码**（登录 / 注册） | 未实现 | **Redis**：`SETEX captcha:{key} 300 {code}` | 生成与校验可能落不同 pod |
| **限流**（防刷 API） | 未实现 | **Redis**：固定窗口 `INCR`+`EXPIRE`，或滑动窗口 `ZSET`+Lua | 跨副本共享计数，否则阈值被乘以副本数 |
| **分布式锁**（定时任务去重） | 未实现 | **Redis**：`SET NX EX`，复杂场景 Redlock | 多副本 cron 防重复执行 |
| **PermissionCache**（权限校验） | 规则里有设计，代码未实现 | **进程内 + 短 TTL（1–3min）+ 变更时 Redis Pub/Sub 广播刷新**（混合） | 权限校验每请求都跑、读极高频，内存读最快；秒级延迟可容忍；DB 是真相源 |
| **会话**（若改用 session 而非 JWT） | 未实现（项目用 JWT） | **Redis** | 同 JWT 黑名单理由 |

**核心决策**：本项目瞄准 k3s 多副本，Redis 是**必选项**——黑名单 / 验证码 / 限流 / 锁四类状态在多副本下没有进程内的正确实现。唯一留在进程内的是 PermissionCache（读极多 + DB 真相源 + 秒级延迟可接受），但它的跨副本刷新仍要 Redis Pub/Sub 协调。

**最终答案**：Redis 已经连上、`pkg/xredis` 也封装好了，**直接用，不必犹豫**。它的成本在你选 k3s 多副本时就已经付了；此刻纠结「要不要 Redis」，等价于纠结「要不要自己手搓一个更差的 Redis」——答案显然。

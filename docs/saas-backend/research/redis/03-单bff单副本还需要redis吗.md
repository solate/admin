# 单 BFF / 单副本，Redis 还有意义吗

> 本篇（2026-07）承接 [02-为什么需要redis-进程内缓存vs集中式缓存](./02-为什么需要redis-进程内缓存vs集中式缓存.md)。读完 02 后，一个很自然的反问冒出来：
>
> **「如果是 BFF 结构、大家都跟 BFF 通讯，那 Redis 是不是就没意义了？你说的都是为了多副本状态相同，那如果只有一个 BFF，是不是就没事了？」**
>
> 这是对 02 论证边界的**正确追问**——02 的核心轴是「多副本」，那单副本前提下这套论证是否整体失效？本篇的回答：**你的直觉有一个成立的内核，但结论下过头了。** 单实例确实能砍掉一部分 Redis 用途（这部分我诚实让给你），但有两个漏洞让 Redis 站得住：BFF 是架构角色而非副本数、持久性是一根与副本数正交的独立轴。

## 一、先把你的推理链摆清楚

你的三段论是这样的：

```
BFF 是单一入口（大家都跟它通讯）
  → 所以只有一个 BFF 进程
    → 所以没有多副本一致性问题
      → 所以 02 讲的 Redis 理由全部失效
```

这条链条里，**第一步到第二步**是最大的跳跃（「单一入口」不等于「单一进程」），**第三步到第四步**漏掉了一整根轴（一致性不是 Redis 的唯一理由）。下面先承认它成立的部分，再拆这两个漏洞。

## 二、先承认成立的内核（诚实让步）

如果**真的永远只有一个进程、且永不重启**，那 02 的「多副本状态分裂」论证确实塌了——而且有几个场景不仅不需要 Redis，用进程内反而更简单、更可靠：

- **分布式锁 → `sync.Mutex`**：单进程内 goroutine 之间用标准库互斥锁天然成立，没有网络往返，也不用碰 Redlock 那套有争议的边界（时钟漂移、GC 停顿导致锁失效）。单进程下 `sync.Mutex` 严格优于 Redis 锁。
- **权限缓存刷新 → 直接刷本进程内存**：02 说 PermissionCache 变更后要用 Redis Pub/Sub 广播给其他副本刷新——单进程下这一步整个消失，权限改了直接重建本进程的 map 即可，不需要任何跨进程协调。
- **限流计数 → 进程内 counter 本就正确**：02 说多副本下「10 req/min × 3 pods = 实际 30」，这个失效在单进程下不存在，本地内存计数器就是准确的。

**这部分明确让给你：单实例确实能砍掉「锁 / 权限刷新协调 / 限流」这三类的 Redis 需求。** 你的直觉在「单进程消除多副本一致性问题」这一点上是对的。

问题只在于——「单一入口」真的等于「单一进程且永不重启」吗？下面两节就拆这个前提。

## 三、漏洞 1：BFF 是架构角色，不是副本数

「BFF」（Backend For Frontend）描述的是**职责**——为某个特定前端（Web / App / 小程序）做接口聚合、裁剪、协议适配的那一层。它讲的是**流量拓扑与分工**，不是**部署了几个实例**。

「大家都跟 BFF 通讯」是说所有前端流量都经过 BFF 这个**逻辑角色**，不是说这个角色只由**一个进程**承载。这两件事在生产里几乎总是分开的：一个逻辑 BFF，背后跑 N 个副本，前面挂一个负载均衡把流量分发过去。

BFF 会多副本，理由和任何在线服务完全一样：

- **高可用**：一个 pod 崩了 / 节点挂了，其他副本立刻顶上。单实例意味着这个进程一挂，全站前端全部 502。
- **滚动发布**：零停机部署本身就要求发布期间同时存在新旧两个版本的实例（k8s 滚动更新先起新 pod、再摘旧 pod）。想不停机发版，发布的那一刻你就是多副本。
- **横向扩容**：流量涨了加副本，是最基本的扩容手段。

而且这里有一个**反噬点**：BFF 是所有前端流量的**必经单一入口**，这恰恰是整个系统里**最不该做成单点故障（SPOF）**的位置。把最关键的咽喉做成单实例，等于赌这个进程永不出问题——发布、崩溃、节点故障任意一个都会让全站瘫痪。所以生产环境里 BFF 不但会多副本，而且是**优先级最高的多副本对象**。

**结论**：一旦 BFF 多副本（对全站入口几乎是必然），02 的整套「多副本状态分裂」论证原样回来——黑名单 / 验证码 / 限流 / 锁又全部需要跨副本共享。你的「单一入口」前提，在部署现实面前不成立。

## 四、漏洞 2：持久性轴（与副本数正交）

现在做最大的让步：**假设你铁了心，就是要跑一个 BFF 实例，永不扩容。** Redis 就没意义了吗？还是没有——因为你只消除了「副本轴」，还有一根**正交的轴**没处理：**进程会重启**。

单实例不等于「永远活着的同一个进程」。它仍然会重启，而且很频繁：

- 每次**发布新版本**（改一行代码上线就重启一次）
- **崩溃**（panic / OOM 被 kill）
- **节点驱逐 / 重调度**（k8s 把 pod 挪到别的节点）
- 机器重启、基础设施维护

**每一次重启，进程内存里的所有状态清零。** 具体后果：

- **JWT 黑名单**：用户点了「登出」，系统把这个 token 拉黑存进内存 → 两分钟后你发了个版、进程重启 → 黑名单空了 → 这个「已经登出」的 token 在它自然过期前**重新生效**。任何拿到这个 token 的人（比如泄露的旧 token）又能用了。这是一个**安全窗口**，而且发生在最不起眼的「发个版」动作上。
- **验证码**：用户请求验证码（存内存，5 分钟有效）→ 恰好这时滚动发布 / 重启 → 验证码没了 → 用户输入正确也校验不过，登录失败。发布期间所有在途验证码全灭，这是**发布期 UX 事故**。

**关键洞察——这是两根独立的轴：**

| 轴 | 方向 | 问什么 | 单实例能消除吗 |
|---|---|---|---|
| **副本轴**（02 的主题） | 横向：同一时刻多个进程 | 状态在 pod 之间一致吗？ | ✅ 能（单进程无此问题） |
| **重启轴**（本篇补充） | 纵向：同一角色跨时间的进程生命周期 | 状态在进程重启后还在吗？ | ❌ 不能（重启照样丢） |

02 讲的是副本轴，你的「单 BFF」反问只打到了副本轴。但**靠持久性活着的状态**（黑名单、在途验证码）依赖的是重启轴——单实例一根汗毛都没动到它。这类状态即便真的单实例，也需要一个**能跨进程重启存活的外部存储**：Redis（带 TTL、够快）或 DB（更持久、更慢）。

换句话说：**Redis 的意义从来不只绑定在「多副本一致」这一个理由上。** 它同时是「跨重启存活的快状态存储」。你砍掉了副本轴，重启轴还在。
